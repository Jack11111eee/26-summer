## 0. 当前总判断

当前状态不能简单表述为“已经全部收敛”或“还没有任何结论”。准确表述是：

> **非 Prompt 的总体架构、核心业务原则和测评路径已经基本收敛；但题量公式、难度状态转换、综合题评分、缺失聚合、事件表契约、数据库字段、计时器边界和修复验收标准仍未达到可以直接实施的细化程度。**

当前可以分成三层：

```text
已对齐的产品/架构原则
    ↓
已基本对齐的测评路径和状态方向
    ↓
尚需对齐的公式、字段、状态转换和验收细节
```

Prompt 讨论明确延后到非 Prompt 设计基本收敛、并得到用户授权写入正式设计文档之后。但在此前所有需要 Prompt 的位置，都必须保留接口或稳定记录，不能因为当前使用规则/mock 就封死未来扩展。

# 1. 已基本收敛的内容

以下内容已经经过前几轮讨论确认，可作为后续正式设计整理时的基础。它们尚未写入 SSOT，也尚未授权实施。

## 1.1 总体架构原则

1. 使用当前 FastAPI 服务，加一个明确的领域状态机；
2. 不立即引入 CrewAI、Google ADK、Haystack 等通用 Agent 框架；
3. 不采用自由 ReAct 控制整场测评；
4. 采用有界测评循环：

   ```text
   Observation → Policy/Plan → Act → Evaluation → Persist
   ```

5. LLM 可以提供结构化观察、分类或话术建议；
6. 代码负责题量、状态迁移、预算、难度护栏、权重、评分聚合和最终报告发布条件；
7. 所有过程状态、版本、证据、工具调用和异常都应可审计。

## 1.2 业务范围

本系统只做：

- 测评用户的人才画像报告；
- 各能力项评分；
- 评分证据展示；
- 测评过程和异常记录；
- 必要的人工复核。

本系统不做：

- 最终录用判断；
- 最终录用排序；
- 自动通过/淘汰；
- 代替企业作出招聘决定。

因此，后续正式设计应删除或改写“最终录用排序”“录用结论”等超出范围的表述。

## 1.3 题库分类

普通对话题库只使用两个大类：

```text
hard_skill
└── required / preferred / plus

soft_skill
└── required / preferred / plus
```

`experience` 与 `qualification` 不进入普通对话题库的三层分类：

- `qualification`：只走结构化表单，不占普通主问题配额；
- `experience`：通过表单/简历检测，不占普通对话主问题配额；
- 两者仍需保留岗位模型的可追溯性，但应通过 `measurement_mode=form` 等方式排除普通题目选择。

## 1.4 普通题与综合题

### 普通题

- 只能绑定一个主评分能力项；
- 必须绑定岗位模型版本、`category`、`tier`、`difficulty`、题型和 rubric 版本；
- 可有非评分标签，但不能通过辅助字段偷偷绑定第二个评分能力项；
- 不同题面分别创建新的 `assessment_question` 实例。

### 综合题

- 单独建立综合题库/逻辑范围；
- 可以绑定多个能力项；
- 每个绑定项必须有独立 `measurement_target`、证据要求和评分映射；
- 在普通 hard/soft 计划完成或合法封存后进入独立综合阶段；
- 拥有独立题量槽位，不占普通 hard/soft 配额；
- 每次 session 最多两题；
- 一题绑定多个能力项，不等于多个能力项自动完成测量；
- 必须防止一段证据被无依据地复制到所有绑定能力项。

## 1.5 主问题与追问

普通能力题的路径为：

```text
easy → medium → hard
```

综合题是后续独立测量阶段，不是普通难度的第四级：

```text
普通 hard/soft 阶段完成或合法封存
→ integrated question 阶段
```

`followup` 的规则：

- 属于当前题实例内部的补证据子轮次；
- `question_id` 不变；
- 不创建新的主问题实例；
- 不增加普通主问题数量；
- 不占综合题槽位；
- 每题最多两次追问。

如果 easy、medium、hard 各自对应不同题面，则每个实际呈现的题面都是一个新的普通主问题实例；它们属于同一能力项的 `difficulty_path`，但不是同一个题目实例。

## 1.6 hard/soft 的 7:3

已确认：

```text
hard_skill : soft_skill = 7 : 3
```

同时作用于两个不同层面：

1. 普通能力项最终 `item.weight` 的大类总权重比例；
2. 普通主问题的基础数量比例。

两者不能在最终聚合时重复相乘。

最终权重层：

```text
Σ hard item.weight = 0.70
Σ soft item.weight = 0.30
```

题量资源层：

```text
hard_base_quota : soft_base_quota ≈ 7 : 3
```

如果某大类不存在有效能力项，则存在的大类重新归一到 1.00；具体是否允许“有 item 但无有效题库”仍需在实施规则中明确。

## 1.7 类内 required/preferred/plus

已确认：

- `required / preferred / plus` 影响原始重要性、题量配额和覆盖优先级；
- `required` 具有刚性覆盖要求；
- 三层不再额外乘最终分数；
- 最终业务权重仍由岗位模型的 `item.weight` 表达。

## 1.8 难度不作为第三层最终权重

已确认：

- 难度不直接作为最终权重；
- 不使用诸如 hard 题乘 1.2 的额外加分；
- 难度通过测量路径、行为锚点和可观测等级上限体现；
- 高难度题答对可以支持更高能力等级，但必须满足该题自身 rubric；
- 低难度题高质量回答不能自动支撑超过其配置的最高可观测等级；
- 难度不改变 `item.weight`。

## 1.9 `score_live` 的角色

已确认采用方案 A：

> `score_live` 只作为过程性选题和难度导航证据，不参与最终分数计算。

最终评分链为：

```text
原始回答证据
→ 独立终局评分 score_final
→ item 聚合
→ 固定 item.weight 加权
→ 画像报告
```

不再使用：

```text
0.5 × score_live + 0.5 × score_final
```

## 1.10 证据、拒答和缺失的总体方向

- 明确拒答：`score_value=0 + score_state=REFUSED`；
- 拒答事件必须留痕并进入画像分析；
- 拒答不应与“1 分能力行为锚点”混淆；
- 网络中断属于系统错误，不扣分；
- 题目无效、系统未能完成提问、模型无法判断，不应搁置，必须进入人工处理或不完整状态；
- 缺失证据触发人工复核；
- 普通非 gate 能力项允许按观察比例补算，并标记 `IMPUTED`；
- `required` 和 `qualification` 不适用普通缺失项比例补算；
- required 缺失时可以生成带警告的临时画像报告；
- required 缺失触发人工复核，但不触发补测；
- 系统不做最终录用排序或最终录用判断，因此不讨论“临时分是否参与录用排序”。

## 1.11 时间和 Token

已确认：

- 全场活跃测评时间不超过 40 分钟；
- 单题计时器不超过 20 分钟；
- 时间只由计时器控制，不参与题目筛选优先级；
- 不因为时间预算不足而提前拒绝合法的 chain、升级或降级动作；
- 全局追问总数暂不设置独立上限；
- 每题最多两次追问仍是硬约束；
- 暂不启用全会话 Token 硬上限；
- 暂不启用模型输出 Token 硬上限；
- 但必须预留配置接口；
- 不做 24 小时自动删除，数据和日志作为证据保留。

## 1.12 上下文管理

确认采用三层分工：

| 层级 | 作用 |
|---|---|
| 原始证据层 | 保存候选人原始回答、hash、时间、题目和技术记录，不被覆盖 |
| 交互上下文层 | 为当前 interviewer 提供当前题、必要消息、策略和有限历史 |
| 导航摘要层 | 保存 item 覆盖、难度、chain、异常和待处理状态，服务下一题选择 |

其中：

- P-refine 是单条回答级压缩；
- 会话滑窗是多轮历史级裁剪；
- 结构化摘要是状态/证据导航级压缩；
- 摘要和精炼文本都不能替代终局评分所需的原始证据。

## 1.13 数据库总体方向

已确认：

- 题库逻辑上是树，数据库物理上使用扁平规范化表；
- 当前不新增 `question_bank_relation` 表；
- 需要留下未来扩展记录/接口，复杂关系出现时再增加关系表；
- session 采用动态实例化方案 A；
- 新增一张 `assessment_state_event` 表承载所有会话状态事件；
- 当前状态字段与不可变事件历史分工保存；
- 状态更新和事件写入需在同一事务完成；
- 不因每一种状态建立专用表，优先扩展现有测评表。

## 1.14 Prompt 安排

Prompt 讨论延后：

- 等非 Prompt 设计完全收敛；
- 用户明确授权写入正式设计文档后；
- 再单独讨论独立 Prompt 模块。

但前面已经识别出的所有 Prompt 场景都必须：

- 预留可替换接口，或
- 留下稳定的 Prompt 扩展记录。

不能因为当前使用规则/mock，就把未来需要 LLM 的边界硬编码封死。

# 2. 尚未完全收敛的非 Prompt 内容

## 2.1 普通主问题目标数量 `N`

已确认 7:3 是普通主问题的基础比例，但还没有最终确定：

- `N` 是固定 10、11、12，还是岗位级策略配置；
- `N` 是否按普通能力项数量和最低覆盖要求生成；
- 同一 item 的 easy/medium/hard 每个不同题面都计入普通主问题数量；
- required 刚性例外如何影响实际数量；
- `N` 是否有岗位级最小值和最大值。

## 2.2 hard/soft 内部题量算法

仍需精确化：

- `required / preferred / plus` 的类内权重如何转为整数题量；
- required 最小覆盖与比例题量冲突时的优先级；
- 小数配额是否使用最大余数法；
- 题库不足时名额如何转移；
- preferred/plus 是否可能被完全挤掉；
- item 之间如何结合 `item.weight` 和未覆盖状态进行选择。

## 2.3 固定优先级和动态选题执行顺序

原则已明确，但需要落成可执行函数：

1. 过滤无效版本、无效题和当前不可访问状态；
2. 当前题仍需合法 followup 时，不选主问题；
3. 优先覆盖未测量的 required item；
4. 检查 category/tier 剩余配额；
5. 检查当前 item 的难度路径；
6. 检查 chain 后继是否满足条件；
7. 根据 item.weight、题目质量和稳定随机种子选择。

仍需明确上述条件在冲突时的绝对顺序、伪代码和边界测试。

## 2.4 难度路径的最终状态转换

仍需细化：

- easy 何时结束并进入 medium；
- medium 何时结束并进入 hard；
- hard 何时结束并进入综合阶段；
- 证据充分和稳定证据的最终阈值；
- followup 后仍模糊时的处理；
- 题库缺少中间难度时是否允许跳级；
- 某 item 是否必须尝试 hard；
- 最高难度题的最小尝试规则。

## 2.5 升级、降级和降级后恢复

已确认方向，但仍需最终写成状态表：

- 正常 `easy → medium` 需要几次充分证据；
- 正常 `medium → hard` 是否需要一次充分证据加稳定记录；
- 跳过、连续两次同难度有效失败、追问后仍模糊/错误时如何降级；
- 最低难度不能继续降级；
- 降级后是否必须两次连续充分证据或一次强证据才能恢复；
- 恢复后如何防止升降震荡；
- 技术故障、拒答、题目无效和模型不确定不应被视作普通答错。

## 2.6 “证据充分”和“稳定证据”

方向已确定，但需要落实：

### `evidence_sufficient`

当前候选条件：

- 与题目 `measurement_target` 相关；
- 覆盖 rubric 要求的必需考察点；
- 包含具体、可归因的行为/事实；
- 不是拒答、跑题、纯态度或复述题目；
- 可定位到原始回答 span；
- 未触发模型不确定或题目无效。

### `stable_evidence`

当前候选条件：

- 两次独立有效观察，或一次高难度强证据；
- 证据不互相矛盾；
- 不是同一回答重复切片；
- 没有依赖未经批准的答案线索；
- 版本和难度可追溯。

仍需确定各条件的机器可判定方式和冲突处理。

## 2.7 难度与最终分数的映射

已确认难度不直接加权，但仍需确定：

- 每个 item 的 `observable_level_max` 如何配置；
- easy/medium/hard 对 1–5 能力等级的支撑边界；
- `required_level` 如何影响最高难度路径；
- 多个不同难度题如何在 item 内合并；
- hard 题答错与 easy 题答错如何分别解释；
- 综合题是否可以提供最高等级证据；
- 同一个 item 的普通题和综合题证据如何共同进入终局评分。

## 2.8 综合题评分和证据拆分

仍需明确：

- 综合题是否生成一个整体分，还是只生成各 item 分；
- 一个回答中的证据如何拆给多个 item；
- 同一证据 span 是否允许被多个 item 引用，以及什么条件下允许；
- 综合题的 item 分是否写入现有 `question_score`；
- 综合题最多两题时如何决定是否激活第二题；
- 综合题是否只能补充普通 item，不能绕过普通题最低测量要求；
- 综合题整体无效时所有绑定 item 如何处理。

## 2.9 required 刚性例外

已确认可以增加普通主问题数量、不改变 `item.weight`，但还需明确：

- 同一 required item 最多触发几次；
- 例外题从什么难度开始；
- 例外题能否沿 easy→medium→hard 路径；
- 例外题是否允许使用综合题；
- `ordinary_exception_count` 的统计口径；
- 例外后仍缺失时的报告字段和人工任务；
- 例外是否有独立事件类型和报告警告等级。

## 2.10 缺失、拒答和补算

总体方向已确认，但仍需形成完整公式和状态机：

- 同一 item 一题拒答、一题有效回答时如何合并；
- `REFUSED` 是否始终按 0 参与普通 item 聚合；
- `INSUFFICIENT_EVIDENCE` 是否进入观察分分母；
- `NOT_ADMINISTERED`、`INVALIDATED`、`MODEL_UNCERTAIN` 的分母规则；
- 普通缺失项比例补算时观察集合 `O` 的精确定义；
- 没有任何有效观察项时是否能补算；
- required 缺失的临时报告状态名称；
- 人工复核后能否修订状态或分数；
- `IMPUTED` 是否显示在候选人报告中。

当前用户确认的范围是：

- 普通非 gate 缺失项允许比例补算并标 `IMPUTED`；
- required/qualification 不做这种补算；
- required 缺失允许临时报告；
- required 缺失触发人工复核，不触发补测；
- 系统不做录用排序或最终录用判断。

## 2.11 `assessment_state_event` 事件表契约

已确认新增一张专用表，但仍需细化：

- 最终字段和外键；
- `event_type` 枚举；
- `from_state/to_state` 的适用范围；
- 哪些信息放普通列、哪些放 `payload_json`；
- 幂等键作用域；
- 事件是否全量追加且不可修改；
- 事件与主状态同事务的具体实现；
- 读取当前状态与事件回放的边界；
- 管理端按 session 查询完整轨迹的接口。

## 2.12 数据库最终字段与迁移

仍需确定：

- `question_bank` 的普通题/综合题字段；
- 多 item 绑定是 JSON 快照还是轻量关联结构；
- `assessment_question` 的动态实例字段；
- `assessment_message` 与 `question_score` 的字段职责；
- `evidence_coverage`、`measurement_target`、`rubric_mapping` 的存储方式；
- `equivalence_group_id` 的约束；
- form schema 是代码常量、JSON 快照还是未来独立表；
- `user_profile` 继续延后还是本轮重新决定；
- SQLite 迁移和回滚方案；
- 新表索引和数据增长策略。

## 2.13 表单 Tools 接口

原则已确认，但仍需接口级设计：

- `render_form` 请求/响应 schema；
- `get_form_schema` 是否作为正式 API；
- `submit_form` 的幂等键和重复提交行为；
- form instance 生命周期；
- gate 结果存储位置；
- 字段错误返回格式；
- `request_pause` 与计时器的关系；
- `extract_form_facts` 的证据结构和人工确认流程。

## 2.14 计时器边界

已确认时间只由计时器控制，但仍需明确：

- 全场计时从哪个事件开始；
- 单题计时从展示、激活还是首次回答开始；
- followup 是否继续使用同一单题计时器；
- 系统等待、网络重试、人工等待是否暂停；
- 页面关闭和恢复如何计时；
- 候选人主动暂停如何记录；
- 单题 20 分钟后的状态；
- 全场 40 分钟后的状态；
- 服务端还是客户端作为时间权威；
- 如何防止客户端修改时间戳。

## 2.15 证据链严格锚定

底层链路已经存在，但仍需明确修复规格：

```text
report
→ session
→ model/version
→ question
→ message
→ trace
```

需要确定：

- trace 是否直接关联 message/question；
- 综合题证据如何关联多个 item；
- evidence span 的偏移定义；
- 精炼文本和原文如何同时引用；
- 报告结论最低证据要求；
- 评分失败时报告是否允许发布；
- 报告发布前的数字、事实和引用一致性校验。

## 2.16 后续修复的验收标准

已确认现有差距先记录、不立即修复，但还需要为后续修复文档建立验收口径：

- 动态选题；
- 非末题 `finish` 护栏；
- 状态分类；
- 终局评分接入正常 UI；
- 资源所有权校验；
- 网络幂等重试；
- 会话历史恢复；
- 失败任务可观测性；
- M1 回归测试；
- 前端 E2E；
- eval 数据隔离；
- 题库和综合题约束测试。

# 3. 目前不应误解的事项

1. “架构基本收敛”不等于“可以立即改代码”；
2. “确认 7:3”不等于题量 `N` 已经确定；
3. “难度不加权”不等于难度对能力等级没有影响；
4. “综合题可绑定多个 item”不等于一题自动测出多个能力；
5. “拒答记 0”不等于正式能力量表已经改成 0–5；
6. “required 缺失可出临时报告”不等于系统做录用排序；
7. “允许补算普通缺失项”不等于缺失 required 也能自动补算；
8. “时间不参与选题过滤”不等于计时器到点后可以继续无限对话；
9. “使用 Tools”不等于把所有 API 暴露给 LLM；
10. “预留 Prompt 接口”不等于现在就开始 Prompt 设计；
11. “有证据链底层组件”不等于当前 answer→score→report UI 主链已经闭合；
12. 前六轮临时讨论稿和本文件都不是 SSOT。

# 4. 推荐的后续讨论顺序

为减少反复修改，建议按以下顺序继续：

## 第一步：先定题量模型

依次确定：

1. `N` 的来源和范围；
2. 7:3 如何转为大类整数配额；
3. hard/soft 内部 tier 配额；
4. required 最小覆盖和刚性例外；
5. 综合题独立槽位和数量。

## 第二步：再定难度和路径状态机

依次确定：

1. easy/medium/hard 的题库定义；
2. 证据充分；
3. 稳定证据；
4. 升级；
5. 降级；
6. 降级后恢复；
7. 综合阶段入口；
8. 最高难度覆盖。

## 第三步：定评分和缺失数学

依次确定：

1. `score_final` 的能力等级映射；
2. 难度与可观测等级上限；
3. 综合题 item 证据拆分；
4. 拒答 0；
5. 普通缺失项 `IMPUTED`；
6. required 缺失临时报告和人工复核；
7. 无效题/模型不确定/系统错误。

## 第四步：定数据库和事件模型

依次确定：

1. `question_bank`；
2. `assessment_question`；
3. `assessment_message`；
4. `question_score`；
5. `form_submission`；
6. `assessment_state_event`；
7. trace 严格锚定；
8. 迁移、索引和增长策略。

## 第五步：定计时器和上下文落地

依次确定：

1. 计时起止事件；
2. 暂停/恢复；
3. 单题/全场超时；
4. P-refine；
5. 滑窗；
6. 导航摘要；
7. 恢复和摘要失败。

## 第六步：非 Prompt 设计收敛后，才开始 Prompt 模块

届时再逐项处理：

- 用户先拟 Prompt 初稿；
- 技术侧补充 schema、边界、失败策略、版本、trace、测试和人工接管条件；
- 逐项确定哪些真正需要 LLM，哪些由代码替代，哪些暂不做。

## 第七步：用户授权后更新正式设计

只有在上述内容完成对齐并获得明确授权后：

1. 更新 `design/总设计文档.md` 正文；
2. 更新 §13 变更日志；
3. 再建立独立修复/重构实施文档；
4. 再实施数据库迁移、代码修改和测试；
5. 最后进行联调、评测和审计验证。

# 临时讨论稿：题库状态页与生成可观测（2026-09-08）

> **文档身份**：临时讨论稿。只记录调研事实、用户裁决与 SSOT 增补草案，**不构成实施或 SSOT 写入授权**。SSOT（《design/final-design/总设计文档.md》）修订须用户明确授权后按文档治理规则以原子 commit 写入。实施一律新分支。

## 1. 背景与需求

用户 2026-09-08 提出：前端题库状态显示单薄——管理端仅有 `/admin/todos` 聚合出的「题库未就绪」KPI 计数 + 页脚一条 `error_msg`（且只显示最新一条失败）；失败排查时只能看到一条 SQLite 原生报错原文。要求新增左侧栏「**题库状态**」页面，覆盖三类状态：

1. **已落库**：可点入查看具体信息（统计概览 + 题目表）；
2. **生成中**：进度条 + 当前到哪一步；
3. **失败**：详细报错信息，便于调试（含 LLM 调用链溯源）。

本轮先讨论对齐、不实施。

## 2. 现状事实（两路只读调研，file:line 以 2026-09-08 工作区为准）

### 2.1 前端（web-next/，当前唯一活跃前端）

- **侧栏/路由**：`AdminShell.vue` navItems 现有 5 项（岗位库/岗位详情/能力词典/用户管理/测试中心，:66-71）；`router/index.js` 管理端 7 个子路由。新页面 = 新增子路由 + nav 项，改造面小。
- **现有可见性全部依赖 `GET /api/admin/todos` 聚合**：`question_bank_not_ready` 计数（Positions.vue KPI 第 4 卡 :34-38）+ `question_bank_failed` 明细（**不含 task_id**）；页脚 `qbankFootText`（:243-246）只取 `failed[0].error_msg` ——「一条报错」的直接原因。
- **错误展示**：全前端仅 toast（3.2s 消失）/ 页内 banner / `errMsg` 取 `detail.message` 单值短路（api/index.js:37-43）；无逐条错误列表 UI。
- **retry 死接线**：`retryQuestionBankTask(taskId)` 已定义（api/index.js:101）、后端端点完整（models.py:333-363），但**前端零调用**，且 todos 明细不含 task_id，无处取得——题库状态页是它的天然首个消费方。
- **可复用模板**：ModelReview.vue 聚合进度条 + 3s 轮询 + RUNNING 认领接续（:37-47、:617-687）；TestCenter.vue 任务卡三态 + 历史；PositionDetail.vue UiDrawer 分层折叠 + error_msg banner。admin.css token（--danger/--n1/--ink-*）直接可用。

### 2.2 后端（server/）

- **管线**：`generate_question_bank`（services/question_bank.py:92-183），FastAPI BackgroundTasks 串行执行；粒度 = competency_item × 难度档（`_question_plan` :16-30）；每档做 (std_name, category, difficulty) 幂等补缺档查重（:137-145）；**每个难度档 commit 一次**（:171）；只处理 hard_skill/soft_skill（SSOT §9.1 收口）。
- **任务表**：`question_bank_task`（db.py:391-406）：`task_id / position_id / model_id / model_version / status(QUEUED|RUNNING|SUCCEEDED|FAILED) / created_at / started_at / finished_at / error_msg`。**无任何进度列**；状态更新仅入口 RUNNING（:109）、岗位不存在 FAILED（:102）、正常 SUCCEEDED（:172）、兜底 FAILED（:177）——**中途零更新**。
- **失败详情**：`error_msg = str(e)[:200]`（:177）——单值、200 字符截断、仅最后一个异常。落表失败静默 pass（:179-180）。
- **查询面缺失**：无任务列表 / 单任务详情 / 题库维度统计端点（对比聚合管线有 `GET /admin/positions/{id}/aggregate/progress`，models.py:51-69）。
- **重启收尸缺失（坑）**：`init_db` 启动 sweep 只清 `aggregate_task` RUNNING 残留（db.py:1118-1125）；`question_bank_task` **无对应 sweep**——进程重启后 RUNNING/QUEUED 残留行永久滞留；且 retry 仅接受 FAILED（models.py:349-350）、confirm 对已确认模型恒 409（models.py:305-306）→ 该岗位**永久锁死在「生成中」**。
- **llm_trace**（db.py:118-130）：记每次调用 prompt/response/error（question_gen 已落，ref_id=item_id），但与 task 行无关联维度（question_gen 不写 trace_link）。
- **对齐先例**：`aggregate_task`（SSOT §8.4，2026-09-07）把同一类问题完整解过一遍——进度列 + 进度端点 + 逐项 commit + 启动 sweep + 前端轮询/RUNNING 认领。题库任务表设计可整体移植，差异见 §4。
- **SSOT 现状**：`question_bank_task` 在 §6 表清单有登记、**无字段级定义小节**（D-12 代码先行）；§5 运行契约「接受 BackgroundTasks 内存执行，不要求进程重启后任务恢复」；§13.2 状态事件枚举含 TASK_* 四态但题库生成不发事件。

### 2.3 故障复盘 `qbt_74fedfff3a23`（证据链实锤，非推测）

- **时间线**（data/app.db）：2026-09-08T02:07:05 建任务（pos_843e848db455，模型版本 3）→ 02:07:07 LLM 调用 1 成功（1 题入库）→ 02:07:11 LLM 调用 2 成功 → **INSERT 抛 `Error binding parameter 14: type 'list' is not supported`** → 任务 FAILED，error_msg = SQLite 驱动原文（经 `[:200]` 截断入库 → todos → 前端页脚透出）。
- **实锤**：`llm_trace` 存了第 2 次调用原始响应，解析得 `{stem: str, difficulty: str, qtype: "subjective", answer_key: null, rubric: list[str]×4}`。`_insert_question`（question_bank.py:62-71）INSERT 共 19 参，**第 14 参 = rubric = `q.get("rubric")` 裸透传**（:167）。CR-01 分支（:156）只拦「objective 缺 answer_key」的题；本题为 subjective，list rubric 直达 INSERT。
- **根因**：question_gen prompt 要求「rubric 给 3~5 条可观察的评分要点」（services/prompts/question_gen.py:20），LLM 自然返回 JSON 数组；mock 路径 `_mock_question_gen` 返回 str（question_bank.py:53），**离线测试永远打不中**——只有真实 provider 触发。
- **修复状态（登记）**：并行会话已在本工作区实现归一化修复（未提交）：`_as_text`（list → 分隔符 join，rubric 用 `\n`、answer_key 用 `|` 对齐 scoring 正则分支口径）+ CR-01/WR-06 判断前移消费归一值 + 2 个直击故障形态的回归用例。本稿登记不重复派发。修复后对该任务点 retry，幂等补缺档逻辑将补齐该岗位剩余档位（已有 1 题留存）。
- **附带确认的伴生雷**：CR-01 分支旧代码 `(q.get("rubric") or "").strip()` 对 list rubric 抛 `AttributeError`（本次报的是 sqlite 错误，说明该题是 subjective/或带 answer_key 的 objective）；归一化前移同时消除。

## 4. SSOT 增补草案：§9.5 题库生成任务可观测（待授权）

> 授权后写入位置：总设计文档第三部分 §9 内新增 §9.5（对齐 §8.4 先例的文档形态），§6 表清单列说明同步，§14 变更日志记一行。以下为草案正文。

**表 `question_bank_task` 增列**（存量库启动自动补列，幂等迁移）：

| 新列 | 类型 | 说明 |
|---|---|---|
| total / done | INTEGER | 计划生成的 (item × 难度档) 总数（循环前写入）/ 已完成数（含幂等跳过档，循环内逐档 +1） |
| current_item | TEXT | 正在处理的 `(std_name, category, difficulty)`（liveness 信号） |

与 `aggregate_task` 的**有意差异**（登记）：① 保留 `QUEUED` 态——confirm 事务先插行、再调度后台任务（db.py:393 既有语义，后台异常前三态可查）；aggregate 无排队阶段故不设；② 已有 `model_version` 列（题库单元 = 岗位 + confirmed 模型版本）；③ 触发源仅 confirm / retry 两路，无 trigger_source 列需求。

**行为规则**：

1. **进度更新**：`generate_question_bank` 循环内逐档 UPDATE done/current_item + commit（与题目写入同事务节奏；逐次 commit 防轮询连接长持锁——§8.4 已论证同型问题）。total = Σlen(plan)（跳过 exp/qual 后）。
2. **启动 sweep**：`init_db` 将 `question_bank_task` RUNNING/QUEUED 残留行一次性置 FAILED（error=「进程重启中断」）——对齐 aggregate_task 先例；与 §5「不要求进程重启后任务恢复」一致（不自动重启，人工 retry）。
3. **error_msg 截断放宽**：`str(e)[:200]` → `[:2000]`。存量 200 字符行不回填。
4. **llm_trace 关联**：不改表。详情查询按任务时间窗（`created_at~finished_at`）× `call_type='question_gen'` × 模型 item 集关联（ref_id=item_id），prompt/response/error/attempt 逐次可溯。

**端点契约**（admin）：

| 端点 | 语义 |
|---|---|
| `GET /admin/question-bank-tasks` | 按 (position, model) 取最新任务行聚合列表：岗位名、model_version、status、done/total/current_item、error 摘要、题量（join question_bank 计数）、时间戳、task_id。服务端分页（§31 分页契约）。支持 status 过滤。 |
| `GET /admin/question-bank-tasks/{task_id}` | 单任务详情：全字段 + 同 (position, model) 历史任务行（retry 留档可见）+ llm_trace 时间窗调用列表（可选展开单次 prompt/response） |
| `GET /admin/question-bank-tasks/{task_id}/questions` | 题目表（该岗位×模型）：std_name/category/difficulty/qtype/stem 预览，分页。统计概览（item × difficulty 覆盖矩阵）由详情端点聚合返回 |

**前端**（web-next）：左侧栏新增「**题库状态**」（`/admin/qbank`，AdminShell navItems +1）：

- 列表页：status 过滤（全部/生成中/已落库/失败），每行 = 岗位 × 模型版本（裁决 4）：状态 tag、进度（生成中显示进度条 + done/total + 当前项，3s 轮询；RUNNING 行进页认领接续）、题量、时间；
- 行点击 → UiDrawer 详情：任务状态卡；已落库 → 统计概览（item × 难度覆盖矩阵）+ 题目表（题干预览，分页）（裁决 5）；失败 → error 全文 + 历史任务行 + llm_trace 逐次调用展开（裁决 3）+ **retry 按钮接线现有端点**（取本行 task_id——列表与详情均含）；
- 展示形态抄 ModelReview.vue 进度模式与 PositionDetail.vue 抽屉模式。

**边界**：列表以 task 行驱动；「有题无任务行」的 D-12 前遗留组合当前库为 0（§2.4 核验），若历史库出现不入列表（不迁移不补挂）。

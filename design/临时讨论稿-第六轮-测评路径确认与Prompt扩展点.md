## 1. 本轮确认结果

用户确认第五轮第 1–9 项均无问题。由此，本轮确认以下事项作为后续正式设计整理时的依据：

1. `integrated question` 是独立测量阶段/题型，不是普通难度的第四级；
2. 普通能力项的难度路径是 `easy → medium → hard`；
3. 如果不同难度对应不同题面，每个实际呈现的题面都创建新的 `assessment_question` 实例；
4. `followup` 属于当前 `assessment_question` 实例内部的子轮次，不创建新的主问题实例；
5. 综合题对某能力项具备独立 `measurement_target`、独立证据和独立评分状态时，可以计为该能力项的一次有效测量；
6. 普通 hard/soft 能力项必须先获得至少一次普通题测量，综合题可以补充，但不能替代这次最低普通测量；
7. 综合题在普通 hard/soft 计划完成或合法封存后进入；
8. 普通计划、required 刚性例外、综合题槽位分别记录：
   - `ordinary_plan_count`；
   - `ordinary_exception_count`；
   - `integrated_plan_count`；
9. 综合题每次 session 最多两题；
10. 暂不展开独立 Prompt 模块的说明、拟定和对齐，待其他设计讨论完全收敛并经用户批准写入正式设计文档后，再单独讨论。

## 2. Prompt 扩展点要求

虽然 Prompt 内容本轮不讨论，但用户明确要求：

> **前文所有未来需要 Prompt 的位置，都必须预留接口或记录，不能因为 Prompt 尚未讨论而把扩展点丢失。**

这里的“预留接口或记录”不等于现在实现 Prompt，也不等于现在引入 LLM。它至少包括以下两种形式之一：

### 2.1 需要运行时扩展的地方：预留接口

如果未来该步骤需要 LLM 参与，应在正式实现相关领域服务时保留可替换的调用边界，例如：

```text
classifier interface
observation interface
evidence evaluator interface
probe generator interface
scaffold generator interface
integrated scorer interface
report writer interface
```

接口应允许未来注入：

- Prompt 版本；
- 模型标识和版本；
- 输入/输出 schema；
- trace 关联；
- 重试和失败策略；
- 人工接管；
- mock/真实实现切换。

但接口本身不能授权 LLM 越过代码状态机修改：

- 题量配额；
- `item.weight`；
- 综合题槽位；
- required 例外；
- 最终状态迁移；
- 最终聚合公式。

### 2.2 暂不进入实现的地方：保留设计记录

如果本阶段没有必要新增接口，则至少在设计/实现差距记录中保存：

- Prompt 候选 ID 或稳定名称；
- 未来调用阶段；
- 预期输入和输出方向；
- 允许影响的范围；
- 不能影响的范围；
- 版本化和 trace 要求；
- 后续启用条件。

不得因为当前先用规则或 mock，就把未来可能需要 Prompt 的业务位置硬编码成不可替换逻辑。

## 3. 当前已识别的 Prompt 扩展点

下列位置来自前几轮讨论，当前只登记扩展点，不讨论具体 Prompt 内容：

### 3.1 JD 与模型构建

- JD 原子能力抽取；
- 能力词典消歧/归一；
- 能力等级冲突裁决；
- 普通题库生成；
- 综合题生成。

### 3.2 测评运行时

- 候选人回答状态分类；
- 证据覆盖判断；
- 追问意图/探针建议；
- 追问和澄清话术；
- 不会/想不到时的脚手架话术；
- 情绪/流程支持话术；
- 主问题过渡与收尾话术；
- 模型不确定说明；
- 综合题多能力证据拆分。

### 3.3 表单和资料

- 简历/自由文本事实抽取；
- 表单异常解释（如果固定模板不足以解决）。

### 3.4 终局评分和报告

- 逐题终局评分；
- 综合题多能力评分；
- 复杂语义证据一致性校验；
- 优势/短板/建议文案；
- 逐题回顾摘要；
- 报告一致性辅助检查。

### 3.5 测试闭环与运营

- 虚拟候选人回答生成；
- 评测结果解释；
- Trace/Bad Case 聚类摘要；
- 人工复核辅助摘要。

以下明确不交给未来 Prompt 或 LLM：

- hard/soft 的 7:3 配置和最终权重计算；
- 主问题及综合题槽位分配；
- required 刚性例外；
- `followup` 上限；
- 状态机最终迁移；
- 难度路径的代码护栏；
- 缺失项补算公式；
- gate 的最终代码判定；
- 报告数字、排序和权重聚合。

## 4. Prompt 扩展点不能破坏本轮确认的模型

未来设计 Prompt 时必须服从本轮已确认的边界：

```text
普通能力题：
    easy → medium → hard

综合题：
    普通 hard/soft 阶段完成或合法封存后进入
    独立槽位
    每次 session 最多两题

followup：
    当前题实例的内部子轮次
    不增加主问题数量

普通题实例：
    每个不同题面对应一个 assessment_question 实例

有效测量：
    综合题只有具备该 item 独立目标、证据和评分状态时，
    才能计为该 item 的一次有效测量

普通能力项：
    必须先获得至少一次普通题测量，
    综合题不能替代该最低普通测量
```

未来任何 Prompt 都不能：

- 把 `followup` 输出成新的主问题；
- 把综合题当成普通 hard 的第四级并沿用普通难度规则；
- 因综合题绑定多个 item 就自动完成多个 item 的有效测量；
- 让模型自由增加综合题数量；
- 让模型绕过普通题最低测量要求；
- 让模型改动 hard/soft 题量比例或最终 item 权重。

## 5. 当前处理规则

1. 本轮只记录确认结果，不修改前五轮临时讨论稿；
2. 不修改 SSOT；
3. 不修改业务代码；
4. Prompt 暂不展开，等待全部非 Prompt 设计收敛；
5. 后续开始 Prompt 讨论前，应先从第 3 节清单逐项确认；
6. 用户先拟定每个 Prompt 的业务初稿；
7. 之后再由技术侧补充 schema、边界、失败策略、测试、trace 和人工接管条件；
8. 在代码实现阶段，即使某 Prompt 尚未定稿，也必须保留可替换接口或稳定的设计记录；
9. 用户明确授权后，才将已收敛内容写入正式设计文档；
10. 正式文档更新后，再建立独立的修复/重构实施文档。

## 一、背景与现状（裁决依据）

### 1. 「退出后可继续」的承诺：会话层为真，入口层为假

- **消息级持久化已完备**：每次作答即时 INSERT `assessment_message`（user/assistant 双行，不等终局提交）；`GET /sessions/{id}` 返回完整消息时间线、当前题、剩余时长，`web-next/src/views/assessment/Chat.vue:356-405` 的 `load()` 即是现成恢复逻辑（刷新/断线重进同 URL 恢复良好）；`pause`/`resume` 端点已存在且 web-next 已接线（`api/index.js:53-54`），PAUSED 态有「继续测评」门卡（`Chat.vue:103-105`）。
- **退出按钮零后端调用**：`confirmExit()`（`Chat.vue:636-643`）纯前端 `router.push('/assessment/positions')`，不 pause、不 abort SSE。确认弹窗文案承诺「退出后本场测评不会作废，回来后可从中断处继续」。
- **计时陷阱**：SSOT §15「短暂断线不自动暂停」——退出后 active 区间照常累积，**离开的每一分钟都在烧 40 分钟预算**。文案承诺字面为真、实质半真：回来时可能已无时间可续。
- **6h 惰性作废只有一个触发点**：`maybe_abandon_session`（`services/timer.py:181-204`）仅在 `submit_answer` 内被调用（`assessment.py:444`）。用户中途退出后**不再回来 → 会话永挂 in_progress**，6h 规则永不触发（用户不调 answer 就没 sweep），证据成孤儿行。

### 2. 再入口断裂（断点不续的根因）

`PositionAssess.vue:77-89`「开始测评」→ `POST /assessment/sessions` → `create_session`（`assessment.py:100-140`）**无条件 INSERT 新行**——没有任何「同 (user, position) 已有 in_progress 会话则复用」的检查。退出后再点同一岗位 = 拿到全新 session_id，旧会话变孤儿（回到上文 6h 死锁）。「确认退出」弹窗承诺的个人，其唯一可见回归路径（重新选岗进入）被 create 逻辑否决。

### 3. 候选端导航现状

- `Positions.vue` **无任何持久导航**：无顶栏、无侧栏、无用户信息、无登出按钮；`PositionAssess.vue`/`Report.vue` 仅页内返回链接。
- `auth.logout()`（`stores/auth.js:31-36`）全库仅 `AdminShell.vue:100-103` 一处调用。JWT 无状态（12h 过期，无服务端会话），**候选端登出纯前端即可，需零后端改动**。
- 管理端侧栏为**纯 CSS hover drawer**（`admin.css:45-53`：`translateX(-112%)` 藏屏外，`.edge` 12px 热区 + `:hover`/`:focus-within` 显现，零 JS 状态）——镜像到候选端成本低。

### 4. feedback 表现状（R5 修正的触发点）

`feedback` 表（`db.py:332-346`）为**逐分异议管道**：`report_id TEXT NOT NULL REFERENCES report` + `item_id TEXT NOT NULL REFERENCES competency_item` 两列强绑报告条目；管理端 `list_feedback`（`admin/feedback.py`）对 report + competency_item 做 **INNER JOIN** 直接展示 std_name/category/score 列；提交侧走 `REVIEW_FEEDBACK_RECEIVED` 会话事件留痕（D-67）+ bad_case 沉淀管道。
**关键约束：SQLite 无法 `ALTER COLUMN` 放开 NOT NULL**——「复用 feedback 表装通用意见」实际需要 12 步表重建迁移，且 list 端点 JOIN、事件挂靠、管理端表格列都要为两种形态分叉。原推荐「一条 ALTER ADD COLUMN」成本描述不成立，见 R5 修正。

### 5. SSOT 覆盖缺口

以下均经全文检索确认**未覆盖**：候选端导航（侧栏/顶栏）、退出登录、候选人可见历史测评记录、候选人→管理员通用意见反馈、自助改密码、「退出后不作废」条款、同 (user, position) 会话复用规则。
已有且**沿用不动的相关条款**：§12.1 状态机（PENDING_START→ACTIVE→SCORING→COMPLETED；ACTIVE→ABANDONED 6h 惰性、不删证据）；§15 计时（pause 由候选人显式触发；短暂断线不自动暂停）；§16.1 表单重复提交「重复返回第一次结果」先例；§7 资源级所有权校验（`WHERE resource.user_id = current_user.id`）。

## 二、设计裁决

### R1 退出语义：确认退出 = 显式 pause（candidate_request）

- 退出确认后前端顺序：**abort 进行中的 SSE 流 → `POST /sessions/{id}/pause` → 跳转岗位页**。复用现有 pause 端点（reason='candidate_request'，`assessment.py:267-307`），后端零改动。
- **409 容忍集**：`SESSION_ALREADY_PAUSED`（已在暂停态）、`SESSION_NOT_ACTIVE`（PENDING_START 尚未开始计时 / SCORING 收尾中）——这两类静默直接跳转。其余错误（网络/4xx）toast「暂停失败，计时仍在进行」后**仍跳转**（后端消息已落库，回来恢复依旧可能，不困死用户）。
- 弹窗文案改为诚实版：**「退出将暂停本场计时，已作答内容已保存，回来后可从中断处继续。确认退出？」**
- 理由：§15 已规定 pause 可由候选人显式触发，此映射不动 §15 本体、不加新端点；且与 R2 强耦合——若退出不休计时，复用会话会把用户困在烧光的时钟里，复用方案反而变陷阱。
- 登记为 by-design：与「短暂断线不自动暂停」不矛盾——断线（关闭页面/网络闪断）不暂停，**显式确认退出**是候选人主动动作。

### R2 再入复用：create_session 改 get-or-create

- 规则：同 `(user_id, position_id)` 存在 `status='in_progress'` 会话 → **直接返回该 session_id（HTTP 200，`resumed: true`）**，不 INSERT 新行；不存在 → 现行路径照旧（201，`resumed: false`）。
- **前置 sweep**：复用查询前对本人 in_progress 行跑 R8 sweep（见下）——避免复用一个实际已超 6h 的死会话（尤其 PENDING_START 从未开始的：其 lazy abandon 只会发生在第一次 answer 时，若永不 answer 则永挂）。
- **复用路径跳过 readiness 检查**（MODEL_NOT_MEASURABLE / QUESTION_BANK_GENERATING / QUESTION_BANK_INCOMPLETE 三态 409）——与 §9.2 归档裁决「在途会话豁免」精神一致：会话锚定创建时的模型版本，动态派题不断粮。
- 归属排序：`ORDER BY created_at DESC LIMIT 1`（多处孤儿并存时取最新；存量孤儿由 R8 sweep 自然清为 abandoned，`status='in_progress'` 谓词天然不再命中）。
- **PENDING_START 会话同样复用**：用户创建后未点开始就退出，再进来看到的是入场确认门（现有 Chat.vue 逻辑，天然正确）。
- 为什么 get-or-create 而非 409：§16.1「重复提交返回第一次结果」先例；前端零改动能通向 Chat.vue 现成恢复链；409 方案需要前端另行 catch + 跳转，徒增一层。
- 响应体：`{session_id, resumed}`（新建另带 `estimated_duration_minutes` 保持现状，复用带不带均可——Chat.vue `load()` 会重锚时钟，前端不依赖）。

### R3 完成后重测：维持现行为

completed/abandoned 后再点同岗位 = 正常新建一场（readiness 照常检查）。历史中同岗位多行并存，不设解锁门、不设「一场定终」。本期不引入任何重测限制。

### R4 历史测评模块（数据面）

- **新端点 `GET /api/assessment/sessions`**（本人、服务端分页 + status 过滤）：
  - 参数：`page` / `page_size`（沿用 `MAX_PAGINATION_LIMIT=100` 上限惯例）、`status`（`in_progress`/`completed`/`abandoned`，可空=全部）。
  - 水平：`WHERE user_id = current_user.id`（§7 资源级所有权，401 边界由 router 级 `require_login` 保证）。
  - 行字段：`session_id`、`position_id`、`position_name`（join）、`model_version`、`status`、`phase`、`created_at`、`ended_at`/`abandoned_at`、`answered_count`（`assessment_question.answered_at` 非空计数）、`session_elapsed_seconds`（进行中行用于「剩余 X 分钟」展示）。
  - 排序 `created_at DESC`。phase 的前端价值：in_progress 行区分「未开始」（PENDING_START）/「已暂停」（PAUSED）/「作答中」（ACTIVE）。
  - **前置 sweep**：列出前对本人 in_progress 行跑 R8 sweep——「不回来的会话」在历史里如实显示为已作废。
- **岗位列表附带进行中摘要**：`GET /assessment/positions` 响应每行增 `active_session: {session_id, phase, remaining_minutes} | null`（本人 (position, in_progress 最新行) 相关子查询派生）；`PositionAssess.vue` 按钮随之变「继续测评 · 剩余约 X 分钟」。该端点签名需增 `user: dict = Depends(require_login)`（router 级已保证登录，仅取 user_id）。
- **completed 行两个入口**（复用现有页面，零新组件）：
  - 「查看报告」→ `/assessment/report/:session_id`：Report.vue 现有 `bootstrap()` 已处理无报告（404→触发生成→3s 轮询）**与** FAILED 重入队（`request_report` 护栏允许），历史行**不需要**报告状态字段，点击即自愈。
  - 「评估模型」→ `/assessment/positions/:position_id`（PositionAssess 即模型预览页，复用）。
- in_progress 行「继续」入口 → `/assessment/session/:session_id`（Chat.vue 恢复链现成）。

### R5 意见反馈：独立 suggestion 表（修正稿，2026-09-08 用户复核采纳）

**修正声明**：原推荐「复用 feedback 表 + report_id 放开可空」，核验后发现 `report_id`/`item_id` 为 NOT NULL 列且 SQLite 无法 ALTER 放开——落地即 12 步表重建迁移，且管理端 INNER JOIN 列（std_name/category/score）、D-67 事件挂靠（suggestion 行无所属会话）、bad_case 管道对建议形态全部不适配。**成本与语义均不成立，修正推荐如下**：

- **新表 `suggestion`**（CREATE IF NOT EXISTS，零迁移风险，不动 feedback 任何管道）：
  ```sql
  CREATE TABLE IF NOT EXISTS suggestion (
    suggestion_id TEXT PRIMARY KEY,
    user_id       TEXT NOT NULL REFERENCES user,
    text          TEXT NOT NULL,
    status        TEXT NOT NULL DEFAULT 'pending' CHECK(status IN ('pending','reviewed')),
    created_at    TEXT NOT NULL,
    review_note   TEXT,
    reviewer_id   TEXT,
    reviewed_at   TEXT
  );  -- 审计四列与 feedback 表 Phase 5 模式完全对齐
  ```
  - `status` 枚举只两值（pending/reviewed）——bad_case 沉淀是异议/评分质量管道，对系统建议无意义，不引入。
- **候选端**：`POST /api/assessment/suggestions`（text 必填、≤`MAX_SUGGESTION_LENGTH=2000` 字符上限，进 config，对齐 `MAX_JD_LENGTH` 先例）+ `GET /api/assessment/suggestions`（本人历史，含 status——让用户看到「已处理/待处理」）。
- **管理端**：`GET /api/admin/suggestions`（status 过滤）+ `POST /api/admin/suggestions/{id}/review`（reviewed + note，全盘镜像 `admin/feedback.py` 的 review 动作）；UI 在 TestCenter.vue 反馈区加「异议反馈 / 意见反馈」切换（意见反馈表格列：用户/时间/内容/状态/处理备注/action，无 std_name/category/score）。
- 不做：通知红点（admin shell 待办计数不接）、匿名提交。
- **备选（表重建复用 feedback 表，已否决 2026-09-08）**：将 `feedback` 重建为 `report_id`/`item_id` 可空 + `feedback_type` 列方案，迁移风险与管道语义分叉自担，不采用。

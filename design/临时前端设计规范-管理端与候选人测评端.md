# 1. 产品前端总原则

## 1.1 两类使用者、两种工作心智

系统前端分为两个明确的工作空间：

| 端 | 使用者 | 核心任务 | 主要心智 |
|---|---|---|---|
| 管理端 | 管理员、招聘/测评运营人员 | 维护岗位、JD、胜任力模型、题库、测评质量和反馈 | 工作台 / 审核台 / 可追溯控制台 |
| 候选人测评端 | 候选人 | 选择岗位、完成动态多轮测评、查看最终报告和反馈 | 安静、可信、像一场访谈 |

两端可以共享基础令牌和控件语义，但不共享完整视觉气质：管理端强调信息密度和操作效率，候选人端强调专注、阅读舒适和心理安全。

## 1.2 信息披露边界

### 管理端可展示

- 岗位、JD、胜任力模型、模型版本和审核状态；
- 题库配置、题目元数据、题目状态和测评配置；
- 测评会话状态、过程事件、消息、证据链和异常；
- 评分、评分理由、证据摘录、差距和报告生成状态；
- LLM trace、测试结果、反馈和 bad case；
- 所有信息必须带有清晰的来源、状态、版本或时间上下文。

### 候选人端禁止展示

候选人测评过程中不展示：

- 任何分数、等级、排名、通过/淘汰判断或录用倾向；
- `score_live`、终局评分、评分理由、差距计算或审核结论；
- LLM 的内部推理、系统提示词、function call、决策 `action` 或后端 trace；
- 管理员注记、审核状态、bad case 标记、模型评审信息；
- 未经产品明确允许的 JD 原文或内部岗位筛选规则。

候选人端只显示帮助完成测评所需的内容：当前题面、已发送的自己的回答、AI 的访谈话术、保存/生成状态、当前测评进度、作答提示和必要的表单。

## 1.3 共同交互原则

- 操作反馈必须明确但克制，优先使用状态文本、轻量提示和局部禁用；
- 加载、空态、错误、完成和不可操作状态必须有对应表现；
- 键盘操作应可用，焦点状态清晰；
- 破坏性或离开当前流程的操作需要确认；
- 真实接口数据优先于原型中的演示数据，不得用静态样例冒充真实状态；
- 数字、标签、时间和版本使用统一的 tabular/monospace 辅助排印，避免数字跳动造成误读；
- 桌面端优先，同时保证窄屏下核心任务仍可完成。

# 2. 视觉系统基础

## 2.1 共享设计令牌

以下令牌是语义基线，具体端可在命名空间内调整色值，不应直接修改会影响全站的全局 Element Plus 主题。

| 语义 | 建议浅色值 | 用途 |
|---|---|---|
| `--ink-1` | `#37352f` | 主标题、正文、主操作 |
| `--ink-2` | `#6f6e69` | 次级正文、说明 |
| `--ink-3` | `#9b9a97` | 辅助文字、时间、元数据 |
| `--line` | `#e9e9e7` | 细分隔线、边界 |
| `--panel` | `#ffffff` | 卡片、输入面、主内容块 |
| `--panel-2` | `#f7f6f3` | 次级背景、表头 |
| `--red` | `#e16259` | 重要提醒、异常、危险操作 |
| `--amber` | `#cb912f` | 进行中、注意、待处理 |
| `--green` | `#448361` | 成功、已确认、完成 |
| `--blue` | `#337ea9` | 链接、辅助信息、非品牌主色 |

原则：管理端可以使用状态色表达工作状态；候选人端的强调色要更克制，不能把测评变成红绿灯或评分仪表盘。

## 2.2 圆角、边框和阴影

- 管理端：圆角 5–8px，卡片边界清楚，阴影极轻；信息表格优先使用细边框；
- 候选人端：圆角 10–20px，输入框和用户回答气泡可更圆润；背景和内容块之间使用层次而非大量分割线；
- 候选人回答的“唯一细描边”原则只用于需要强调其为已发送内容的区域，不在每个元素上增加装饰性边框；
- 禁止大面积强阴影、玻璃拟态、霓虹渐变或高饱和蓝色用户气泡。

## 2.3 字体层级

- 中文界面默认使用系统无衬线字体，保证跨平台可读性；
- 候选人端题面可使用 Georgia、宋体或可用的中文衬线字体；
- 管理端标题、表格、筛选器和按钮使用无衬线；
- 辅助元数据可使用等宽字体或 tabular 数字，但不能让整页变成代码编辑器；
- 页面必须有明显层级：页面标题 > 区块标题 > 题面/主数据 > 正文 > 辅助信息；
- 辅助文字不能小到影响候选人阅读，状态和提示不能依赖颜色 alone 表达。

# 3. 管理端前端设计

## 3.1 管理端整体骨架

管理端采用稳定的三段式工作台骨架：

```text
┌─────────────────────────────────────────────────────────┐
│ 品牌 / 面包屑 / 当前状态                         用户 / 退出 │
├───────────────┬───────────────────────────┬─────────────┤
│ 左侧导航       │ 中央工作区                  │ 右侧上下文栏  │
│ 模块入口       │ 标题、工具栏、表格/表单/详情   │ 状态、提示、摘要 │
├───────────────┴───────────────────────────┴─────────────┤
│ 系统标识 / 当前角色 / 环境或版本信息                         │
└─────────────────────────────────────────────────────────┘
```

当前 Vue 共用骨架类为 `.grail`、`.grail-head`、`.grail-body`、`.rail-left`、`.rail-center`、`.rail-right`、`.grail-foot`；后续重构可以替换实现，但必须保留“导航—工作区—上下文”的信息关系。

### 顶栏

- 左侧：系统标记、产品名称、当前页面面包屑；
- 中部：当前业务状态或任务状态；
- 右侧：登录用户、角色信息、退出；
- 顶栏高度应稳定，不能因为状态文本变化导致主体跳动；
- 退出、删除、驳回等高影响操作使用明确按钮文字，不只使用图标。

### 左侧导航

建议分组：

1. 岗位与 JD：岗位库、岗位详情、JD 解析、模型版本；
2. 审核与维护：模型审核、词典、题库；
3. 测评与报告：测评会话、报告、反馈；
4. 质量闭环：测试中心、trace、bad case。

当前实现中导航由 `web/src/components/AdminNav.vue` 复用。导航项应支持 active、hover、disabled 和待处理数量徽标；徽标只表示待处理数量，不表示候选人评分。

### 右侧上下文栏

右栏不是重复主内容，而是提供“下一步需要什么”的上下文：

- 当前岗位和模型版本；
- 当前审核/生成/测试状态；
- 待处理事项；
- 关联 trace 或报告摘要；
- 操作风险提示。

## 3.2 管理端页面类型

### A. 岗位库 / 列表页

- 页面标题、开放岗位数量、搜索/筛选和“新增岗位”主操作；
- 表格行展示岗位名称、模型版本、状态、能力项数量、最近更新时间；
- 状态使用文字 + 语义色，不只用颜色圆点；
- 空态说明下一步动作；加载态不改变表格整体高度；
- 删除或停用需二次确认，避免误操作。

### B. JD 导入与解析页

- 输入区支持粘贴/上传，顶部说明输入要求；
- 解析过程用阶段时间线或步骤状态展示：接入、清洗、抽取、归一、聚合、待审核；
- 展示原始输入与处理结果时要有明确分栏和版本标识；
- 失败状态必须给出可操作的重试/查看详情入口；
- 不把 LLM 原始长输出直接铺满页面，原始 trace 应在独立详情中查看。

### C. 胜任力模型审核页

- 左侧或顶部展示模型版本和岗位上下文；
- 中心区域按能力类别分组展示能力项、层级、来源、权重和状态；
- 人工确认、驳回、编辑必须体现操作者和时间；
- diff 用新增/删除/修改的结构化标识呈现；
- 版本确认是高影响动作，按钮旁必须有影响说明和确认对话框；
- 不能以“AI 已确认”代替人工权威状态。

### D. 题库管理页

- 过滤器：岗位、能力项、类别、难度、题型、来源、状态；
- 列表至少显示题面摘要、绑定能力项、难度、题型、来源、版本/状态；
- 题面详情展示 rubric 和链条关系，但编辑区与只读预览区分开；
- 题库状态变更需要保留操作反馈；
- 题库数据多时优先分页、筛选和抽屉详情，不把所有信息塞在单行。

### E. 测评会话 / 报告管理页

- 以会话状态、岗位、候选人标识、创建时间、完成时间和异常状态为主要索引；
- 管理员可以打开完整对话、证据链和报告，但这些内容不应反向出现在候选人测评页；
- 对话回放区区分候选人原文、系统话术、内部事件和 trace；
- 内部事件使用折叠/抽屉，默认不干扰主阅读流。

### F. 测试中心与 trace 查看器

- 测试运行、trace 查看、反馈/bad case 使用明确 tab 或子导航；
- 运行中显示任务状态和轮询更新时间；
- trace 详情使用等宽字体、可复制、最大高度滚动；
- prompt、response、模型、耗时、成功状态、关联 ref 必须分组；
- bad case 操作需要显示当前状态和不可逆影响提示。

## 3.3 管理端交互状态

所有页面至少定义：

- `loading`：页面结构存在，局部显示加载；
- `empty`：说明没有数据和推荐动作；
- `error`：保留重试和错误上下文；
- `pending/running`：说明后台任务仍在进行；
- `success/confirmed`：说明完成和下一步；
- `disabled`：明确为什么不能操作。

管理端允许展示详细原因、评分和 trace，但必须放在管理端权限范围内，并与候选人端组件隔离。

# 4. 候选人测评端最终设计：04 融合方案

## 4.1 设计定位

04 融合方案不是“更漂亮的聊天室”，而是：

> **长得像 AI 对话，读起来像一场访谈。**

它融合三类已经验证的交互心智：

- ChatGPT：候选人回答右侧、胶囊输入框、AI 不使用厚重气泡；
- Claude：暖纸底、衬线题面、让长问题像值得认真阅读的访谈问题；
- DeepSeek：保留“可折叠结构”的节奏感，但候选人端不披露测评思路、评分或内部推理。

最终候选人页面不使用静态原型中的假数据；岗位名称、题目、进度、用户、消息和表单都来自真实会话接口。

## 4.2 候选人端整体骨架

```text
┌───────────────────────────────────────────────────────────┐
│ 胜任力测评 · 岗位/模型标签                 候选人 · 夜间 · 退出 │
├───────────────────────────────────────────────┬───────────┤
│                                               │           │
│               居中的访谈对话流                  │ 本场访谈    │
│  开场说明                                      │ 进度数字     │
│  AI 题面（无气泡、衬线）                         │ 进度条       │
│  候选人回答（纸灰右气泡、时间）                   │ 当前题       │
│  AI 追问（无气泡）                               │ 作答提示     │
│  中性状态行                                     │           │
│                                               │           │
│               胶囊输入框                        │           │
├───────────────────────────────────────────────┴───────────┤
│ 回答发送后保存 · 测评时长提示                                 │
└───────────────────────────────────────────────────────────┘
```

- 主体使用两栏网格：主对话流 + 右侧访谈上下文栏；
- 主对话流最大宽度约 720px，保证中文长题面行长舒适；
- 右栏约 264px，作为访谈目录和进度，不作为聊天历史导航；
- 窄屏（约 1060px 以下）隐藏右栏，主对话流占满宽度；
- 不引入候选人左侧聊天历史栏，减少任务切换。

## 4.3 色彩契约

### 浅色

| 令牌 | 值 | 用途 |
|---|---|---|
| `--bg` | `#faf9f5` | 页面暖纸底 |
| `--bg-rail` | `#f3f1ea` | 右侧访谈栏 |
| `--paper` | `#ffffff` | 输入区、当前项、折叠内容 |
| `--bubble-me` | `#e9e6dc` | 候选人回答气泡 |
| `--ink-1` | `#262624` | 主文字 |
| `--ink-2` | `#555552` | 次级文字 |
| `--ink-3` | `#807e78` | 元数据、时间和提示 |
| `--line` | `#e2dfd4` | 细边界 |
| `--accent` | `#b4552d` | AI 身份、进度、发送按钮 |
| `--accent-soft` | `rgba(180,85,45,.10)` | 焦点和轻强调 |

### 深色

深色模式仍保持暖纸方向，不切换为纯黑蓝色产品风格：

- `--bg: #26241f`；
- `--bg-rail: #201e19`；
- `--paper: #2e2c26`；
- `--bubble-me: #3a382f`；
- `--ink-1: #eeece4`；
- `--ink-2: #c2bfb4`；
- `--ink-3: #8d8b82`；
- `--line: #413e35`；
- `--accent: #d98e5f`。

深色模式只改变明度与对比度，不改变“安静访谈”的语义。

## 4.4 顶栏

- 左侧显示“胜任力测评”和岗位 badge；如接口提供模型版本则显示模型版本；
- 右侧显示候选人身份、主题切换和退出；
- 不显示内部岗位 ID、评分状态、管理员审核状态或 LLM 名称；
- “退出”触发确认：“退出后可继续当前测评，确定离开吗？”；
- 顶栏不显示倒计时，除非未来明确设计并提供可信的计时器契约。

## 4.5 开场区

开场区是访谈的建立信任区域：

- 小号全大写/字距标签：`ASSESSMENT · 岗位名 · 共 N 题`；
- 衬线主标题：`请结合你的真实经历作答`；
- 辅助说明：预计时长、无标准答案、会根据回答追问或推进、回答发送后保存；
- 只使用真实的岗位名和总题数；字段缺失时省略，不得硬编码演示岗位；
- 开场说明不泄露评分维度、模型策略或候选人筛选逻辑。

## 4.6 AI 消息

- AI 消息采用头像/身份标记 + 元信息 + 文本，不使用大面积灰色聊天气泡；
- 题面使用衬线字体，建议字号 17–18px、行高约 1.7；
- 普通访谈说明使用无衬线 15px 左右；
- 元信息可显示“当前问题”“追问”等流程性词语，但不显示 action 原值、评分或内部原因；
- 流式生成时可显示轻量光标；生成结束后移除；
- AI 文案必须来自后端消息，不能把原型中的样例问题复制到真实页面。

## 4.7 候选人消息

- 候选人回答右对齐；
- 使用低饱和纸灰气泡，不能使用高饱和蓝色；
- 气泡最大宽度约 85%，圆角 16px，右下角可保留小圆角差异；
- 上方显示候选人称谓和发送时间；时间来自发送时刻或服务端数据，不得伪造固定时间；
- 文本保留换行，长内容自动换行；
- 已发送回答与草稿视觉上必须区分；草稿如未来需要展示，应明确标记“正在作答”，不能误认为已保存。

## 4.8 状态行

状态行是候选人与系统同步的唯一过程反馈之一，必须使用中性文案：

- `回答已保存 · 正在理解你的回答`；
- `正在准备下一问`；
- `可以继续了 · 等待你的回答`；
- `正在加载测评内容`；
- `回复生成失败，请重试`。

禁止将以下信息放入候选人状态行：

- “评分中”“得分”“质量 4/5”；
- “因为你缺少某能力所以追问”；
- “模型选择了 followup/next”；
- 任何 prompt、trace 或内部推理内容。

状态行应有 `aria-live="polite"`；动画在 `prefers-reduced-motion: reduce` 时关闭。

## 4.9 右侧“本场访谈”栏

右栏的目的，是让候选人知道自己在整场访谈中的位置，而不是展示评分。

### 可展示

- 已答题数 / 总题数；
- 轻量进度条；
- 当前题面或当前题摘要；
- 作答提示；
- 如果接口未来提供题目目录，可展示真实的已完成/当前/待进行题目标题。

### 当前接口不足时的处理

当前会话接口可能只提供 `position_id`、`model_version`、`current_question`、`answered_count` 和 `total_count`。在没有题目目录、岗位名或历史题标题时：

- 只展示真实计数、当前题和通用提示；
- 不伪造“第 03 题”“后端开发”“还有 3 题”等原型样例；
- 不根据 answered_count 猜测未返回的题目标题；
- 若未来增加目录接口，目录项必须带状态和来源，前端再渐进接入。

## 4.10 输入区

- 输入区固定在主对话流底部附近，使用白色胶囊容器、细边框和轻阴影；
- textarea 自适应高度，设置合理最大高度，超长内容内部滚动；
- placeholder：`在此写下你的回答……`；禁用时说明“测评已结束或正在生成回复…”；
- Enter 发送；Shift+Enter 换行；中文输入法 composition 状态下 Enter 不得误发送；
- 发送按钮使用陶土橘，发送中显示生成状态并禁用；空文本禁用发送；
- 发送后立即清空输入、追加候选人消息，并显示“回答已保存/正在理解”中性状态；
- 错误时保留已输入文本或提供明确恢复方式，不能静默丢失回答；
- 输入区下方显示“回答发送后保存 · 本场测评约 N 分钟”，N 只有在接口或产品配置真实提供时才展示。

## 4.11 表单卡

当后端消息包含正式表单标记时，表单以消息关联卡片渲染：

- 表单卡属于当前访谈流的一部分，不显示内部工具名称；
- 字段标签和校验错误使用候选人可理解的语言；
- 提交按钮有明确 loading/成功/失败状态；
- 原始 payload、gate 判定、内部字段和评分不展示给候选人；
- 当前接口尚未提供表单时，不在页面硬编码空表单或假数据。

## 4.12 错误、完成与恢复

- 会话加载失败：页面保留基本框架，显示可重试错误；
- 流式回复失败：移除无内容的空助手消息；已有内容则保留并提示重试；
- 测评完成：由服务端状态驱动跳转报告页，不由前端猜测题量完成；
- 候选人退出后再次进入：以服务端消息/当前题为准恢复，不复制静态原型历史；
- 页面卸载时中止未完成请求，避免重复写入；
- 任何恢复失败不得泄露后端异常堆栈、SQL、prompt 或 trace。

## 5.2 实现隔离规则

- 候选人对话新样式使用 `.chat-hybrid` 根命名空间或独立 `chat-hybrid.css`；
- 不修改 `grail-notion.css` 的全局令牌和管理端选择器；
- 不将静态原型脚本直接复制到 Vue；
- 不把 demo 数据复制到生产组件；
- template 只渲染真实会话数据，脚本保留既有 `assessment.getSession`、`assessment.submitAnswer`、FormCard、完成跳转和请求中止逻辑；
- 后端返回的 decision 可以留在内存中供协议流程使用，但不能进入候选人 template；
- `decision.reason`、`decision.action`、`score_live` 不得以任何形式出现在候选人页面。

## 5.3 前端验收清单

### 结构

- [ ] 桌面端显示主访谈流和右侧本场访谈栏；
- [ ] 窄屏隐藏右栏，输入和对话仍可用；
- [ ] 顶栏、主流、输入区不会因为内容变化产生横向溢出；
- [ ] 加载/空态/错误/完成状态均有对应界面。

### 视觉

- [ ] 暖纸底，不是默认纯白后台；
- [ ] 题面衬线且层级明显；
- [ ] AI 无厚重气泡；
- [ ] 候选人回答为纸灰右气泡；
- [ ] 输入框为胶囊形；
- [ ] 进度栏不呈现评分；
- [ ] 深色模式仍保持暖纸语义。

### 业务边界

- [ ] 页面无分数、评分理由、action、内部推理、提示词和管理员注记；
- [ ] 不使用静态岗位名、固定题号、假历史题目或固定时间；
- [ ] 真实 current_question、messages、answered_count、total_count 正确渲染；
- [ ] FormCard 标记路径不泄露内部字段；
- [ ] 完成状态由后端驱动报告跳转。

### 交互与可访问性

- [ ] Enter 发送、Shift+Enter 换行；
- [ ] 中文输入法不会误发送；
- [ ] 发送中禁用输入和按钮；
- [ ] 状态行具有 polite live region；
- [ ] 主题切换按钮有 pressed 状态；
- [ ] 关键控件支持键盘焦点；
- [ ] reduced-motion 下不强制动画。

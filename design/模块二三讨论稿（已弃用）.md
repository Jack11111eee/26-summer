## 0.5 关键澄清：模块一的「权重」到底是哪两层（U3 已确认）

模块一聚合时，权重的生成是**两层相乘、一次合成**：

```
第一层（类目间）：硬技能 : 软技能 : 经验 : 门槛 = 5.5 : 2 : 2 : 0.5  → 55% / 20% / 20% / 5%
第二层（类内）  ：类目份额按各项 importance 系数分摊（required 1.0 / preferred 0.6 / plus 0.3）
                ↓ 合成结果
最终 item.weight（Σ=1，已存进 competency_item.weight）
```

**对齐结论（U3 已拍板确认）**：

1. 模块三算总分，**直接复用已合成的 `item.weight`**，不得再乘一次 5.5:2:2:0.5——再乘就是双重计费。
2. 「权重高题多、递进慢」落到**类目权重**：题量按 55/20/20/5 分配；难度递进速度按类目分档（见 N1）。

# Part I 主链路：测评（模块二）与画像（模块三）

## 1. 出题与题库

### D1. 题型与能力类目的映射 —— ✅ 已定：A 继承

| category | 题型 | 测评方式 |
|---|---|---|
| hard_skill | 技术问答 / 场景小设计（不上代码评测器） | 对话中考察 |
| soft_skill | 情景行为题（STAR） | 对话中考察 |
| experience | 经历追问（项目深挖） + 客观事实题 | 对话 + 表单 |
| qualification | **不进对话**，结构化表单填报 + 代码校验 | 见 D8/N5 |

补充：hard_skill 内含**客观题**（有精确答案），题干带 `answer_key`，评分走代码（正则/算法匹配），不经 LLM——见 D9。

### D2. 题量策略 —— ✅ 已定：B 按权重分配（联动 N1）

总题数 10~12 题，**按类目权重分配**：硬技能约 6~7 题、软技能约 2~3 题、经验约 2 题、门槛走表单不占题。required 项必考，preferred/plus 按类内权重竞争题位。

### D3. 出题与题库模式 —— ✅ 已定（题库驱动；异步模式按 M3 修订）

```
岗位模型 confirmed（人审动作）
   → 异步触发「题库生成」【异步任务+轮询，M3】：LLM 批量出题，prompt 携带
     [岗位名 + 模型项定义 + required_level 锚点 + 难度档位]
   → 产出该岗位的【岗位题库】（hard_skill / soft_skill，position_id 绑定）
   + 复用【通用题库】（experience / qualification，跨岗位，position_id=NULL）
对话推进中：
   → 用户选定岗位 → 题库范围 = 该岗位题库 ∪ 通用题库
   → 每轮 D4 决策 action=next 时，【代码】按选题规则取下一题：
     当前 item 完成度 + 难度递进（N1）+ 类目剩余题量
   → LLM 可对题面做岗位化/口语化轻包装，但 question_id 落库绑定，可溯
```

设计要点：
- **选题是代码做的**（确定性规则），LLM 只负责话术与追问——选题依据可审计；
- 题目与能力项**强绑定**（N7），无绑定的题不允许进入对话；
- 题库行的 `question_id` 支持后续替换为人工/外部真实题库（N8）；
- **异步模式分工（M3 拍板）**：题库生成 / 报告生成等十秒级以上任务 → 「异步任务 + task_id 轮询」（沿用 05 惯例）；对话轮次（秒级）→ SSE 流式（见 N4）。总文档须把两类异步模式分开定义。

### N1. 难度体系与递进策略 —— ✅ 已定

| 类目 | 档位 | 递进策略 |
|---|---|---|
| hard_skill | 简单 / 中等 / 困难 | **慢递进**：过程判分达标 → 同能力项升一档；不达标/含糊 → 保持或降一档；权重越高的项走完的档位越多 |
| soft_skill | 简单 / 困难（2 档） | 快递进：1 题基础情景达标后可直接进压力情景 |
| experience | 无难度 | 事实深挖（追问项目细节自动加深，不设显式档位） |
| qualification | 无难度 | 表单 + 代码校验，不进对话 |

- 递进状态记在每个 session 的 `(item, current_difficulty)` 上，选题规则（D3）消费它；
- 递进所用的"达标/不达标"来自**过程判分**（H1，见 R1），与 D5 追问上限不冲突——追问是"同一题内挖深"，递进是"换更难的题"，两个维度。

### N2. 岗位背景绑定 —— ✅ 已定

核心论点：同一能力在不同岗位的要求不同。落地：
- 岗位题库出题 prompt 强制携带岗位名 + 该岗位模型中此项的 `required_level / definition / evidence`，题目必须体现岗位场景；
- 评分 prompt 同理携带岗位背景——同一回答在不同岗位语境下得分可以不同；
- 通用题库只装与岗位无关的事实题（年限、学历、证书）。

### N3. 题库双轨设计（schema，M1 已补链条字段）

```sql
question_bank(
  question_id TEXT PRIMARY KEY,
  scope       TEXT NOT NULL CHECK(scope IN ('position','general')),
  position_id TEXT REFERENCES position,        -- scope=general 时为 NULL
  std_name TEXT NOT NULL, category TEXT NOT NULL,   -- 绑定能力项（N7）
  difficulty  TEXT CHECK(difficulty IN ('easy','medium','hard')),  -- N1；经验/门槛为 NULL
  qtype       TEXT NOT NULL CHECK(qtype IN ('objective','subjective')),
  stem TEXT NOT NULL,                          -- 题面
  answer_key TEXT,                             -- 客观题答案（代码判分用）
  rubric TEXT,                                 -- 主观题评分要点（给评分 prompt 用）
  chain_key   TEXT,                            -- 问题链条 key（M1 补，D5）
  chain_seq   INTEGER,                         -- 链条内顺序（M1 补，D5）
  source TEXT NOT NULL CHECK(source IN ('llm_seed','imported','human')),
  status TEXT NOT NULL DEFAULT 'active',       -- admin 可禁用
  created_at TEXT NOT NULL
)
```

### N4. 流式输出（SSE） —— ✅ 已定，H2 拍板修订

决策与话术**分两阶段**（OpenAI function call）：

1. **决策阶段（非流式，同步）**：调用 function call（工具名如 `interview_step`），一次拿到结构化 `{action, reason}` → 后端落库（action/reason 先于展示，可审计）；
2. **话术阶段（流式，SSE）**：基于已定 action 生成/转发 `reply` 正文，逐 token 推送前端。

DeepSeek 支持 tools。此方案保住「action 落库在展示之前」的时序，又保住 reply 的流式体验。题库批量生成不走 SSE（走 D3 的异步任务+轮询）。

### N5. 表单工具 / function call —— ✅ 已定

落地为**后端工具**（不引入 MCP 进程，MCP 留作后续扩展）：
- 工具 `render_form(form_type, fields[])` 注册在后端；面试官系统指令（P-interviewer）约定触发时机：开场简历表、gate 项缺信息时；
- LLM 输出标记 `📎[form:form_id]` → 前端渲染卡片表单 → 提交直传 `POST /api/assessment/forms/submit` → 存 `form_submission(form_id, session_id, user_id, payload_json, created_at)`；
- 提交后表单结论回注对话历史（精炼版），原始 payload 落库；与 D8 的 `user_profile` 打同一张表（已填过自动带入）；
- 典型表单：简历表（开场）、学历/年限/证书（门槛项）。

> N4/N5 共用 function call 通道：`interview_step`（决策）与 `render_form`（表单）是两个注册工具，模型按指令择一调用。

### N6. 上下文管理系统 —— ✅ 已定（U2 阈值触发）

```sql
context_raw(raw_id TEXT PRIMARY KEY, hash TEXT UNIQUE NOT NULL,
            full_text TEXT NOT NULL, created_at TEXT NOT NULL)
-- assessment_message 表增列：
--   content_refined TEXT        -- 入对话历史的（可能是精炼版）
--   raw_hash TEXT NULL          -- NULL=未精炼（原文即全部）；非空→指向 context_raw
```

- **精炼**：LLM（P-refine）提取与测评相关的事实，丢弃客套/重复/无关；精炼版进对话历史，原文按哈希归档，留痕可回溯；
- **防污染**：精炼同时承担注入防护（长文本里的指令性内容进历史前被过滤）；
- **评分不受损**：逐题终局判分时评分器按 `raw_hash` **回捞原文**输入——对话用精炼版、打分用原文版；
- **触发频率**：阈值触发（U2 拍板）——长度 > ~500 token（config `REFINE_MIN_TOKENS`，数值存疑、后续可调）才走 LLM 精炼，短输入原文直存。

### N7. 题目—模型可溯约束 —— ✅ 已定（硬规则）

**每道题必须四要素齐全才允许进入对话**：能力项绑定（std_name+category）✔、难度档（或无难度的类目标记）✔、题型（客观/主观）✔、岗位归属（岗位题库 or 通用）✔。出题入库时强校验。

### N8. 题库导入接口（留口） —— ✅ 已定

`POST /api/admin/question-bank/import`（JSONL，每行一题，字段同 N3 schema）。本期演示数据 = LLM 种子生成（`source=llm_seed`，U4）；后续真实题库走此接口，`source=imported`。

## 2. 多轮对话

### D4. 对话控制模式 —— ✅ 已定：C 结构化 action（H2 分两阶段）

## 5. 模块三：打分与报告

### R1. 两次评分的合成（H1 拍板，本节核心）

同一回答存在两次评分，**各加权 50% 合成**，保留追问智能性：

| 评分 | 时机 | 驱动者 | 用途 | 记录 |
|---|---|---|---|---|
| **过程判分** `score_live` | 对话中每轮 | function call `interview_step` 附带 `assessment`（quality 1~5 + 一句判定依据） | 驱动追问 / 递进 / 切题 | 落 message/score 表 |
| **终局判分** `score_final` | 测评结束后 | LLM 逐题评分（P-score，temperature≈0，含 evidence_quote + reason） | 终分基础 | 落 score 表 |

合成规则：**每道题应得终分 = round( score_live × 0.5 + score_final × 0.5 )**（1~5 区间）。
- 过程判分的出现让访谈体验"答得好被认可、答得深被追问"，是用户明确要求保留的体验环节；
- trace 同时留两次评分的依据 → 若两者严重背离（≥2 级），进 bad case 候选（喂 D16/D17）；
- 客观题（answer_key 代码判）只有 score_final，无过程判分——终分=代码判定分。

### D9. 打分架构 —— ✅ 按 H1 修订

| 阶段 | 执行者 | 干什么 |
|---|---|---|
| ① 逐题评分 | 客观题：**代码**（answer_key 匹配 → 分数档）；主观题：**R1 双次合成**（score_live 过程 + score_final 终局，各 50%） | question_score |
| ② 代码聚合 | item 得分=该项各题合成后均分；gap=required−actual；**总分=Σ(item.weight × actual/5)×100**（权重直接复用 item.weight，U3）；gate 项代码二值判定 | item_score + total |
| ③ 报告文字 | LLM：分数+差距排序+评分理由摘录 → 优势/短板/建议 | report |

### D10. 打分刻度 —— ✅ 已定：1~5 Dreyfus 同锚点

过程判分与终局判分**同一套 1~5 Dreyfus 锚点**（否则 50/50 合成无意义）；`gap=required−actual` 直接可解释。

### D11. 总分口径与门槛 —— ✅ 已定（U3 复核锁定）

以"后端开发工程师"模型为例（默认配比 55/20/20/5，Σ=100）：

| 项 | category | required | importance | weight | 计分 |
|---|---|---|---|---|---|
| Python | hard_skill | Lv4 | required | 19% | 19 × actual/5 |
| Go | hard_skill | Lv3 | preferred | 11% | 11 × actual/5 |
| …硬技能其余… | | | | 25% | |
| 沟通协作 | soft_skill | Lv3 | required | 12% | 12 × actual/5 |
| …软技能其余… | | | | 8% | |
| 后端开发经验(3年) | experience | —(gate) | required | 8% | 年限≥3→8 分；<3→**0 分** |
| …经验其余… | | | | 12% | |
| 本科 | qualification | —(gate) | required | 5% | 达标→5 分；不达标→0 分 |

- 门槛项无 actual_level，二值制；UI 门槛达标情况单列红绿标签。

### D12. 优势短板 —— ✅ 已定：代码排序 → LLM 措辞

优势=gap≥0 中权重最大前 3；短板=gap<0 中 |gap|×weight 最大前 3；LLM 只写自然语言段落。

### D13. 报告页 —— ✅ 已定：五段式（异步生成按 M3）

①总分+门槛标签 ②雷达图 required vs actual（ECharts）③逐项明细表（理由可展开）④优劣文字段 ⑤逐题回顾（含 score_live / score_final 双分对照+理由，可溯回原文）。报告生成走异步任务+轮询（十秒级，M3）。第 3、5 段是可审计的 UI 实体。

### D14. 建议生成 —— ✅ 已定：B 绑证据

输入=短板项+问答摘录+锚点描述；prompt 约束只能基于给到的短板项提建议。

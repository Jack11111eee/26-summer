# 第一部分 总览与全局约束

## 1. 系统定位与端到端链路

「AI 驱动的岗位胜任力测评与人才画像系统」：把非结构化 JD 转化为可测量的**岗位胜任力模型**（尺子），基于尺子对候选人进行**有界动态测评**，产出**立体人才画像**（读数），并通过**测试闭环**保证全链可审计、可回溯、有评测标准。

```
JD 文本 ──► 胜任力模型（模块一）──► 有界动态测评（模块二）──► 人才画像/评分（模块三）
                                                                      │
                                            测试闭环（模块四）◄────────┘
                                       可审计 / 反馈可回溯 / 测评标准（可迁移）
```

## 2. 系统范围（v2.0 收敛，不可扩张解读）

**系统做：**

- 候选人测评的人才画像报告；
- 各能力项评分与证据展示；
- 测评过程、状态与异常记录；
- 必要的人工复核支持。

**系统不做：**

- 最终录用判断；
- 最终录用排序；
- 自动通过/淘汰；
- 代替企业作出最终招聘决定。

任何界面、报告文案、Prompt 不得出现"录用结论""排名"等表述。qualification gate 只表达"资格事实核验结果"，报告警告只表达"测量完整性/资格信息提示"。

## 3. 四条强约束（全系统不可谈判）

| # | 约束 | 落点 |
|---|---|---|
| ① | **LLM 不碰数字** | 权重、分数算术、配额、题量、聚合、补算全部由代码计算 |
| ② | **人工是唯一权威** | confirmed 模型不被静默覆盖；评分可异议但绝不自动改分；报告发布必须人工明确点击 |
| ③ | **一切留痕** | 每道工序中间产物落库；每次 LLM 调用 trace 落库；答案原文不可变归档；状态事件 append-only |
| ④ | **代码是唯一状态机** | 难度升降、追问上限、题量、finish、工具授权等关键迁移全部由代码执行；LLM 只提供结构化观察与建议 |

## 4. 有界测评循环（模块二运行时总纲）

不采用自由 ReAct。每轮执行：

```
Observation → Policy/Plan → Act → Evaluation → Persist
```

- **Observation**：LLM 可参与回答状态分类、证据观察（结构化输出，代码裁决）；
- **Policy/Plan**：代码依据状态、配额、难度护栏、题量裁决下一步；
- **Act**：受限话术或允许的交互动作（表单、脚手架等）；
- **Evaluation**：代码判断证据是否充分、是否覆盖 measurement target；
- **Persist**：状态、证据、版本、事件同事务持久化。

LLM 永远不能决定：题量、追问上限、finish、难度最终迁移、权重、综合题数量、最终分数、报告发布。

**全站日/夜主题（2026-09-09 裁决）**：日/夜切换入口覆盖全部页面——登录/注册页右上角浮按钮、CandidateShell / AdminShell 侧栏按钮（side-foot 区，与「退出」并排）、Chat / Report 既有按钮保留；切换经共享 `useTheme()`，`html[data-theme]` 单点生效、localStorage 持久化、跨页签 storage 事件同步。无记录默认**日间**（不再跟随系统 `prefers-color-scheme`）；`?theme=` 调试口与既有 localStorage 记录行为不变。管理端补暗色 token 板（`html[data-theme="dark"] body.admin`，admin.css 原为 light 单主题；板块底色/边框/遮罩同步暗色派生）。**异议详情覆盖层跟随测评快照（§22.2）**：候选端 Chat / Report 按场次写 `localStorage['asmt-theme:<session_id>']`（进入时 + 切换时；管理端嵌入复用 Report 不回写，防管理员查看主题污染快照）；测试中心覆盖层打开时按该场 session 读快照决定报告正文明暗（`.fbd-scope[data-theme]` 局部生效，不从 `html[data-theme]` 继承），无快照（老会话/清库）回落日间；覆盖层管理壳（标题/关闭条）跟管理员当前主题。无接口/表变更。

**管理端侧栏（2026-09-08 更新）**：岗位库 / 模型聚合 / 题库状态 / 能力词典 / 用户管理 / 测试中心。「模型聚合」项替换原「岗位详情」死链项（`/admin/positions/detail` 会被 `positions/:id` 吞作岗位 ID，见 §8.6），挂 stalled 徽标（数据源 `/admin/todos.stalled_models`）。

## 7. 权限模型（P0 上线阻断项）

- 全部候选人资源接口（session/report/form/feedback）必须做**资源级所有权校验**：`WHERE resource.user_id = current_user.id`，不能只查 ID 存在；
- candidate 只能访问本人资源；admin 为最高权限（本期不分级），可读取候选人数据与完整 trace；
- 角色限制必须在后端执行，不能依赖前端 route guard；
- 测评入口统一要求：position `active` + 模型 `confirmed`；
- 越权测试矩阵（candidate↔candidate 读写、admin 边界）为上线阻断测试。

# 第二部分 模块一：JD 解析与胜任力模型构建（已实现，重构时保持）

## 8. 流水线（六工位，现状沿用）

```
①接入(粘贴/JSONL) → ②清洗(纯规则) → ③抽取(LLM#1) → ④归一消歧(词典+LLM#2)
→ ⑤聚合(代码频次+LLM#3裁决+代码算权重) → ⑥人审(审核页确认升版本)
```

- 状态机：`imported → parsing → parsed/failed → aggregating → draft/stalled → confirmed`；confirmed 后新增 JD/重解析走 diff 审阅流升 v{n+1}；
- 标题源优先：JSONL 行内 `job_title`（兼容 `position` 键名）入库即存 `jd_record.job_title`；pipeline 与 reparse 不覆写已存标题，仅库内标题为空时以 LLM#1 抽取兜底；
- 归岗：取标题（上述源标题优先）→ 规范化（去空格/大小写/常见后缀）→ position 精确匹配（`COLLATE NOCASE`，大小写不敏感；存量岗位名不迁移）→ 别名表 → 未命中建 `pending_review` 岗位（人工审激活；不聚合、不对测评端可见）；
- 岗位生命周期（2026-09-09 产品化）：状态机 `pending_review`（入口态）→ approve → `active`；`active ⇄ inactive` 由管理员经 `POST /admin/positions/{id}/status`（body `{"status": "active"|"inactive"}`）手动下架/上架——pending 岗禁用该端点（入口态须经审核流）、目标态=当前态 409、下架时同岗位存在 `RUNNING` 聚合任务 409（等完成再下架）；下架语义：不可开考（§10.4 首项 position active 检查挡）、对测评端不可见（岗位列表过滤 active）、不聚合（auto+manual 均限 active）、不吸收自动归岗的同名新 JD（归岗 name/alias 匹配限 active+pending_review，inactive 落穿 → 建新 `pending_review` 壳，管理员可上架旧岗+合并新壳收口）、不影响在途会话（豁免同 §9.2 精神）；已归属 JD 改归：`POST /jds/{jd_id}/reassign` 对任意 JD 开放（不再只限孤儿），管理端岗位详情页 JD 清单行内改归（target 仅 active、排除本岗位）；岗位合并：`POST /admin/positions/{source_id}/merge`（body `{"target_id"}`，单事务、先校验后变异）——target 须 active，source 须为数据壳（无 competency_model/question_bank_task/assessment_session 子表数据，占用检查同 reject 撤销；有数据岗不可合并——模型属岗位聚合产物不可搬运，走逐条改归+壳岗下架），JD 全量改归 target、source 名及其 `position_alias` 全量迁为 target 别名（UNIQUE 冲突 409 报冲突项）、source 删除，不自动重聚合（合并入证据由管理员到聚合页手动重聚合吸收——升版本须 diff 人审，不绕过），响应含 `moved_jds`/`moved_aliases` 计数；pending 岗处置三选一：approve / reject / merge（merge 即以该壳为 source）；`GET /admin/positions/options` 增 `status` 查询参数（默认不传=全量，保持岗位详情页名称查找语义；改归/合并目标下拉传 active）；inactive 岗开放模型审核页只读浏览（历史/版本/diff；写操作各端点已有 active 守卫）；
- 异步：导入/聚合后台任务 + 前端轮询（聚合任务进度反馈见 §8.4）；聚合自动触发钩子独立于解析异常处理，触发前做收尾判定（同岗位仍有 imported/parsing JD 则本轮跳过，§8.4）。跨岗位聚合总览与管理见 §8.6。

## 8.1 工序实现约束（沿用并需补测试）

| 工序 | 要点 |
|---|---|
| ② 清洗 | 纯规则切段；要求块空或 <30 字 → `low_confidence=1` 但继续流程 |
| ③ 抽取 | LLM#1 JSON 强 Schema；校验失败带错误重试 ×2 → failed |
| ④ 消歧 | 词典候选 top10（编辑距离/拼音）→ LLM#2 裁决；失败重试 ×2 → 降级代码去重；词典为空跳过 LLM#2 |
| ⑤ 聚合 | 代码频次（r/req/occ——req 为**条件口径**：「标 required 的 JD 数 ÷ 该能力**出现**的 JD 数」，绝对口径废弃）→ importance 三档映射：`required ⇔ 条件req ≥ REQ_THRESHOLD 且 r ≥ REQ_MIN_OCCURRENCE_RATIO 且 出现 JD 数 ≥ REQ_MIN_OCCURRENCE`（仅 hard_skill 类目可判 required，soft_skill 上限 preferred——2026-09-07 裁决）；`preferred ⇔ 未达 required 且 出现 JD 数 ≥ PREFERRED_MIN_OCCURRENCE`；否则 `plus` → level 冲突交 LLM#3（无自动众数后门）→ 权重纯代码；LLM#3 重试 ×2 仍败 → `stalled`。required 三重判据各职责：条件 req 修正单 JD 内 LLM#1 措辞泛滥（实测单 JD 80 %+ 项标 required，绝对口径下被稀释至 22 岗均值 3.5 项）；r≥0.25 保证岗位共识而非孤证；occ≥3 是统计证据下限。裸条件口径（仅换分母）已实测否决——图像算法岗 271/306 项 required 泛滥。`_collect_items` 滤除 evidence_exclusion active 行（**全排除的 JD-项不计 r/req 分子**，分母不变——§8.5）。preferred occ 基准（2026-09-08 裁决）：绝对 r 阈值与样本量耦合致 34 模型中 15 个 preferred=0（低样本岗 r 恒不可达 0.5，中段 [0.25,0.5) 全被判 required 无剩余人口）——改 occ≥3 统计语义与 required 双门槛同基，15→11 模型消除、SLAM 10/0/153→10/10/143（三档 17/10/74,Σw 9.9%）、算法岗 plus 池 Σw 97.8%→65.8%；R_THRESHOLD 退役（required 侧 r≥0.25 保留，职责不重叠）。**gate qualification facet 打标与断言等价合并（2026-09-08，§16.1 下游渲染消费）**：分组产物中的 gate qualification items 先做 facet 分类（确定性纯函数：关键词词表 + 内嵌数字解析，无 LLM），打标落 `competency_item.facet_key / facet_params_json`（两 nullable 列）；随后对**有序 facet 且派生参数一致**的组做断言等价合并（一组一行，std_name 取更窄措辞，evidences/jds/req_jds 并集；复合断言如「211硕士及以上学历」横跨学历+院校两轴、专业范围类、长尾未分类项**不参与**），合并先于 LLM#3 分档（被合并项不进其视野）。语义边界：只合「**事实含义完全一致**的同断言不同措辞」（2026-09-09 修订：原举例「本科及以上学历」与「全日制本科学历及以上」可合并——**作废**；学习形式/专业范围/院校条件等限定词是断言的组成部分，限定不一致不得合并，详见 §16.2），不处理「跨 JD 词面近重复」（词典第 3 层管辖，冻结裁决有效）；存量模型 facet_key 为 NULL → 渲染端整组降级勾选组（§16.1 fallback），已 confirmed 模型不回填不重打标，岗位重聚合刷版本自然带上 |
| ⑥ 人审 | PUT 编辑草稿 → confirm 升版本；编辑 stalled 模型后自动转 draft 并清 stall_reason。证据可标记排除/恢复（语句粒度软排除+留痕，§8.5；前端仅 draft/stalled 可操作） |

## 8.2 权重口径（v2.0 关键修正：普通题类目比例改为 7:3）

**第一层（类目间，模块一聚合时使用）：**

```
hard_skill : soft_skill : experience : qualification = 0.70 : 0.30 : 0 : 0（评分能力项）
experience/qualification 走表单事实采集，不占类目权重池，gate 二值判定
```

普通评分能力项满足：

```
Σ hard_skill item.weight = 0.70
Σ soft_skill item.weight = 0.30
```

若某大类无有效能力项，现有大类归一到 1.00；若大类有 item 但无合法题库 → 阻止开考（见 §10.4），不静默转移权重。

**第二层（类内）：** 各项按 importance 系数分摊（required 1.0 / preferred 0.6 / plus 0.3），合成结果存 `competency_item.weight`。模块三算总分**直接复用 item.weight，不再二次乘大类比例**。

**tier 语义（v2.0 确认）：** required/preferred/plus 影响原始重要性、题量配额和覆盖优先级；**不再额外乘最终分数**。

## 8.3 关键原则

- gate 项（qualification 全部 + experience 年限项）二值判定，不进 1–5 评分；
- 人工唯一权威：confirmed 模型不被静默覆盖；分数是历史事实；
- 每道工序中间产物（raw_items/std_items/cleaned_text）落 jd_record 可查；
- 能力词典独立管理；被引用条目停用/合并而非删除。

## 8.4 聚合任务可观测（2026-09-07 新增）

聚合为后台任务，过程中**无中间状态落库**（模型行在循环结束后一次性写入），前端原先只能轮询「模型 404→200」二态感知，存在卡点不可见、超时误报问题。本节定义聚合任务的**进度反馈与全程可追溯**契约。

**表 `aggregate_task`**（聚合任务记录，每次触发一行，不清理）：

| 字段 | 类型 | 说明 |
|---|---|---|
| task_id | TEXT PK | `agg_task_` 前缀 |
| position_id | TEXT NOT NULL | 归属岗位 |
| status | TEXT NOT NULL | `RUNNING / SUCCEEDED / FAILED`（不设 QUEUED：BackgroundTasks 触发即执行、无排队阶段） |
| trigger_source | TEXT NOT NULL | `manual / retry / auto:jd-parse`（三条触发路径可区分） |
| total / done | INTEGER | 能力项总数（循环前写入）/ 已处理数（循环内逐项 +1） |
| llm_total / llm_done | INTEGER | 需 LLM#3 裁决的冲突项数（纯代码预计算）/ 已裁决数 |
| current_item | TEXT | 正在处理的 `(std_name, category)`（liveness 信号） |
| model_id | TEXT | 聚合产物 competency_model id（模型行落库时回填——含 stalled 产出行，保溯源链完整） |
| error | TEXT | FAILED 时停滞/异常原因 |
| created_at / started_at / finished_at | TEXT | 触发/起/止时间 |

**进度端点**：`GET /admin/positions/{position_id}/aggregate/progress`——按岗位查**最新一条任务行**，无记录 404。响应含上表全部进度字段。

**行为规则**：

- 记录位置在 `run_aggregate` 内部（非 endpoint 层），pipeline 内联自动聚合路径一并覆盖；
- **入口并发守卫（2026-09-08 新增）**：`run_aggregate` 起跑前查同岗位是否已有 `RUNNING` 任务行，命中则本次跳过（不产生新任务行/新版本，静默返回）——单点挡住批量导入期间后到 JD 的尾部重复触发、跨请求并发与同岗位并发撞 `UNIQUE(position_id, version)`；主动路径（POST aggregate / retry-level）在端点层先判同岗位 RUNNING 行即 409「聚合进行中」（retry-level 守卫须在删除 stalled 模型之前，防「删了模型却没跑起来」）；
- **收尾触发（2026-09-08 新增）**：pipeline 尾部自动触发前先查同岗位是否仍有 `imported/parsing` 状态的 JD，有则本轮跳过——同批导入每岗位恰好聚合一次（批内最后一条解析完成者触发）；与入口守卫互为兜底，双触发不重跑；
- **双计数进度**：done/total 是条目进度（非冲突项毫秒级、可能跳变），llm_done/llm_total 与真实耗时同步——前端应同时展示两者；
- stalled 并入 `FAILED + error`（进度记录不复刻模型级 stalled 语义，失败行永久可查）。设计差异登记：§8 状态机的 `stalled` 指**模型产物**状态（模型已落库但标记不完整），本表 FAILED 指**任务运行**状态，两者并存不冲突；
- 进程重启 → 启动时将 RUNNING 残留行一次性置 FAILED（error=进程重启中断）；BackgroundTasks 后台任务同死于重启，语义一致。
- 前端停机判定依据 progress 端点心跳（行不变 N 轮报停滞），替换现行 3 分钟硬超时误报。

**溯源链**（迭代修复）：`aggregate_task(task_id) → competency_model(model_id) → llm_trace(ref_id=model_id, call_type=aggregate_level)`——从失败聚合可一路钻取到当时 LLM#3 逐次裁决原文。

**前端联动**：`ModelReview.vue` 触发后轮询对象改 progress 端点；进入页面时若已有 RUNNING 行即认领恢复（任务生命周期与页面组件解耦——离开页面不中断、不报错，后台照常跑完）。展示形态：进度条 + `done/total` + `llm_done/llm_total` + 当前项名。跨岗位总览与管理入口见 §8.6。

## 8.5 证据排除（可标记、可恢复、重聚合生效，2026-09-07 新增）

管理员在模型审核页（工序⑥）审查聚合证据时，可将单条证据摘录标记为**已排除**（软标记，不删数据，操作人/时间/原因留痕，可解除再恢复）。排除是**源头治理**动作：作用于「岗位 × JD × (std_name, category) × 证据原文」粒度，独立于模型版本持久存在，重聚合不丢失，对新版本生效。

**表 `evidence_exclusion`**（证据排除记录，岗位维度持久，不随聚合重建）：

| 字段 | 类型 | 说明 |
|---|---|---|
| position_id / jd_id | TEXT NOT NULL | 归属岗位 / 证据来源 JD |
| std_name / category | TEXT NOT NULL | 消歧后标准名 + 类目（判重口径与 competency_item 对齐） |
| text | TEXT NOT NULL | 被排除的证据摘录原文（语句粒度判重键成分） |
| reason | TEXT | 排除原因（管理员填写，可空） |
| excluded_by / excluded_at | TEXT NOT NULL | 排除操作人 / 时间 |
| status | TEXT NOT NULL | `active`（生效中）/ `lifted`（已解除）——解除不删行，审计可查 |
| lifted_by / lifted_at | TEXT | 解除操作人 / 时间（可空） |
| PRIMARY KEY | | `(position_id, jd_id, std_name, category, text)` |

**生效规则**（三条，`run_aggregate` 的 `_collect_items` 单点收口，下游 LLM#3/occurrence/权重全部继承）：

1. **证据级**：被排除摘录不进入新版本的模型快照 evidence、LLM#3 等级裁决 prompt、题库生成岗位背景摘录；
2. **频次级（2026-09-07 用户裁决：全排除才影响）**：某 JD 对某 (std_name, category) 的**当期证据全部**被排除（原有证据非空且无剩余）→ 该 JD 不计入该项 r/req 分子（分母 total_jds 口径不变）→ importance 可能降档 → 类内权重重算；部分排除不影响 r/req；原有证据为空的项无可排除对象、行为不变；
3. **消项级**：某能力项在全部 JD 上的证据均被排除 → 该项从聚合产物消失，权重并入其余项（Σ=100% 不变）。

**读取与交互**：`GET /admin/positions/{id}/model` 对 draft/stalled 模型**读取时实时合并**被排除条目（每条附 `excluded: true` + 留痕字段，前端灰显/划线/可恢复，合并非版本历史快照——历史以表内审计列为准）；confirmed 版本返回入库快照不合并；`PUT /admin/models/{id}` 收到含 excluded 标记的 evidence 由后端剥离落库（存储不变量：模型存储只含未排除证据）。

**端点**（岗位作用域，require_admin）：

- `POST /admin/positions/{id}/evidence-exclusions`——body `{jd_id, std_name, category, text, reason?}`；目标须为本岗位 parsed JD 的现存证据摘录（400 校验）；幂等 upsert，最后写入者覆盖 reason/操作人；
- `DELETE /admin/positions/{id}/evidence-exclusions`——body `{jd_id, std_name, category, text}`；置 `lifted` 不删行，幂等；
- `GET /admin/positions/{id}/evidence-exclusions`——全量列表（含已解除），每行附 `evidence_matched` 实时标志：JD 重解析或词典合并改名后失配的排除据此可见，不做自动迁移。

**行为边界**：后端不因当前模型 confirmed 拒绝标记/解除（排除是版本无关的岗位级治理）；前端仅在 draft/stalled 暴露标记/恢复按钮，confirmed 只读；标记不自动触发重聚合（管理员手动「重新聚合」生效）；全排除致能力项从模型消失后，恢复经由「排除记录」列表（GET 端点）完成闭环。

# 第三部分 模块二：有界动态测评

## 9. 题库

### 9.1 分类树（v2.0 确认）

普通对话题库只有两个大类，每类下三层 tier：

```
hard_skill ── required / preferred / plus
soft_skill ── required / preferred / plus
```

`experience` / `qualification` **不进入普通对话题库**：qualification 只走结构化表单；experience 通过表单/简历检测；两者不占普通主问题配额。能力项以 `measurement_mode` 区分（ordinary_question / form / resume），该字段来自 confirmed 模型版本，不可由前端或 LLM 修改。**2026-09-07 裁决收口（生成侧同步）**：题库生成不为 experience/qualification 产生任何 question_bank 行——两类信息唯一采集通道为 §16 表单链；历史 scope=general 通用题为存量遗留（选题白名单本就隔离），不迁移不删除。

### 9.2 question_bank 表（演进后）

```sql
question_bank(
  question_id TEXT PRIMARY KEY,
  position_id TEXT NOT NULL REFERENCES position,
  model_id TEXT NOT NULL, model_version INTEGER NOT NULL,   -- v2.0：题库必须绑定模型版本
  item_id TEXT NULL REFERENCES competency_item,             -- 普通题必填；综合题 NULL
  question_type TEXT NOT NULL CHECK(question_type IN ('ordinary','integrated')),
  measurement_stage TEXT NOT NULL CHECK(measurement_stage IN ('ordinary','integrated_final')),
  category TEXT NULL, tier TEXT NULL,                       -- 普通题必填
  difficulty TEXT NULL CHECK(difficulty IN ('easy','medium','hard')),  -- 综合题 NULL
  qtype TEXT NOT NULL CHECK(qtype IN ('objective','subjective')),
  stem TEXT NOT NULL, answer_key TEXT,
  rubric TEXT, rubric_version TEXT NOT NULL,
  measurement_target TEXT NOT NULL,                        -- v2.0：测量目标
  evidence_requirement TEXT,                                -- v2.0：证据要求
  observable_level_max INTEGER NOT NULL,                    -- v2.0：默认 easy=3/medium=4/hard=5
  observable_level_min INTEGER NOT NULL,                    -- v2.0：默认 easy=2/medium=3/hard=4
  equivalence_group_id TEXT NULL,                           -- v2.0：人工批准等值组
  integrated_bindings_json TEXT NULL,                       -- v2.0：综合题多 item 绑定快照
  chain_key TEXT, chain_seq INTEGER,
  source TEXT NOT NULL, status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL
)
```

- **题目属于岗位 + confirmed 模型版本**；模型升版必须生成/绑定新题库，否则阻止开考；
- 综合题 `question_type='integrated'`，`integrated_bindings_json` 为结构化绑定列表，每项含 `item_id / measurement_target / rubric_mapping / evidence_requirement`，在题库发布与实例化时校验并存不可变快照；本期不建关系表；
- 综合题不编码为 `difficulty=integrated`（正交两字段：question_type + ordinary_difficulty）；
- **有效题目定义**：`status='active'` 且 model/version 匹配、难度题型合法、未标记无效。
- **旧版题库归档**（2026-09-08 新增）：`status` 增枚举值 `'archived'`（与 `'active'`、eval 工具占位题 `'eval_seed'` 并存，代码校验、不加 DB CHECK）——语义为「被同岗位**更新 confirmed 模型**的题库取代、保留行以支撑追溯」。规则：①归档单元 = 模型（model_id），谓词为「同岗位存在更新 confirmed 模型」；②归档在新模型 confirm 事务内执行（helper 单点：`archive_superseded_banks(position_id)`）；③`model_id` 被 `in_progress` 会话引用时**豁免**（动态派题不断粮——豁免只认 in_progress，已终态会话的追溯不依赖 active，见下条）；④会话到终态（completed/abandoned，含 6h sweep）时补刀归档；⑤retry 端点对「岗位已存在更新 confirmed 模型」的 FAILED 任务返回 409（防归档模型重跑复活 active 行）。**archived 不改变任何按 `bank_question_id` 直连的 join 语义**：评分、报告、追问、答卷展示均不读 status，已归档版本的在途答卷、评分、报告、追溯不受影响（by-design 不变量，回归测试守恒）。归档**不延迟、不依赖**新库生成结果——新会话可用性由 model/version 绑定与 §10.4 readiness 决定，与归档正交。

### 9.3 等值备用题（v2.0 确认）

第一阶段只支持**人工批准的显式等值组**：同组强制一致 `item_id / difficulty / measurement_target / rubric_version / evidence_requirement / 权重语义`；配 `equivalence_status(pending/approved/rejected) + approved_by + approved_at`。不同难度的替代题标记为 `difficulty_alternative`，不入等值组；综合题与普通题之间不建立等值关系。

### 9.4 难度与 1–5 能力等级映射（v2.0 最终确认；2026-09-09 修订注入语义）

| 难度 | observable_level_max | rubric 最低锚点（level_min） | 锚点区间 |
|---|---:|---:|---|
| easy | 3 | 2 | [2, 3] |
| medium | 4 | 3 | [3, 4] |
| hard | 5 | 4 | [4, 5] |

评分语义：

- 作答达到最低锚点：在区间内评分；
- 有效作答但低于最低锚点：支撑**等级 1**（区别于拒答/缺证据）；
- 未形成有效观察（拒答、缺证据、题目无效、系统错误、模型不确定）：**不产生能力等级证据**；
- rubric 可将单题上限配低，不允许配超过所属难度默认上限；
- 等级 5 只能由 hard 题 5 级锚点、证据完整且稳定的测量支撑；
- `required_level` 只用于难度路径决策与报告达标比较（gap=required−actual 可解释），不改变 item.weight、不改变评分；
- **难度不构成最终分数第三层权重**。

**注入语义与消费契约（2026-09-09 新增）**：观测上下限与测量字段是评分链的**输入**而非事后装饰——

1. 题库生成必须为每题写入 `measurement_target / evidence_requirement / observable_level_max / observable_level_min / rubric_version`（§9.2 表结构早已声明为 NOT NULL，2026-09-09 起为生效契约而非占位）；空值/None 视为生成缺陷，落库前校验拒绝（§13 题库生成有效性检查）。存量缺字段的旧题进入待审核（§13 旧题处理），不静默投入新测评。
2. P-score 评分 prompt 必须携带该题的 measurement_target 与锚点区间（替代"通用 Dreyfus 五级 + 一句 rubric"的脱靶评分），评分结果受锚点约束：**obtain 等级不得超 observable_level_max**；基础题观察到的高阶能力（如理论正确性）不能自动判为高阶实践等级。
3. 评分器输出校验升级：非法类型、越界、缺证据引用、锚点编号不存在 → 明确失败/复核路径，**不得** `int()` 截断小数或静默接受越界值生成正常低分记录。
4. 生成侧口径统一：question_gen 提示词难度描述与 §9.4 表对齐（easy 对应 [2,3] 锚点区间，**不得**另行宣称 Lv1~Lv2——2026-09-09 前生成 prompt 中 easy=Lv1~Lv2 描述与 §9.4 冲突，作废）；
5. hard 档生成触发条件与 `weight>0.10` 解耦（§10.4 开考检查同条）——high difficulty 档的存在性由测量目标覆盖需要决定，不由权重稀释偶然决定。本条属于 §13 题库生成契约，与所有度为依据的机械规则脱钩。

### 9.5 题库生成任务可观测（2026-09-08 新增）

题库生成同为 BackgroundTasks 后台任务，现行实现任务行只有入口 RUNNING 与终态两个写入点：生成中无中间状态落库、失败仅存 `str(e)[:200]` 单值截断错误、无任务查询端点（前端可见性仅 `/admin/todos` 聚合计数与最新一条失败摘要）、进程重启后 RUNNING/QUEUED 残留行无收尸（且 retry 仅接受 FAILED、confirm 对已确认模型恒 409，残留即该岗位永久锁死「生成中」）。本节为 `question_bank_task`（§6 既有登记，D-12 代码先行，本节补字段级契约）定义进度反馈与全程可追溯，形态对齐模块一 §8.4 先例。

**表 `question_bank_task` 增列**（存量库启动自动补列，幂等迁移；既有列 task_id / position_id / model_id / model_version / status / created_at / started_at / finished_at / error_msg 不变）：

| 新列 | 类型 | 说明 |
|---|---|---|
| total / done | INTEGER | 计划生成的（item × 难度档）总数（循环前写入）/ 已完成数（含幂等跳过的档，循环内逐档 +1） |
| current_item | TEXT | 正在处理的 `(std_name, category, difficulty)`（liveness 信号） |

与 §8.4 `aggregate_task` 的**有意差异**（登记）：①保留 QUEUED 态——confirm 事务先插行再调度后台任务（三态在后台异常前可查；聚合触发即执行故不设）；②已有 model_version 列（题库单元 = 岗位 + confirmed 模型版本，§9.2）；③触发路径仅 confirm / retry 两路，不设 trigger_source。

**端点契约**（admin）：

| 端点 | 语义 |
|---|---|
| `GET /admin/question-bank-tasks` | 按（岗位 × 模型）最新任务行的列表：岗位名、model_version、status、done/total/current_item、error 摘要、题量（关联 question_bank 计数）+ `archived_count`（该模型 archived 行计数——归档后主计数归零仍可辨明「未丢题」）、`bank_status`（派生字段：使用中/已归档，按该 task 行 model 旧版题库行状态）、时间戳、task_id；服务端分页 + status 过滤 + `bank_status` 过滤 |
| `GET /admin/question-bank-tasks/{task_id}` | 单任务详情：全字段 + 同（岗位 × 模型）历史任务行（retry 保留旧行审计）+ llm_trace 时间窗调用列表；该模型已整体归档时 item × difficulty 覆盖统计按不过滤 status 口径重算（归档版本照常可看） |
| `GET /admin/question-bank-tasks/{task_id}/questions` | 该题库题目表：std_name / category / difficulty / qtype / stem 预览，分页；该模型已整体归档时 queryset 放开 status 过滤（active+archived 全量分页）、题目行增 status 列 |

**行为规则**：

- 进度更新在 `generate_question_bank` 内部：循环前写 total，循环内逐档 UPDATE done/current_item、与该档题目写入同事务 commit（逐次 commit 防轮询连接长持锁——§8.4 已论证同型问题）；
- 启动 sweep：进程重启时 `init_db` 将 RUNNING/QUEUED 残留行一次性置 FAILED（error=「进程重启中断」），与 §5「不要求进程重启后任务恢复」一致——不自动重启，人工 retry 补跑；
- error_msg 截断放宽 `str(e)[:200]` → `[:2000]`；存量短行不回填；
- llm_trace 关联不改表：按任务时间窗（created_at～finished_at）× `call_type='question_gen'` × 该模型 item 集（ref_id=item_id）过滤，prompt / response / error / attempt 逐次可溯；
- 列表以任务行驱动：「有题无任务行」的 D-12 前遗留组合不入列表（2026-09-08 核验当前库为 0，不迁移不补挂）。

**前端联动**（web-next）：左侧栏新增「题库状态」（`/admin/qbank`）。列表按岗位 × 模型版本一行，status 过滤（全部/生成中/已落库/失败）+ `bank_status` 筛选（全部/使用中/已归档，已归档行弱化视觉）；列表行展示 `question_count` 旁并列 `archived_count`；生成中行显示进度条 + done/total + 当前项名（3s 间隔轮询列表端点、进页认领 RUNNING 行，任务生命周期与页面解耦——§8.4 同型）；点行开抽屉详情——已落库：item × 难度覆盖统计 + 题目表（题干预览，分页；归档版本后端自动放开 active+archived 全量、题目行带 status 列，无手动 toggle 交互）；失败：error 全文 + 历史任务行 + llm_trace 逐次调用（默认折叠、按次展开）+ retry 按钮接线既有端点（列表/详情均含 task_id，为 retry 提供取值来源；岗位已有更新 confirmed 模型时 retry 得 409，前端提示冲突原因）。

## 10. 题量与配额

### 10.1 三类主问题分别计数

```
ordinary_plan_count       岗位级策略配置的普通题计划数 N
ordinary_exception_count  required 刚性例外新增普通题数 E
integrated_plan_count     综合题独立槽位数 I（0 ≤ 实际 ≤ 2）
followup_count            追问轮次，单独统计，不计主问题
main_question_count = N + E + 实际综合题数
```

- `N` 由管理员在岗位测评策略中配置，系统不设全局上下限，默认值实施期结合 40 分钟体验测定；
- 综合题不占 N；required 例外不改变 item.weight。

### 10.2 大类 7:3 整数分配（最大余数法）

```
raw_hard = 0.70 × N；raw_soft = 0.30 × N
先取整数部分，余下名额按小数部分大小分配；小数部分相等时归 hard_skill
```

| N | hard | soft |
|---:|---:|---:|
| 9 | 6 | 3 |
| 10 | 7 | 3 |
| 11 | 8 | 3 |
| 15 | 11 | 4 |

### 10.3 类内 tier 配额（v2.0 用户公式）

以各大类实际题量为总体，按 `required 0.8 : preferred 0.6 : plus 0.3`（和 1.7）分配：

```
required_target  = ceil(category_quota × 0.8 / 1.7)
preferred_target = ceil(category_quota × 0.6 / 1.7)
plus_target      = category_quota − required_target − preferred_target
```

实际分配遵守 `required > preferred > plus` 优先级：题量不足时先保 required 再保 preferred，plus 用剩余名额；向上取整不得使目标超过该大类总量（如 soft 仅 2 题：required=1、preferred=1、plus=0）。

### 10.4 开考前可测量性检查（不通过 → 阻止创建 session 并报告管理员）

```
confirmed model → question bank readiness → quota feasibility → form schema readiness → session 可创建
```

检查项：position active；模型 confirmed；题库绑定当前 model/version 且已生成完成；每个有效 required item 至少一条合法普通题（**普通类目 hard/soft——experience/qualification 不生成题、不参与题库覆盖检查，2026-09-07 裁决，见 §9.1**）；hard/soft 配额可满足（**有 item 但题库不足 → 不允许转移名额，阻止开考**）；综合题槽位有合法题目（若策略 I>0。**本期 I=0 且综合题不排期 → 恒过，by-design，2026-09-06**）；qualification 表单 schema 可用（**现为模型 items 数据驱动生成（form_instance.schema_snapshot），其存在性已被"items 非空"检查隐式覆盖 → 恒过，by-design，2026-09-06**）。

**检查项扩充（2026-09-09 新增，配套 §17.A 测评范围）**：

9. **测量路径合法性**：正式范围内每个能力项都有合法测量路径（有可达难度档题目且难度路径状态机可达——如 required_level=5 的 item 必须有 hard 档题目存在，否则 §9.4「等级 5 只能由 hard 支撑」使该 item 在本场结构性不可测）；
10. **锚点覆盖**：题库中该版本宣称测量的等级范围（easy[2,3]/medium[3,4]/hard[4,5]）都有题目锚点覆盖——某能力项的 required_level 所在档位无题目 → 阻止开考并指出哪一项不可测；
11. **必备项证据可得性**：必备（required）与其他正式计分项在题量和时间预算内可获得最低证据；题目存在但按配额被抽不到 → 与题目不存在同判定（配额与范围配套，§10.1 N 的可行性）；
12. **例外预算**：§10.5 required 刚性例外与追问预算在时间预算内可达（I>0 综合题时综合题同查）。

不通过时返回明确状态：`QUESTION_BANK_GENERATING / QUESTION_BANK_INCOMPLETE / MODEL_NOT_MEASURABLE`，并产生管理员待办，而非创建 0 题 session。检查 9–12 的失败状态复用 `MODEL_NOT_MEASURABLE`，detail 指明首个不可测能力项与原因（不发明新状态）。

### 10.5 required 刚性例外（v2.0 确认）

普通计划结束后检查 required 覆盖；未获有效普通测量的 required item：

- 同一 item **最多一次例外**，新增一条普通主问题（计入 E）；
- 例外题**只允许 medium**；无可用 medium 题时选 **hard**（不走 easy 起始）；
- 不使用综合题；
- 例外仍受题库版本、session 状态、计时约束；
- 耗尽后 item 状态 `REQUIRED_UNMEASURED` → 带警告临时报告 + 人工复核。

### 10.6 动态选题执行顺序（代码执行，可审计）

```
第一层 合法性过滤：版本/阶段/未用实例/当前题已封存/路径合法
第二层 硬约束：未覆盖 required 优先（无候选 → 触发例外或不完整）
第三层 配额：category/tier 剩余配额
第四层 排序：chain 后继（条件满足才继续，可让位 required）→ item.weight → 题目质量 → 稳定随机种子
```

- 每轮 `action=next` 时由代码选题；LLM 只做岗位化/口语化轻包装，question_id 落库绑定；
- chain 不能挤掉未覆盖 required、不能改变题量槽位、不能绕过难度护栏。

## 11. 会话、对话与追问

### 11.1 实例模型（v2.0 确认）

- 每个实际呈现的**不同题面**创建新 `assessment_question` 实例（动态实例化方案 A）；
- `followup` 是当前实例内部子轮次：`question_id` 不变、不建新实例、不增主问题数、不占综合题槽位、**每题最多 2 次**（config 硬约束）；
- 同一 item 的 easy/medium/hard 不同题面 = 三个实例，同属该 item 的 `difficulty_path`；
- 一个实例结束才进下一个主问题实例。

### 11.2 难度路径状态机（v2.0 确认）

```
easy → medium：一次充分证据
medium → hard：充分且稳定的证据；hard 仅对 target_level > 4 的 item 开放
降级触发（仅统计有效候选人证据失败）：
  - 跳过；同 item 同难度连续两道有效题未达最低锚点；
  - followup 后仍模糊/错误/不足；当前非最低难度才可降级
降级后恢复：连续两次充分证据或一次稳定证据（滞回原则）
一次实例内不升降级；路径变更在实例封存后由下一实例承载
不设 item 级路径振荡次数上限
```

**不计入普通失败**（不得触发降级）：技术故障、无障碍问题、题目无效、模型不确定、合理流程质疑、明确拒答、攻击性事件、单纯紧张/停顿/表达风格。

**跳级**：默认禁止运行时静默跳级；仅当模型/rubric 明确配置允许且报告记录实际路径时才可；否则 `PATH_UNAVAILABLE` → 人工/不完整。

### 11.3 证据判定（v2.0 确认：结构化观察 + 代码裁决）

**`evidence_sufficient`** 由 LLM/规则提供结构化观察维度（relevance / required_points_covered / specificity / attribution / source_span_available / contradiction_detected / uncertainty），代码按固定条件计算最终布尔值。明确排除：拒答、纯态度、复述题目、与 target 无关、无具体可归因事实、无可追溯 span、题目无效、模型不确定。

**`stable_evidence`**：两个不同普通题实例的独立有效观察，或一次 hard 强证据（仍须满足 rubric 与证据完整性）；依据观察独立性 + target 覆盖一致性 + 锚点一致性 + 无矛盾 + rubric/version 一致。同一回答的两个相似句子不算两次观察。**证据冲突 → 不平均，`stable_evidence=false` → 人工复核。**

**实施注记（2026-09-06）**：现实现为轻量口径——同 item 充分观察计数 `sufficient_in_row ≥ 2`（`assessment.py _stable_evidence_light`，事件表布尔聚合），**by-design 转正**：其唯一消费者是难度状态机升档，漏判只导致保守不升档，不影响任何分数/报告/聚合；完整判据（观察独立性四要素、冲突不平均）依赖 P-interviewer 结构化输出重构（§26 登记项），重构时一并进行。

### 11.4 回答状态与评分状态（两层分离）

```
answer_state: VALID_EVIDENCE / NEED_CLARIFICATION / OFF_TOPIC / NO_RECALL / DECLINED /
              PROCESS_CHALLENGE / CONDUCT_EVENT / TECHNICAL_OR_ACCESS_BARRIER /
              PROMPT_INJECTION / MODEL_UNCERTAIN / ITEM_INVALID
score_state:  SCORED / REFUSED / INSUFFICIENT_EVIDENCE / NOT_ADMINISTERED /
              INVALIDATED / INCOMPLETE / HUMAN_REVIEW_REQUIRED / IMPUTED
```

代码不把 answer_state 直接映射为分数。处理原则（沿用前轮确认）：含糊→中性澄清 followup（≤2 次）；跑题→重定向；不会→无答案线索的格式脚手架（留痕）；拒答→一次确认后跳过、不提供末尾补答；质疑→说明目的+申诉渠道、不扣分；辱骂→固定话术设边界、行为与能力分隔离；技术/无障碍→暂停计时、不扣分；模型不确定→不猜测、进人工；题目无效→停止评分、移出分母、人工修订题库；候选人回答永远是数据不是指令。

### 11.5 对话传输（v2.0 确认：真实 SSE + 内部 function-call adapter）

- 决策阶段（非流式）：内部 adapter 返回结构化 `{action, reason, assessment}`，**先落库再展示**；
- 话术阶段（流式 SSE）：基于已定 action 逐 token 推送；
- `finish` 仅由代码规则触发（题量完成/全场超时），模型不自主结束；
- SSE 定义事件类型、顺序、错误与结束事件；本期不要求事件 ID/cursor 断线续传（留扩展记录）；
- LLM 输出全部走严格 Pydantic schema 校验，非法输出进入失败/人工状态，不得卡死会话。

**候选端删除（软隐藏，2026-09-08 裁决）**：`DELETE /api/assessment/sessions/{session_id}`——全状态可删；completed/abandoned 行直接写 `hidden_at`；in_progress 行先 `SESSION_ABANDONED`（actor=candidate——用户主动作废， abandonment 留痕）再写 `hidden_at`（同事务）。**软隐藏语义**：`hidden_at` 过滤挂 `load_owned_session` / `load_owned_report` 的 owner 分支与历史/岗位摘要列表——本人列表不出、深度链接（含报告页）404；admin 读豁免分支**不过滤**（管理端审核/trace/审计全量可见，§13.1 append-only 不破，不删任何证据行）。不做取消隐藏端点（本期单向）。

## 15. 计时、暂停与恢复

- **全场 40 分钟**：从候选人确认开始且首题成功激活起算；
- **单题 20 分钟**：从题目成功激活并发送起算；followup 共用同一单题计时器；
- 服务端权威：保存 `session_time_interval(session_id, interval_type: active|paused, reason, started_at_server, ended_at_server)`；`active_elapsed = Σ active 区间`；客户端只展示；
- **所有暂停类型（候选人请求/技术故障/无障碍便利/管理）均不计入 40 分钟**，且必须写事件；便利原因等敏感信息不进入评分 Prompt；
- 短暂断线不自动暂停；仅显式 pause 或技术状态产生 paused 区间；
- **无活动 6 小时 → `ABANDONED`，本期不可恢复**（后续可开发可恢复，仅留记录，不细化不留接口）；检测 = 下次请求惰性判断 + 单进程周期扫描；ABANDONED 不删证据；
- 单题超时：封存当前题（seal_reason=timeout），继续下一题；全场超时：停止新增主问题，进入收尾评分；
- 时间不参与题目筛选优先级，不因剩余时间不足拒绝合法 chain/升降级。

### 16.1 form_instance（v2.0 新增生命周期实体）

### 16.2 资格条件的判定规则（2026-09-09 新增）

资格核验的三层分离——**事实、规则、条件性质**。此前「表单 absent→不达标（保守）」与「所有 gate 条件并集视为全须满足」的隐式语义作废。

**层 1 事实（candidate facts）**：候选人事实独立采集（最高学历、学习形式、专业、通用工作年限、专项经历、年龄…），归候选人本人；事实与断言的冲突、缺失不自动判定为「不达标」，进入「待确认」。

**层 2 规则（condition rules）**：条件规则独立于事实定义（「学历不低于本科」「计算机或数学相关专业」），由代码评估；同一条件内的「或」按 OR、彼此独立的必需条件按 AND；无法明确解析的复合条件进入人工确认，不由字符串猜测判定。

**层 3 性质（condition nature）**：每条资格条件必须携带性质标签——`required`（必需）/ `preferred`（优先考虑）/ `info`（背景信息）。**只有正式纳入本测评的必需条件影响资格结论**；优先项未满足不得显示为未过门槛。不同 JD 汇总的条件先经**岗位模型审核**（§8.1 人审），不能直接合成「所有候选人都必须满足的交集」。

**资格结论四状态**（取代原二值 passed）：

```
SATISFIED     已满足（必需条件）
UNSATISFIED   明确未满足（必需条件）
PENDING_CONFIRMATION  待确认（必要事实未提供 / 事实冲突 / 条件解释不清）
NOT_APPLICABLE 不适用（优先/背景/非本测评范围条件）
```

**专属性限与规则细节**：

- **通用年限不证明专项年限**：`years_of_experience`（通用工作年限）只核对通用经验类条件；专项经验条件（如「3 年 NLP 经验」）必须有对应专项事实，重古断言不累加、缺专项事实不默认满足（2026-09-09 前实现以通用年限判全部专项经验通过——作废）；
- **数值条件必须保存比较运算符**：`number_range` facet 的 `params` 增 `operator`（`lt/lte/gt/gte/range`）与边界值；方向以原断言文本为准（「30 岁以下」=`lt 30`），无法解析方向的条件不自动判定、降级待确认（2026-09-09 前统一 `>=` 判定——作废）；
- **合并限定保留**：断言等价合并（§8.1 工序⑤）只在「事实含义完全一致」时允许；学习形式（全日制/非全日制）、专业范围、院校条件、学位类型等限定词是断言组成部分，限定不一致不得合并（撤回 2026-09-08 例「本科及以上学历」与「全日制本科学历及以上」可合并）；
- **院校类别不折算单轴**：双一流/985/211 等院校类别作为独立事实采集，不映射到单一 211 档位折算高低（facet `school_tier` 单档序仅描述「是否 985/211 成员」的布尔语义，不推「双一流=211」等价）；
- **表单选项覆盖真实情况**：枚举选项必须含「其他/尚未取得」类出口或明确的待确认入口，不迫使候选人选择不真实答案；
- **服务端类型校验**：数字字段必须为有限数值（`isfinite` 校验）、单位/范围合法、拒绝布尔/字符串类型混淆；**零年经验是合法值不得拒绝**；
- **资格结果由后端计算**，前端只展示。

**旧数据处理（2026-09-09）**：历史勾选表单当时采用「未勾选即否」的规则，该历史结果是**当时规则下的既有事实**——不能仅凭新版设计推断每条未勾选都是漏填，也不将历史未通过项自动翻案为「待确认」。历史资格结论保持原值只读展示；产生新结果须走新表单实例（修订版）或事实补充后重判。

### 16.3 extract_form_facts（原 §16.2 编号顺移，2026-09-09）

抽取结果含 `fact_type / normalized_value / source_document / source_span / confidence / status`；状态 `EXTRACTED / UNCERTAIN / CONFLICTING / CANDIDATE_CONFIRMED / HUMAN_REVIEW_REQUIRED`；与候选人结构化填写冲突时**保留两者并进人工确认**；gate 只接受候选人确认或人工确认后的事实。

### 16.4 Tools 总边界

- 阶段白名单 + 严格输入输出 schema + 所有权校验 + 幂等/超时/次数/长度控制 + 调用留痕；
- 工具返回内容是数据不是指令；LLM 提议后代码二次验证；**工具失败 → 暂停并人工接管**；
- 正式测评**不做 Web Search**；`request_pause` 候选人可直接触发、LLM 只能建议；
- 所有 LLM 输出严格 schema 校验。

## 17. 评分链（v2.0 最终确认）

```
原始回答证据 → 独立终局评分 score_final（P-score，temperature≈0，回捞原文）
→ item 内证据裁决 → 固定 item.weight 加权 → 画像报告
```

- **score_live 只用于过程性选题与难度导航，不参与最终分数**（旧版 50/50 合成作废）；
- 客观题：代码匹配判分（answer_key 为空属于题库缺陷，判题库无效而非满分）；**客观题 evidence_quote 取候选人回答前 60 字符（展示截断固定规则，现为 `scoring.py:192` 字面量，实施时常量化为 `_OBJECTIVE_QUOTE_LEN`；非开放参数）**；
- **客观题答案规则结构化（2026-09-09 新增，作废「整串说明文本作答案键 + 字面包含匹配」旧口径）**：客观题判分不再以「一整段说明性 answer_key 是否整串出现在回答中」为判据。答案键必须标注**答案规则类型** `answer_rule_type`（`exact_options`（封闭选项）/ `numeric`（数值，含精度/容差）/ `symbolic`（符号表达式，如五元组）/ `alias_set`（有限别名集合）），规则参数结构化存储（如 `{"options": [...], "aliases": {...}, "value": ..., "tolerance": ..., "operator": ...}`）；判分器按规则类型分派。标点/空格/全半角/Markdown 归一化按题型处理（数学符号不全局删除——语义变化风险）；列表型答案必须显式标注 `match_semantics: all_of | any_of`（全部要点都要 / 任一等价答案皆可），不再用 `|` 连接列表后靠正则分支猜（**作废**现行 `_as_text(answer_key, "|")` + `_looks_like_regex` 以 `|` 猜正则的做法）；否定句、错配关系、矛盾陈述不得仅凭关键词存在判正确；无法可靠判分的自由表述进复核路径不强行给最低等级。命中=5 分/未命中=1 分口径不变（层级证据归 §9.4 锚点，正确性与能力等级分离见下条）；
- **正确性与能力等级分离（2026-09-09 新增）**：答题正确性（answer correct）与能力等级（competency level）是两回事。客观题命中得 5 分仅表示「答案正确性：正确 + 该题锚点区间内最高置信」；基础概念题答对不自动证明独立实践/专家水平，基础题未展示高阶能力不证明缺乏高阶能力。item 最终等级由多题证据按锚点区间裁决（§19），单题不超过其 observable_level_max（§9.4）；
- 题库生成结构规则（非运行期参数）：hard_skill 项 `weight>0.10` 生成 easy/medium/hard 三档，否则两档；soft_skill 两档（`question_bank.py _question_plan`）；**experience/qualification 不生成题（2026-09-07 裁决，§9.1——旧「无难度各 1 题」结构作废，两类走 §16 表单链）**。
  **档位与测量目标挂钩（2026-09-09 修订，强约束）**：hard 档生成与否由该 item 的 required_level 是否 >4（即 §11.2 可达 hard 的 item）**或**测量目标覆盖需要决定，不由 `weight>0.10` 单独决定——否则高等级题的存在性随条目数量与权重稀释漂移，与测量目标脱钩（2026-09-09 前的「weight>0.10 才有三档」作废，存量模型最大权重 0.0089 时全场无 hard 题、Lv5 结构性不可得，为已确认缺陷）。生成规划必须保证 §10.4 检查项 9-12 可满足；
- score_live 与 score_final 差值仅用于偏差分析与 bad case 候选，不写回分数；
- 评分失败/无可信结构化结果 → 报告 `FAILED`，不得生成 0 分正常报告。
- **主观评分锚点约束（2026-09-09 新增）**：P-score 评分动机评分理由必须受题目 rubric 与锚点约束——输出至少含「命中的锚点或要点 / 对应回答原文 / 必需但缺失的要点 / 明确错误或反证 / 尚未展示的更高等级证据 / 评分或无法评分原因」；不得增加题干与 rubric 中未要求的必要标准（「没提某额外技术」不是扣分理由）；更高等级证据不足与本题答错分开说明；替代方案满足任务目标和约束的不因未用指定工具扣分；Lv5 是否需要领导他人以该能力锚点为准，不得让所有技术题通过「没带团队」限制最高等级。输出严格校验类型/范围/证据引用/锚点编号；非法结果进明确失败或复核路径（§13）。

## 18. 拒答（v2.0 最终确认）

```
score_value = 0
score_state = REFUSED
```

- 0 是特殊状态值，不是能力量表 1 分；
- **拒答只进入行为聚合与完整度聚合，不进入能力等级聚合**；item 最终等级由有效能力证据决定，后续有效回答可改变等级；
- 拒答事件永久保留，报告单独展示拒答次数与位置；
- 可能涉及受保护信息或合法隐私质疑的拒答 → 合规/人工处理边界，不直接记 0；
- **实施注记（2026-09-06）**：score_state 六态枚举位 `INSUFFICIENT_EVIDENCE / NOT_ADMINISTERED / INCOMPLETE` 本期**不产出**（by-design）：现终态由 REFUSED（拒答）、INVALIDATED（题库无效）与聚合层 IMPUTED/PROVISIONAL/NO_VALID_OBSERVATION + missing_warnings（§20.1/§20.2）语义等价覆盖；NOT_ADMINISTERED 的潜在场景（派发未答实例进 finalize）走 §20.1 缺失路径，不做区分。枚举位保留供校验与后续生产（D-28 口径集）。

## 19. item 内多题合并与综合题（v2.0 最终确认）

普通题与综合题先转为统一测量记录：

```
item_measurement(question_id, item_id, observed_level, evidence_refs, measurement_source: ordinary|integrated)
item_final_level = adjudicate(ordinary_measurements + integrated_measurements)
```

裁决规则：普通最低测量资格先检查（综合题不能替代）；按 rubric/覆盖/稳定性/冲突裁决，**不按来源加权、不按题数重复乘 item.weight**；共享 evidence span 只影响证据解释、不折扣不自动复制；**旧「观测等级极差 ≥ 阈值即取较低值留人工标记」的直接极差取低法作废（2026-09-09）**——量表统一前置与裁决算法见下；阈值常量 `ADJUDICATE_CONFLICT_THRESHOLD=2` 保留为冲突判定的输入之一（仅在可比较锚点档上生效，集中 `config.py`）；综合题可作为最高等级证据来源（仍受其 rubric 约束）。

**裁决前置：量表统一（2026-09-09 新增）**。裁决前必须先将每题测量记录归一到统一锚点语义——每条测量记录携带 `measurement_target + anchor_level（锚点档） + observed_level`；不同锚点档（基础理解/应用/优化）的证据**不直接互相比较**，更不得跨尺度计算极差（easy[2,3] 与 medium[3,4] 题目回答质量差异是量表差异不是候选人矛盾）。**作废**「对 item 内全部题目的 observed_level 直接求极差」的现行实现（CNN 案例已确认：easy 答对得 5、medium 分析得 3，极差 2 触发伪冲突取低——量表混用产物）。

**裁决算法（修订）**：

1. 相容证据（同锚点档或记录声明相容）按锚点区间合并——共同支持更高层次判断；
2. 冲突判定仅对**同一 measurement_target、可比锚点档**的证据进行；实质矛盾（同一目标上相反陈述）才触发冲突；
3. 冲突未解决 → 该 item 显示待复核，**不以「保守」为理由自动形成确定低等级**（现行 `min(levels)` 取低留标记作废——冲突归冲突，不产生替代性确定值）；
4. 明确自我纠正的回答保留纠正过程（纠正前后都算）；未明确解决的矛盾陈述不得任取较新/较高者；
5. 同一证据被多处引用只算一份独立支持；
6. 最终等级必须能列出所满足的必要锚点与其来源题（完整审计级——实施可分层：第一层只在报告 item 行关联来源题，第二层才做锚点分解展示）。

**不采用以下捷径**（即使冲突或样本不足）：简单平均、直接最高、直接最低、只按题目来源加权。本期综合题仍沿用现有范围（I=0 不排期），测量记录格式保持兼容。

综合题第二题决策表：剩余合法联合 target 为主触发；第一题整体无效可触发；仍受最多 2 题、题库版本匹配、session 状态约束；全场超时不再激活。综合题整体 `ITEM_INVALID` → 所有绑定 item 综合结果无效、移出分母、不算有效测量；单 item 证据不足不影响其他 item 独立评分。

## 20. 缺失、未测量与聚合（2026-09-09 修订：补算作废）

### 20.1 观察集合与未测量项处理（2026-09-09 重大修订：作废比例补算）

```
O = 全部 score_state=SCORED 的 item 级测量
M = 未测量集合（无有效直接观测的正式范围内能力项）
未测量项：无个人等级，标记 UNMEASURED
```

- **比例补算（IMPUTED，以已测能力加权均值 r 为无证据能力统一生成等级）作废**（2026-09-09）：Python 作答不能证明沟通能力、其他算法与经验背景处于同一等级——345 项无证据能力统一标注 3.41 级并占报告权重 91.88% 的实测形态，判定为已知缺陷而非设计特性。**未测量能力显示「未测量」，不生成个人等级，不进实际表现雷达、优势、短板与正式综合分**；不用 0 分代替缺失；不将其他能力的分数重归一化后仍称「完整岗位综合分」。
- **过渡期兼容（仅存量报告回放）**：历史报告 JSON 中已存在的 IMPUTED 数据按当时规则解释生成，只读展示（标注旧口径——补算值参与总分构成），**不得据此重算历史成绩**；
- `O = ∅` → `NO_VALID_OBSERVATION / HUMAN_REVIEW_REQUIRED`（不变）；
- **未测量比例超阈值 → PROVISIONAL + HUMAN_REVIEW_REQUIRED**（阈值沿用裁决值 0.2：正式范围内未测量项占比 > 0.2 → 不能形成完整综合分，复核原因注明「未测量比例过高」，不得混成「题目冲突」或只给列表后段条目标 human_review）；
- required 与 qualification 不适用（前者缺失 → §20.2，后者本就独立展示）；
- 若未来需要抽样估计，另行设计、验证并明确标注——**本期不引入未经验证的估计模型**。

### 20.1.A 测评范围（assessment scope，2026-09-09 新增）

「模型中出现过的能力」≠「本测评评价的能力」。每个测评版本在发布时**冻结正式测评范围**，开考时不可变：

- **冻结字段**：正式计分能力项集（item_id 清单）、各项 required_level、权重、measurement_target、最低证据要求、可使用题目及难度路径、资格条件 集、策略版本；
- **范围区分三类条目**：正式计分项（participant）、岗位背景资料项（reference-only，不占权重、不出雷达、不进总分）、表单事实项（form facts）；
- **发布时确认、开考冻结**：范围随模型 confirm 显式确定（管理端可在 §8.1 人审时标记何者入正式范围），源 JD 与来源证据保留可追溯（为何纳入/排除）；
- **两个禁止事项**：不得在测评结束后只保留问过的能力把覆盖率变 100%；不得前端隐藏未测项却让它们继续参与总分；
- 通用岗位与专项方向需要不同测量目标时建不同**测评版本**（模型版本 + 范围标记），**不得**单凭关键词自动拆岗或删条目；
- 存量模型无范围标记时：默认全部 gate=0 能力项为正式计分范围（与现行行为一致，无破坏迁移）。历史报告无范围快照时按其 item_details 口径解释并注明口径限制。

### 20.2 required 缺失

```
report_status = PROVISIONAL；review_status = HUMAN_REVIEW_REQUIRED
```

不触发补测；人工确认后**可发布为正式报告，必须明确点击发布**；系统不做录用判断。required 缺失与未测量（§20.1）、题目冲突（§19）的复核原因**分别记录**，不得互相混同。

### 20.2.A 评分批次与历史修订（2026-09-09 新增）

- **评分批次（scoring batch）**：`question_score` 增 `scoring_batch_id`（不可变版本标识）；每份报告绑定具体评分批次；新评分结果**追加保存**（不再删除旧评分行后重插——`score_session` 的 DELETE+INSERT 循环作废，该形态即使 report_json 保留旧版本也会替换评分证据链，审计断裂）；
- 原始消息、原题目、旧评分、旧报告、旧异议全部保留；修订记录说明修订原因、规则版本、影响结果；
- 资格覆盖采用可追溯的有效版本（`ORDER BY created_at` + 明确版本选择语义），不使用无 ORDER BY 的 `LIMIT 1`；
- 表单修订使用实例标识 + revision 查询/更新/消费，不更新同一实例的全部版本；表单实际评估使用的 schema 版本写入结果（不统一写当前全局版本）；
- 保存真正使用的 rubric/scorer/测量目标版本（不再长期硬编码 `'v1'` 与空目标）；
- **重算入口**：用户刷新与普通「生成报告」幂等（不重复评分）；历史纠错走**管理员修订流程**——先只读预演（列出受影响题目/分数/覆盖/文案），确认后生成正式修订版；不把旧会话套到后来重建的新岗位模型；旧题无法支持新量表时明确说明「不可完整重建」而非制造新成绩；
- 后台任务绑定明确的生成任务或报告版本：旧任务超时后返回不得更新新任务的占位报告（重试、评分批次、最终报告归属一致）。

### 20.3 总分

```
normalized_item_score = (actual_level − 1) / 4（与 §20.1 s_i=(score−1)/4 同尺度：1→0、5→1）
总分 = Σ(item.weight × normalized_item_score) × 100
gap = required_level − actual_level
门槛项：达标拿满/不达标 0，UI 红绿标签单列
```

大类的 7:3 已体现在 item.weight 中，**聚合时不再二次乘大类比例**。

**完整性门控与精度（2026-09-09 新增）**：

- **总分仅在正式计分范围满足最低测量要求（未测量比例 ≤ 阈值 0.2，§20.1）且关键争议已解决时生成完整值**；否则该场报告**无综合分**（`total_score = NULL`），各接口与消费页面（历史列表、报告页、admin）必须支持无综合分展示，不得以 0 分或占位值冒充（`report.total_score` 列改 NULLABLE，实施须明确迁移与状态契约——2026-09-09 前 NOT NULL 默认 0.0 的旧库行为作进化处理）；
- **未测项得分为「无结果」而非 0**；缺失不得偷偷缩小分母；
- 资格事实独立展示，不进入能力指数（不变）；
- **精度规则**：内部统一精度与舍入规则；权重归一化的累计舍入误差不得全部压给单个最大权重项；报告 JSON 保留可复算的原始贡献（保留足够精度）；总分从未提前舍入的贡献统一计算、**最后一次舍入**；展示层逐项贡献四舍五入后相加不等于显示总分时注明「显示值存在舍入差」，不为凑显示总分修改任何能力的实际等级。

### 20.4 覆盖率口径（2026-09-09 新增）

报告分别展示以下五个指标（取代单一 `coverage_ratio` 观察/可测比例——该口径将必备项排除在分母外为已确认缺陷，作废）：

1. **作答完成情况**：已回答题数 / 计划或允许的题量；
2. **能力观察覆盖**：正式范围内，有有效直接观测（存在 SCORED 记录）的不同能力项数 / 正式范围能力项总数；
3. **有效测量覆盖**：满足该能力最低证据要求的能力项数 / 同分母；
4. **权重覆盖**：达到有效测量要求的能力权重 / 正式范围总权重；
5. **必备项覆盖**：已满足测量要求的必备项 / 必备项总数（单列）。

规则：同一能力两道题只计一个能力项；必备项不从分母排除；资格、经验事实不进入对话能力覆盖率；未出题、拒答、题目无效、证据不足等原因分开显示；被排除或未测项保留在开考前确定的分母中（不得事后删项抬高覆盖率）；分母为零显示「不适用」而非 0%/100%。**区分「存在一条 SCORED 记录」与「已充分测量」**——11 项有评分记录不代表 11 项都满足证据要求。

## 21. 报告（五段式沿用 + v2.0 发布契约）

①顶层结果摘要（总分或无综合分原因 + 状态 + 资格核验摘要折叠——49 项级资格详情默认折叠、展开按类别分组逐条展示，§16.2 四状态）②雷达图（required 灰 vs actual 蓝；只绘制已直接观测项；IMPUTED 项不进雷达——§20.1 已作废补算；轴由测评版本预先确定、不按数据库返回顺序截取，轴绑定 item_id 防索引错位；缺失值不按 0 绘制；观测项不足时不强行画雷达改逐项对比）③优势/短板/建议（代码排序：优势=gap≤0 中权重前 3；短板=gap>0 中 gap×weight 前 3；只基于可用、无未解决争议的证据；未测项进「尚未覆盖」不算短板；争议项进待复核；LLM 只写文字且只能基于给定短板项；无足够证据显示「暂不足以判断」不显「没有短板」）④逐题回顾（score_final + 证据 quote + 来源定位；实际题号 seq、包含全部实际出过的题、正确性/能力证据/最终结论分别展示、过程参考值与终局结果分列）⑤逐项明细（放最后；正式范围能力默认视图 + 筛选；「得分」列明确为观测等级或综合贡献；差距=要求−表现、正值未达标 0 达标 负值超出；无数据/拒答/无效/待复核分别显示；长表筛选不改变覆盖率与总分）。

**报告顺序与锚点（2026-09-09 确认）**：五段固定顺序——摘要 → Radar → Summary（③）→ Review（④）→ Details（⑤）；长明细放最后；顺序同时适用正常报告、暂定报告与无综合分报告；页面锚点使用稳定标识（section id），不按「第几个 section」定位（避免调整顺序后跳错位置）。优势/短板每条结论关联具体题目和证据；文案限定为本场证据，不泛化为永久能力特征；「达到要求」与「超出要求」用词区分。

### 21.1 报告状态机与发布

```
report_status: GENERATING → PROVISIONAL | READY → PUBLISHED | FAILED
review_status: NONE | REQUIRED | IN_PROGRESS | CONFIRMED | CLOSED
```

**发布前一致性校验（代码，七项为基础、2026-09-09 扩充语义深度）**：数字可重算（从未提前舍入的贡献统一计算）；weight 总和一致；引用 question/message 属于该 session；model/version 与快照一致；无效题/系统错误未进正常分母；缺失/REFUSED/required 警告与结构化状态一致；文案无录用判断表述。**校验语义升级（2026-09-09）**：仅验证「字段存在/清单存在」的浅检查不算通过——至少含：每条评分绑定评分批次与题目一致；引文可定位到对应消息（source_message_id 归属正确的轮次）；覆盖率按能力项计数守恒（资格/经验不进对话能力分母）；无效/拒答/缺失未被当成正常低分；综合分仅在完整性条件满足时存在；雷达、Summary、Details 用同一组结果；优势短板不含未测或未解决争议项；报告文字无结构化结果中不存在的确定性结论；复核原因与报告状态一致；发布不清除仍然存在的完整性限制。

**发布前一致性校验（2026-09-09 执行性补充）**：`generate_report()` 返回 FAILED 不抛异常——调用方（后台任务）必须检查返回值的 report_status，不得在 FAILED 时记 TASK_SUCCEEDED（事件状态与真实报告状态矛盾为已确认缺陷，修复必须覆盖此调用点）。

**发布语义（2026-09-09 修订）**：报告状态三维度——是否生成成功 / 测量是否完整（有无争议）/ 是否已人工发布。**发布不能补出不存在的证据**：部分报告可以在明确标注范围限制的前提下发布（PROVISIONAL 正常发布路径），但不得因发布而变成完整测量或获得完整综合分。发布请求必须携带明确复核结果（review_outcome）与必要理由；默认值直接 CONFIRMED 的免审直通**作废**（现行 `review_outcome: str = "CONFIRMED"` 默认值移除——发布需显式选择结果）；发布动作不改变证据完整性；记录执行人、时间、依据与报告版本。

**接口一致性（2026-09-09 新增）**：报告读取序列化出口统一——按会话（GET by-session）与按 report_id 读取返回一致的 report_status/version/完整性信息；结果快照（report_json）与生命周期元数据（report 行列）职责分离但状态必须一致（发布动作更新表列时同步更新 JSON 内复核字段，不得一处新一处旧）。

**流程**：评分完成 → 聚合与校验 → 生成（PROVISIONAL 或 READY）→ 有人工复核要求则等待 → 管理员复核后**明确点击发布** → PUBLISHED。人工复核字段：`review_request_reason / reviewer_id / review_note / review_outcome / reviewed_at / publish_confirmed_by / published_at`。报告生成不隐式代替评分；正常 UI 主链必须 score→report 串行（前端完成后由服务端执行，不依赖浏览器补调）。

**重复触发护栏（P0 成功标准 5）**：`POST /sessions/{id}/report` 在会话已存在报告且报告处于生成中（`GENERATING`）或终态成功（`PROVISIONAL`/`READY`/`PUBLISHED`）时返回 409（`REPORT_GENERATING` / `REPORT_ALREADY_GENERATED`），不重复触发评分/报告；报告为 `FAILED`（后台链失败）或无 report 行时允许重新入队（202），作为失败重试路径。

**死任务接管与看门狗（2026-09-08 事故登记）**：`GENERATING` 为占位态，其 409 护栏仅保护**真在途**任务——最新 `GENERATING` 行行龄超 `REPORT_STALE_SECONDS = 60 分钟`（用户 2026-09-08 裁决，落 `api/assessment.py` 常量 `_STALE_GENERATING_SECONDS`）视为死任务（后台线程已死亡 / 进程重启丢任务），`POST /report` 放行**版本化接管**（写新 `version=MAX+1` GENERATING 行，不覆盖旧行；`created_at` 解析失败保守维持 409 不接管）；60 分钟内维持 409。后台串行链整体处于**看门狗**下（内层线程执行 + `join(60min)`，与接管阈值共用同一常量——统一语义：前端可见的死任务接管阈值 = 后端看门狗超时），超时写 `TASK_FAILED` 事件 + `FAILED` 行（文案注明超时，前端确定性展示失败原因）；任务异常兜底链（写 FAILED 行 / TASK_FAILED 事件）自身失败不再静默——至少落 stderr 进程日志（uvicorn.log 可查）。**执行纪律**：后台链任何「另开连接写库」的步骤（`llm_trace` 审计行、失败收尾行）之前，主连接不得持有未提交写事务（2026-09-08 事故：`_detect_bad_case_divergence` 的 bad_case INSERT 挂在主 conn 末尾 commit，持有 RESERVED 锁进 LLM 调用 → 全进程 `database is locked`、锁泄漏至进程重启）；违例修复为该检测改**独立小事务**（自开连接自 commit/close）+ `generate_report` 全函数 `finally` 兜底 rollback（正常路径已 commit → no-op）。连接纪律已核查全部 9 个 `call_llm_json` 调用点，其余 8 处原有「先 commit 再进 LLM」纪律（docstring 明载）。前端：报告页「重新生成」按钮必须走 `POST`（`regenerate()`）而非只读 bootstrap（GET 只会读回旧状态，POST 才能触发超龄接管 / FAILED 重生成）；409 分支分派——`REPORT_GENERATING`（真在途）并入轮询、`REPORT_ALREADY_GENERATED`（极端时序）重取、`SESSION_NOT_COMPLETED` 明确文案。

- **一致性（b）**：固定 transcript 复跑，断言 score_final 分差 ≤1（temperature=0；固定 model/provider/版本/rubric 快照）；score_live 不在断言范围；

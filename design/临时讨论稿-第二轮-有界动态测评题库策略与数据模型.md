## 0. 本轮讨论的处理结果

本轮在上一轮临时讨论稿基础上，进一步明确了：

1. 题库是按岗位预先生成/维护的结构化题库，不是每轮临时自由生成；
2. 题库具有四层逻辑：大类、类内子类、具体题目，以及题目之间可能存在的 chain 关系；
3. `followup` 仍属于当前题，不增加主问题数量，不切换到下一题；
4. 下一道主问题应由代码策略根据题库层级配额和当前会话状态动态选择，而不是创建 session 时一次性固定完整队列；
5. 采用当前服务加明确的领域状态机，不立即引入 CrewAI、ADK 等通用 Agent 框架；
6. 正式测评不设计 Web Search；模型知识不足时走受控失败/人工介入路径；
7. 使用 Tools 概念，但工具必须分阶段授权，关键状态迁移只能由代码决定；
8. `score_live` 只作为过程性导航信号，不进入最终分数的 50/50 合成；
9. 当前目标按真实上线项目要求处理，不以“课程演示可接受”为放宽理由；
10. 本轮目标时间约束暂定为：全场不超过 40 分钟，单题不超过 20 分钟；暂不预设全会话 Token 硬预算、模型输出 Token 硬上限和 24 小时数据过期删除。

下列问题仍需在本文中细化并由用户确认：

- 题库层级配额的精确算法；
- chain、追问、难度三者的优先级；
- “等值备用题”的严格定义；
- 评分量表中“拒答记 0”与现行 1–5 分制的兼容方式；
- 缺失项补算公式的精确定义及风险控制；
- 动态难度升级/降级的触发、速度和最高难度题数量；
- Tools 中表单各操作的边界；
- 上下文管理与现有 P-refine 的关系；
- 不增加过多表的前提下，如何表达题库、chain、会话动态状态和证据关系。

# 1. 统一术语和边界

## 1.1 “主问题”和“追问”必须是两个不同层级

### 主问题（main question）

主问题是题库中一次正式进入测评队列、用于覆盖一个能力项或门槛维度的题目。主问题切换时：

- 当前题结束；
- 当前题的回答和证据状态被封存；
- 主问题计数增加 1；
- 代码策略重新决定下一题；
- 可切换能力项、大类、类内子类或难度。

### 追问（follow-up / probe）

追问是当前主问题内部的补证据行为：

- `question_id` 不变；
- 不增加主问题数量；
- 不消耗另一个题目的配额；
- 仍属于同一能力项、同一题目上下文和同一题链位置；
- 每题最多两次追问的既有约束继续保留；
- 追问本身、触发原因、回答和结果必须单独留痕。

因此，本轮确认的基本规则是：

```text
主问题 = 题库中的一次测量机会
追问   = 当前主问题内补足证据的子轮次
```

不能把追问误计为新题，也不能把新主问题伪装成追问来绕过题量和时间限制。

## 1.2 四个大类和三个类内子类

题库的逻辑分类为：

```text
hard_skill
├── required
├── preferred
└── plus

soft_skill
├── required
├── preferred
└── plus

experience
├── required
├── preferred
└── plus

qualification
├── required
├── preferred
└── plus
```

其中：

- 大类：`hard_skill`、`soft_skill`、`experience`、`qualification`；
- 类内子类：`required`、`preferred`、`plus`；
- 具体题：隶属于一个大类、一个子类，并绑定一个能力项或门槛项；
- `qualification` 原则上优先通过结构化表单核验，但是否允许题库问题作为补充，需要另行确认；
- `chain` 是题目之间的测量路径关系，不是额外的分类层。

### 需要确认的边界

现有设计将 `experience` 和 `qualification` 都作为题量/门槛体系的一部分，但本轮尚未最终明确：

1. `qualification` 是否完全不占对话主问题配额，只走表单；
2. `experience` 是通过行为问题测量，还是也可以由简历/表单事实核验；
3. 同一个能力项是否允许同时存在于多个题目、多个难度和多个 chain；
4. 一个题目是否允许绑定多个能力项。

**当前建议：**

- `qualification` 的事实核验以代码触发表单为主，不占普通能力题配额；如果岗位要求对资格进行解释性核验，另设明确标记的 qualification follow-up，不与 hard/soft 的能力分混算；
- `experience` 可以同时有事实表单和行为问题，但两种证据类型必须在评分模型中分开标记；
- 一个题目原则上只绑定一个主要评分能力项，可有若干非评分的辅助标签；
- 一个能力项可以有多道不同难度题和多条 chain，但一次 session 不应无理由重复测同一证据。

这四点仍需用户确认，未视为已定。

# 2. 题库应是“逻辑树”，还是“物理树”

## 2.1 建议：逻辑上是树，数据库中不拆成四层表

用户提出的题库结构很适合作为产品和策略层的树：

```text
大类 → 子类 → 题目
```

但不建议在数据库中建立：

```text
hard_skill_table
required_table
question_table
chain_table
...
```

这会造成表数量膨胀、跨层外键复杂、查询和迁移困难，也不利于题目版本化。

更合适的是：

- 题目使用一张规范化的 `question_bank` 表；
- 用枚举列表示 `category` 和 `tier`；
- 用字段表示 `difficulty`、`chain_id`、`chain_seq`、`chain_role`、`item_id`、`qtype`、`scope` 等；
- 由 `(position_id, category, tier)` 形成逻辑树的索引；
- 用 JSON 保存题面变体、探针模板和非核心扩展属性，但不把关键筛选字段只藏在 JSON 中。

概念形式：

```text
question_bank
├── position_id
├── model_id / model_version
├── item_id（能力项或门槛项）
├── category
├── tier
├── difficulty
├── qtype
├── scope（position / general）
├── chain_id（可空）
├── chain_seq（可空）
├── chain_role
├── prompt / rubric_ref
├── answer_key（客观题时使用）
├── equivalence_group_id（可空）
├── status
└── version metadata
```

## 2.2 不建议让 `question_bank` 直接承担所有会话状态

题库是岗位/模型版本级的静态资产；当前会话中的：

- 已选题；
- 已回答；
- 当前 chain 进度；
- 当前难度；
- 追问次数；
- evidence coverage；
- 该题被跳过/拒答/无效的原因；

都属于 session 运行状态，不应回写题库原记录。

推荐保留当前已有的 `assessment_question` 作为 session 题目实例，但不再把它理解成“创建 session 时必须一次性填满的固定队列”。它可以承担两种职责之一：

### 方案 A：动态实例化（推荐）

- session 创建时只建立 session；
- 每次代码策略选中一个题目时，才创建一条 `assessment_question` 实例；
- `seq` 表示实际进入测评的顺序；
- 记录选择原因、预算快照和题库题目版本；
- 被拒绝/未选中的题目不产生实例。

优点：真实反映动态路径，避免预排队列与实际状态不一致。

### 方案 B：候选集合 + 动态激活

- session 创建时建立一个候选题集合；
- 每轮只激活其中一个题；
- 额外记录 `activated_at`、`skipped_at` 和选择原因。

优点：可以提前校验题库是否覆盖 required 项；缺点是会产生更多 session 题目记录和状态复杂度。

**当前倾向：方案 A。** 但这属于数据库/运行时设计决策，需要确认后才进入正式设计。

## 2.3 题目版本必须冻结

一次 session 开始后，至少要冻结：

- 岗位模型版本；
- 能力项版本或模型快照；
- 题库题目版本；
- rubric/行为锚点版本；
- question prompt 版本；
- tool policy 版本；
- 状态机策略版本；
- 题目权重快照。

后台管理员之后修改题库，不得静默影响已开始的 session。

# 3. 下一主问题的动态选择策略

## 3.1 总体原则

下一道主问题不是由 LLM 自由决定，而由代码策略执行以下顺序：

```text
1. 判断测评是否应结束
2. 判断当前大类是否还有可访问配额
3. 判断当前大类下的子类是否还有可访问配额
4. 判断当前能力项/题链/难度是否有可访问候选题
5. 在候选题中按固定优先级选择
6. 写入选择原因、配额和状态快照
```

LLM 可以提供当前回答的结构化 observation，例如：

- 证据覆盖了哪些考察点；
- 是否需要补充；
- 是否属于拒答、跑题或其他异常状态；
- 当前证据是否达到当前题的最低要求。

但 LLM 不能直接：

- 增加配额；
- 改变模型权重；
- 自己结束整场；
- 访问未授权题库范围；
- 修改难度规则；
- 把一条普通回答解释成已覆盖任意能力。

## 3.2 配额的来源与表达

用户提出：大类题目数量和子类题目数量由权重及题目数量决定。这里需要把“权重决定什么”和“题目数量决定什么”拆开，否则会出现同一权重被重复计算的问题。

推荐分为三步：

### 第一步：确定大类主问题配额

对于岗位模型中的四个大类，代码根据：

- 该大类是否存在有效可测能力项；
- 大类的模型权重；
- 大类中 required 能力覆盖要求；
- 预设的最小/最大题量；
- 40 分钟总时间预算；
- 题库可用数量；

计算每个大类的主问题配额。

### 第二步：在大类内部确定 tier 配额

在某大类配额确定后，再根据：

- `required / preferred / plus` 的能力项权重；
- required 必测约束；
- 子类最小覆盖要求；
- 各子类可用题库数量；
- 时间和题量剩余；

计算该大类内三个 tier 的配额。

### 第三步：把配额映射到能力项

在每个 `category × tier` 配额内，根据能力项 `item.weight`、required 标记、题库覆盖和已测证据，选择要测的能力项，再选择具体题目。

### 必须防止的错误

不能简单地：

```text
大类权重 × 子类权重 × 难度权重 × 题目数量
```

然后再把所有乘积相加，因为：

- 大类权重和子类权重可能已经包含同一层重要性信息；
- 题目数量是测量资源，不天然是分数权重；
- 难度是测量路径，不天然是最终分数权重；
- 这样容易重复乘权，导致总分不满或某些能力被隐性放大。

## 3.3 推荐的配额约束顺序

在不改变用户提出的层级逻辑前提下，建议执行：

```text
A. 全局结束检查
   ├─ 已达到主问题总量上限？
   ├─ 已覆盖所有必须测的 required 能力？
   ├─ 剩余时间不足以完成下一题？
   └─ 当前 session 是否进入 incomplete / human_review？

B. 大类配额检查
   ├─ 当前大类未达到配额 → 留在当前大类
   └─ 当前大类达到配额 → 按固定类目顺序进入下一可用大类

C. tier 配额检查
   ├─ 当前 tier 未达到配额 → 在当前 tier 中选题
   └─ 当前 tier 达到配额 → 进入当前大类下一个可用 tier

D. 题链与难度检查
   ├─ 当前题需要 followup → 不进行主问题选择
   ├─ 当前 chain 允许且策略要求继续 → 取 chain 下一节点
   ├─ 当前 chain 不应继续 → 选择其他候选题
   ├─ 当前能力需降/升难度 → 取对应难度题
   └─ 无候选题 → 标记该能力未测或进入人工复核
```

这里有一个需要用户确认的细节：你描述的是“当前大类达到限额就跳至下一个大类”，但如果当前大类中存在尚未覆盖的 `required` 能力，而配额已经耗尽，系统应当：

- 严格遵守大类配额并标记未覆盖；还是
- 为 required 能力触发刚性例外，允许临时增加该大类题量；还是
- 提前从其他大类/子类回收题量。

**当前建议：required 覆盖是硬约束，但不能无上限突破 40 分钟；应采用“回收非 required 配额 → 仍不足则 incomplete + human review”的顺序。**

## 3.4 题库遍历不是简单的“从上到下扫树”

如果直接按：

```text
hard_skill → soft_skill → experience → qualification
```

固定遍历，会让类目顺序本身成为隐含权重，并可能在前面大类耗尽时间后使后面类目无法测量。

建议预先生成一个 `category_plan` 和 `tier_plan`：

```json
{
  "category_plan": [
    {"category": "hard_skill", "quota": 6, "min_required": 3},
    {"category": "soft_skill", "quota": 2, "min_required": 1},
    {"category": "experience", "quota": 2, "min_required": 1},
    {"category": "qualification", "quota": 0, "form_required": true}
  ],
  "tier_plan": {
    "hard_skill": {
      "required": 4,
      "preferred": 1,
      "plus": 1
    }
  }
}
```

这里的数字只是结构示例，不是当前拍板值。

策略引擎应在 session 开始时计算计划快照，但在每轮选择时根据实际完成、拒答、无效题、时间和错误进行“剩余配额”重算。这样既满足岗位模型驱动，又避免固定整套队列。

# 4. Chain、追问和静态难度的优先级

## 4.1 三者不是同一种关系

需要明确区分：

- `followup`：当前题内补证据；
- `chain`：同一能力或关联能力的预定义题目路径；
- `difficulty`：题目难度层级。

不建议把它们都放进一个简单的优先级数字中。

## 4.2 推荐的决策优先级

```text
第一优先级：流程和安全护栏
第二优先级：当前题 followup
第三优先级：required 能力覆盖
第四优先级：当前 chain 是否应继续
第五优先级：难度升级/降级策略
第六优先级：category/tier 剩余配额
第七优先级：题目权重、题库质量和随机种子
```

但上面第三至第六项需要更精确地解释：

### 推荐的实际决策顺序

```text
if 当前题仍需要合法追问:
    保持当前题，执行 followup
elif required 能力尚未覆盖:
    优先选择能覆盖该 required 能力的题
elif 当前能力的 chain 尚未完成且继续 chain 有策略价值:
    选择 chain 下一题
elif 当前能力需要升级或降级:
    从对应难度候选中选择题目
else:
    按剩余 category/tier 配额和 item.weight 选择下一题
```

### Chain 不应无条件优先

即便题库里存在 chain，也不能因为“链还没走完”就强行继续。以下情况应终止当前 chain：

- 当前能力证据已经达到该题链的测量目标；
- 当前题已两次追问仍然证据不足；
- 当前题发生明确拒答；
- 时间预算不足；
- 继续 chain 会挤掉尚未覆盖的 required 能力；
- chain 下一题难度或内容不符合当前策略；
- 题目自身被标记为无效或模型无法可靠判断。

### 追问和 chain 的关系

当前题的 followup 达到上限后：

- 不再继续当前题追问；
- 先对当前题封存状态；
- 再决定是否进入 chain 下一题；
- 如果当前题证据不足且 chain 下一题仍然测量同一构念，是否继续应由策略决定，而不是自动继续；
- 如果 required 能力尚未测到，优先使用另一个等值题或人工复核，而不是无限追问。

## 4.3 “等值备用题”的严格定义

本轮用户明确要求：等值备用题中，参与总分权重的所有字段必须相同。这个方向应保留，但需要把“所有字段”拆成可验证字段。

建议一个题目只有在以下字段全部一致时，才可归入同一个 `equivalence_group_id`：

### 必须一致的评分/测量字段

- `position_id`；
- `model_id` 和 `model_version`；
- `item_id`；
- `category`；
- `tier`；
- 该 item 的 `weight_snapshot`；
- `qtype`；
- `difficulty`；
- `measurement_target` / 考察点集合；
- `rubric_version`；
- `score_scale`；
- `gate_flag`；
- `chain_role`（若替换发生在 chain 内）；
- 题目是否占用主问题配额；
- 预计最长时间/最大追问预算（若该字段被纳入测量路径）。

### 还需要人工或离线验证的字段

仅字段一致并不自动证明心理测量意义上的等值。还需：

- 内容覆盖一致；
- 认知负荷相当；
- 语言难度相当；
- 可能的领域知识要求相当；
- 评分员/评分器对两题的评分分布可比；
- 不因某一题更容易诱发详细回答而给予额外机会。

因此必须区分：

```text
schema_equivalent       = 字段和版本一致
measurement_equivalent  = 经过人工/数据验证的测量等值
```

正式测评中，只有 `measurement_equivalent=true` 的备用题才能无条件替换；只有 schema 相同但尚未验证的题目，最多作为人工复核候选，不能直接声称公平等值。

### 需要确认的字段冲突

如果 `item.weight` 不随难度变化，那么不同难度题不能称为等值备用题，因为 `difficulty` 不同；它们只能是同一能力项的不同测量路径。也就是说：

- **等值备用题**：难度也必须相同；
- **升/降难度题**：不是等值备用题，应记录为不同路径和不同难度。

# 5. 静态难度是否构成总分权重

## 5.1 推荐结论：难度不作为第三层最终权重

当前系统已有：

- 类间权重：`hard_skill / soft_skill / experience / qualification`；
- 类内权重：`required / preferred / plus`；
- 最终能力项 `item.weight`，且设计要求权重和为 1。

本轮建议保持：

> **静态难度不再作为第三层最终分数权重。**

难度是“如何测量同一个能力”的路径参数，不是“这个能力在岗位上有多重要”的业务权重。

如果把难度再乘进总分，会造成：

- 同一个能力因回答了 hard 题而获得更高权重；
- 候选人因路径不同而承担不同分母；
- 自适应降难度导致分数不再可比；
- 大类、子类和 item 权重被重复计算；
- 总分难以保持满分且无法解释。

## 5.2 难度对最终评分的正确影响方式

难度仍然可以影响：

- 题目选取；
- 证据要求；
- 能力等级的可观测上限；
- 题目是否足以支持某个等级判断；
- 诊断报告中“在哪个难度层级表现稳定”；
- 人工复核触发条件。

但最终分仍应按岗位模型的 `item.weight` 聚合：

```text
item_score = 根据回答证据和 rubric 得到的能力项分数
final_score = Σ(item.weight × normalized_item_score)
```

其中 `normalized_item_score` 的含义需要进一步确认：

- 是始终按 1–5 归一化；还是
- 根据实际答题难度设置证据上限；还是
- 只有达到最高难度题才允许获得 5 分。

如果采用“达到最高难度才可获得最高等级”，必须预先写入 rubric，而不是在聚合时偷偷给难度加权。

## 5.3 最高难度题的公平性问题

用户提出必须保证一定数量的最高难度题。这里不能只规定“每个人都做相同数量的最高难度题”，因为岗位不同、能力项不同、题库深度不同；也不能让模型自由决定某人是否进入最高难度。

建议先定义三个概念：

- `hardest_available`：该能力项题库中最高可用难度；
- `highest_difficulty_required`：该岗位模型/能力等级要求的最高测量难度；
- `highest_difficulty_min_count`：该 session 至少需要完成的最高难度题数量。

推荐初始策略不是一个全局固定数字，而是按岗位模型生成：

```text
highest_difficulty_min_count
= min(
    岗位 required 能力中具备已验证最高难度题的数量,
    受 40 分钟和单题 20 分钟预算允许的数量
)
```

然后要求：

- 只能在题库具备已验证最高难度题时计入；
- 不足时标记题库覆盖不足，不用低难度题冒充最高难度；
- 因候选人回答差而降级时，若尚有时间，应保留至少一个最高难度验证机会；
- 不应为了凑数量，在不同候选人身上使用不等值或不同构念的最高难度题；
- 如果某候选人因时间、技术、合理便利或系统错误未完成最高难度题，记录 `NOT_ADMINISTERED` 或 `INCOMPLETE`，不直接推断其能力低。

### 仍需用户确认的核心问题

“必须确保有一定数量的最高难度题”至少有三种含义：

1. 每个 session 至少问固定数量最高难度题；
2. 每个 required 能力至少尝试一次最高难度题；
3. 只对最终有机会达到高等级的能力项问最高难度题。

**当前推荐：采用第 3 种，并设置岗位级最小覆盖计划。**

理由是：对一个明显低于最低要求、且已经出现充分低水平证据的能力，强行继续大量最高难度题，既浪费时间，也不一定增加有效信息；但至少应保留一套验证高等级的路径，防止过早锁死候选人。

这只是建议，未确认。

# 6. 难度升级、降级和速度

## 6.1 用户提出的降级触发条件

本轮拟保留以下降级触发条件：

1. 候选人跳过；
2. 连续答错两道同一难度级别的题；
3. 当前难度不为最低难度；
4. 追问后回答仍然模糊；
5. 追问后回答仍然错误或明显不足。

这里的“答错”必须先定义为有效回答经过评分器/规则判定后未达到该难度题的最低行为锚点，不能把：

- 拒答；
- 技术故障；
- 题目无效；
- 模型无法判断；
- 合理便利；
- 题目理解障碍；

直接当成答错。它们进入其他状态。

## 6.2 降级行为

当触发降级条件时：

- 如果当前不是最低难度，下一道同一能力项题目降一级；
- 如果已经是最低难度，保持最低难度，不再继续降；
- 降级不改变 `item.weight`；
- 降级不直接扣最终分；
- 降级事件写入会话轨迹，并在报告/人工复核中可见；
- 低难度题的回答仍需按该题自身 rubric 评分，不能因为题目被降级就自动给低分；
- 降级之后是否回到更高难度，需要独立的升级条件，不能自动来回震荡。

## 6.3 升级行为

从最低难度开始，并不意味着每答对一题就立即升级。推荐使用“稳定证据”而不是单次 `score_live`：

```text
最低难度答对且证据充分
→ 进入中等难度

中等难度答对且证据充分
→ 进入最高难度

最高难度达到岗位要求的证据阈值
→ 当前能力项停止继续加题，转下一个覆盖目标
```

### 推荐的升级速度

- 每个难度级别至少有一次有效作答；
- 从低到中：一次有效且充分的最低难度证据即可尝试；
- 从中到高：至少一次有效且充分的中等难度证据，或同一能力项两次连续稳定证据；
- 发生模糊、错误或追问后仍不足时，不升级；
- 每次升级最多跨一个难度级别；
- 不允许从最低直接跳最高，除非岗位题库明确没有中间级别；
- 升级和降级都不能改变能力项最终权重。

这些是初始策略建议，不是心理测量结论，需要真实数据、题目校准和路径等值验证。

## 6.4 连续答错的窗口如何定义

“连续两题”应限定为：

- 同一 `item_id`；
- 同一 `difficulty`；
- 两题均为有效作答；
- 两题均未被标记为 `INVALIDATED`；
- 中间没有成功达到该级别证据阈值；
- 不是单纯的拒答、技术错误或流程质疑。

如果题库只有一题该难度，则不能伪造“连续两题”，可使用“追问后仍不足”触发降级或保持。

## 6.5 防止降级策略造成不公平

降级是测量路径变化，不是惩罚。必须保存：

- 降级前难度；
- 触发状态；
- 触发回答对应的证据；
- 降级后题目；
- 降级后是否获得完整回答机会；
- 最终评分使用了哪些难度题。

此外，应在评测中做路径反事实测试：相同候选人回答仅改变回答顺序、冗长度或礼貌程度时，不应无理由触发不同的降级路径。

# 7. 模糊、不会、拒答、跑题和攻击性行为的状态控制

## 7.1 统一处理管线

每次候选人提交回答后，建议经过以下顺序：

```text
1. 系统/权限/会话有效性检查
2. 技术和无障碍检查
3. 候选人输入安全分类
4. 过程状态分类
5. 证据覆盖判断
6. 代码策略决定动作
7. LLM 生成该动作对应的固定边界话术
8. 持久化全部状态
```

LLM 可以协助分类，但分类结果必须经过代码白名单校验；对于高风险状态可采用“规则 + LLM”双重判断，冲突时进入人工复核，不让 LLM 单独决定不利结果。

## 7.2 建议的状态枚举

```text
VALID_EVIDENCE
NEED_CLARIFICATION
OFF_TOPIC
NO_RECALL
DECLINED
PROCESS_CHALLENGE
CONDUCT_EVENT
TECHNICAL_OR_ACCESS_BARRIER
PROMPT_INJECTION
MODEL_UNCERTAIN
ITEM_INVALID
```

这些是过程状态，不等同于最终能力分。

建议再为评分结果设置独立的 `score_state`：

```text
SCORED
REFUSED
INSUFFICIENT_EVIDENCE
NOT_ADMINISTERED
INVALIDATED
INCOMPLETE
HUMAN_REVIEW_REQUIRED
```

## 7.3 含糊或信息不足：中性澄清就是 followup

本轮确认：这里的“中性澄清”就是一次 `followup`，但不是随意聊天，而是有明确目的的证据探针。

推荐阶梯：

```text
第一次回答含糊
→ followup-1：中性澄清

仍未覆盖考察点
→ followup-2：统一结构探针（如情境/行动/结果）

仍然含糊
→ 封存当前题为 INSUFFICIENT_EVIDENCE
→ 根据策略进入下一题、等值备用题或 HUMAN_REVIEW_REQUIRED
```

留痕至少包括：

- 触发状态；
- 触发的考察点；
- 使用了哪一种探针模板；
- 是否改变题意；
- 候选人对探针的回答；
- 追问前后 evidence coverage；
- 是否消耗了单题/全局/时间预算。

## 7.4 不会或想不到：脚手架必须作为测评证据

本轮确认：提供回答格式脚手架这一行为要留痕，并进入最终分析。

建议将帮助分级：

### Level 0：不提供内容线索

```text
“可以先说一个最接近的具体经历，包括你当时做了什么以及结果如何。”
```

仅提示回答结构，不提供答案关键词或理想行为。

### Level 1：重复或中性释义

重新说明题目要求，但不加入原题没有的能力线索。

### Level 2：等值备用题

只有存在 `measurement_equivalent=true` 的备用题时才允许替换。

每次脚手架事件需要保存：

- `scaffold_level`；
- 模板版本；
- 触发原因；
- 是否属于所有候选人可获得的标准支持；
- 候选人在支持前后的回答；
- 支持是否影响 evidence coverage；
- 是否影响最终评分解释。

### 评分含义

“在脚手架帮助下答出”不能被当成与“未经帮助独立答出”完全相同的证据。建议在评分证据中同时记录：

```text
independent_evidence
scaffold_assisted_evidence
scaffold_level
```

但是否直接降低分数、降低多少，不能由 LLM 自由决定，必须在 rubric 中预先定义。当前建议：

- 脚手架不直接修改 `item.weight`；
- 脚手架不自动把能力分归零；
- 如果岗位要求“独立完成”是被验证的构念，可以在行为锚点中规定帮助后的最高等级；
- 如果没有这项岗位效度依据，报告应描述“证据是在结构化提示后获得”，而不是擅自扣分。

这里与用户“对于不会的答案应相应减分”的理解存在一个需要明确的细节：

> 是“只要出现不会/想不到就扣固定分”，还是“根据脚手架等级限制可获得的最高能力等级”，还是“把不会本身作为独立的过程指标而不直接改能力分”？

**当前更推荐第三种与第二种结合：**不会/想不到作为过程证据留痕；只有 rubric 已明确要求独立作答时，才限制该题最高等级。未确认。

## 7.5 明确拒答：不提供补答机会

本轮修正为：

- 不在测评末尾提供统一补答机会；
- 候选人明确表示不回答当前题后，最多发送一次确认/跳过提示；
- 候选人仍拒绝时，当前题结束；
- 记录 `DECLINED` 和 `REFUSED`；
- 按本轮用户意见，拒答对该题映射为 0；
- 拒答不自动改变其他能力项的分数；
- 拒答行为本身作为报告和人工分析证据；
- 如果拒答针对的是可能触及受保护信息的题目，应转为流程/合规审查，不应直接当成能力拒答。

### 重要冲突：现行量表是 1–5，不包含 0

当前设计使用 1–5 Dreyfus 分数，而本轮提出拒答映射为 0。必须二选一：

#### 方案 A：0 是特殊状态分，不是能力量表分（推荐）

```text
score_value = 0
score_state = REFUSED
```

聚合器明确知道 0 来自拒答，不把它误解释为“能力量表最低锚点”。报告同时显示：

- 能力评分；
- 拒答事件；
- 该项未获得有效行为证据。

#### 方案 B：把正式能力量表扩展为 0–5

需要重新定义所有 rubric、报告、聚合、测试和历史数据兼容策略。

**当前建议采用方案 A，但需用户明确确认。**

### 拒答与公平性的边界

“拒答记 0”只能应用于：

- 候选人明确表示不回答；
- 已被告知可跳过且仍明确拒绝；
- 不是技术故障、无障碍障碍、题目错误、模型错误或合理的隐私/合规质疑；
- 拒答对象确实是岗位相关且已批准的测量内容。

不能把以下情况记为拒答 0：

- “我想不起来”；
- “我不知道”；
- 回答含糊；
- 短暂沉默；
- 无法理解题目；
- 申请合理便利；
- 对涉及敏感信息的合法质疑。

## 7.6 网络中断和系统错误

网络中断属于系统范围错误，不扣分。建议流程：

```text
检测到请求失败/连接断开
→ 保存当前客户端请求和服务器状态
→ 暂停测评计时
→ 使用幂等键重试
→ 重试成功则恢复当前题
→ 重试失败则进入 TECHNICAL_OR_ACCESS_BARRIER
→ 必要时人工介入或改期
→ 该题/会话标记 INCOMPLETE 或待人工复核
```

至少需要：

- answer submission idempotency key；
- 服务端不能因重试重复写消息、重复计追问或重复扣预算；
- 重试次数和退避策略；
- 测评计时暂停/恢复记录；
- 前端明确显示“系统处理中”，而不是要求候选人重新提交并承担风险；
- 失败日志和影响范围可供管理员查看；
- 若无法恢复，不能把缺失回答当作 0。

## 7.7 模型无法判断和题目无效

必须区分：

### `MODEL_UNCERTAIN`

模型无法可靠判断候选人的回答是否覆盖考察点，或无法安全执行下一步：

1. 不猜测；
2. 不自动扣分；
3. 不自动结束整场；
4. 可以执行一次预定义中性澄清；
5. 仍无法判断则暂停该题并进入人工复核；
6. 保存原始回答、模型输出、冲突信息和人工处理结果。

### `ITEM_INVALID`

题目本身存在错误、答案键失效、rubric 缺失、题目与岗位模型不匹配或无法确定岗位相关性：

1. 立即停止该题评分；
2. 标记 `INVALIDATED`；
3. 该题不进入正常总分分母；
4. 触发人工介入；
5. 必要时对受影响 session 执行重新测评或重新计算；
6. 题目进入题库禁用/修订队列。

“模型无法判断”和“候选人答错”不能混用。

# 8. 模型知识不足时的应对（不设计 Web Search）

本轮确认：不设计 Web Search，也不在正式测评中临时访问外部互联网。

## 8.1 知识不足的三种来源

### A. 题目要求超出已批准知识边界

例如题目涉及岗位并未定义、题库和 rubric 未覆盖的技术细节。处理：

- 标记 `ITEM_INVALID` 或 `MODEL_UNCERTAIN`；
- 不向候选人临时搜索；
- 不改变评分标准；
- 人工检查题目是否应从题库移除或补充批准知识。

### B. 候选人回答信息不足

这不是模型知识不足，而是证据不足。处理：

- 按含糊/跑题/不会/拒答状态走标准路径；
- 最多两次追问；
- 之后按对应状态封存。

### C. 外部知识是题目本来要测的能力

如果未来要测“开放资料研究能力”，应把它设计为独立题型和独立测量模式，而不是在普通测评中临时启用 Web Search。该模式需另行立项，不属于当前范围。

## 8.2 当前运行时的确定性 fallback

建议每个题目/能力项在入库时配置：

- `knowledge_boundary`；
- `approved_reference_version`；
- `model_uncertainty_action`；
- `fallback_question_id`；
- `human_review_policy`。

运行时遇到模型无法可靠判断时：

```text
第一步：尝试结构化解析/规则校验
第二步：一次中性澄清（不引入外部知识）
第三步：若仍不确定，标记 MODEL_UNCERTAIN
第四步：暂停不利评分，人工介入
第五步：题目无效则 INVALIDATED，否则按人工结果决定是否继续
```

这保证“模型知识不足”不会变成“候选人被扣分”。

# 9. Tools 管理和表单操作

## 9.1 Tool 不是所有 API 的别名

工具应表示“模型或状态机可以请求的一项受控能力”，而不是把每个后端接口都暴露给 LLM。

每个工具应有：

```text
name
version
stage_allowlist
caller_allowlist
input_schema
output_schema
timeout
max_calls
idempotency_policy
audit_policy
failure_fallback
side_effect_level
```

## 9.2 表单相关操作拆分

### Tool A：`render_form`

职责：向前端发出一个经过服务端批准的表单展示事件。

推荐输入：

```json
{
  "form_type": "qualification_gate",
  "schema_id": "qualification_gate_v1",
  "reason_code": "QUALIFICATION_REQUIRED",
  "session_id": "server-bound"
}
```

运行规则：

- 对 `qualification_gate` 等固定表单，优先由代码在进入资格核验阶段时触发；
- LLM 只能提出“需要表单”的建议，不能自行选择任意 `schema_id`；
- 服务端检查该岗位、模型版本和 session 是否允许该表单；
- 同一 session/同一 schema 默认幂等，重复请求不生成多个活动表单；
- 发送事件、schema 版本、展示时间、候选人是否看见都留痕；
- 表单 schema 必须从服务端注册表读取，不能由候选人输入或 LLM 动态拼装。

### Tool B：`get_form_schema`

职责：由前端/服务端根据 form instance 获取严格 schema。

推荐规则：

- 这是读取接口，不一定需要作为 LLM tool；
- 只能读取当前 session 已批准的 form instance；
- 返回字段类型、是否必填、枚举、校验规则、展示文案版本；
- 不返回不必要的内部规则、评分阈值或其他候选人信息；
- schema 版本一旦展示，不得在填写过程中静默改变。

### Tool C：`submit_form`

职责：接收候选人填写的结构化数据。

它不是 LLM 代候选人调用的工具，推荐由前端表单提交 API 执行：

```text
前端填写
→ session/form 所有权校验
→ schema 版本校验
→ 字段类型与枚举校验
→ 幂等键校验
→ 保存原始 payload
→ 生成规范化字段
→ 更新 gate 状态
→ 写入审计事件
```

需要同时保存：

- 原始 payload；
- schema_id/version；
- 规范化结果；
- 校验错误；
- 提交次数；
- 最终 gate 判定；
- 操作时间和会话版本。

### Tool D：`extract_form_facts`

职责：从候选人自由文本或简历中提取可能的结构化事实。

建议默认不在交互测评的关键 gate 路径中自动调用。若启用：

- 只能抽取，不直接通过 gate；
- 原文和抽取结果都保留；
- 每个字段附证据引用和置信状态；
- 候选人或管理员可修正；
- 最终 gate 必须由代码按规则计算；
- 抽取失败或不确定时进入人工复核，不自动判定不合格。

### Tool E：`request_pause`

职责：请求暂停计时或进入无障碍/技术处理状态。

建议：

- 候选人前端按钮和固定命令可以直接触发；
- LLM 只能建议，不得阻止候选人暂停；
- 代码决定是否进入 `PAUSED`、`ACCOMMODATION_HOLD` 或 `TECHNICAL_HOLD`；
- 暂停开始、结束、原因类别和处理人留痕；
- 不保存不必要的医疗细节到普通评分记录。

## 9.3 Tool 调用的统一生命周期

```text
LLM/前端提出请求
→ 代码验证 caller、stage、session、schema、budget
→ 记录 tool_call_requested
→ 执行工具
→ 校验返回结果
→ 记录 tool_call_succeeded / failed
→ 更新领域状态
→ 生成前端事件
```

任何工具失败都必须有预定义 fallback，例如：

- `render_form` 失败：不计入候选人能力分，暂停并重试；
- `get_form_schema` 失败：不允许提交未知结构，暂停并人工处理；
- `submit_form` 网络失败：幂等重试，不重复扣分；
- `extract_form_facts` 不确定：标记待人工确认，不直接影响 gate；
- `request_pause` 失败：前端本地立即停止计时显示并联系人工，服务端补写事件。

# 10. 情绪支持、提示和客观性

## 10.1 只做流程支持，不做情绪能力推断

允许系统响应：

- 候选人明确说紧张、需要停顿或需要重述；
- 候选人请求暂停；
- 候选人表示没有理解题目；
- 发生可观测技术问题。

不允许系统根据：

- 语气；
- 口音；
- 停顿；
- 打字速度；
- 表情或声音特征；
- “看起来不自信”；

推断岗位能力、人格稳定性或录用结论。

## 10.2 标准化支持话术

建议支持话术版本化，并对所有候选人可用：

- “可以稍作停顿后再回答。”
- “我可以重复题目，或用不改变题意的方式重新说明。”
- “如果暂时没有合适经历，可以明确说没有合适经历。”
- “如遇技术或无障碍问题，可以暂停本次测评。”

以下行为不允许作为默认策略：

- “你答得很好”式内容性鼓励；
- 暗示关键词或答案方向；
- 因候选人紧张而降低 rubric；
- 只对特定候选人增加未经批准的帮助；
- 因候选人礼貌、讨好、质疑或不满改变能力分。

## 10.3 支持行为如何进入报告

报告中不必把“紧张”作为能力结论，但应在审计数据中保存：

- 支持事件类型；
- 触发方式；
- 支持模板版本；
- 是否暂停计时；
- 是否改变题目路径；
- 是否获得合理便利；
- 是否影响证据可比性。

候选人可见报告可以只展示“本次测评包含结构化澄清/暂停”等必要信息，敏感流程细节进入受限管理员视图。

- 动态选择解释；
- 评估模型是否过度降级/升级；
- 做 live/final 偏差分析；
- 触发人工复核候选；
- 评估模型谄媚、长度偏差和路径偏差。


前端不得在未完成终局评分时直接生成最终报告。

# 12. 缺失证据、拒答和总分计算

## 12.1 缺失状态与拒答状态不能混为一谈

本轮需要同时保留：

- `REFUSED`：用户明确拒答，本轮意见要求记 0；
- `INSUFFICIENT_EVIDENCE`：已经给过规定机会，仍不足；
- `NOT_ADMINISTERED`：尚未实施/未能实施；
- `INVALIDATED`：题目或系统使该题无效；
- `HUMAN_REVIEW_REQUIRED`：不能自动决定。

这几种状态在报告和聚合中不能只靠 `score = null/0` 区分。

## 12.2 缺证据触发补测和人工复核

本轮确认：

- 缺证据可以触发补测；
- 必须进入人工复核；
- 不能搁置在一个没有后续处理的状态；
- 补测是否仍属于当前 session、还是创建关联补测 session，需要另行确认；
- 补测必须使用同一岗位模型/rubric 版本，或明确记录版本变化。

建议流程：

```text
INSUFFICIENT_EVIDENCE
→ 立即创建补测/人工复核任务
→ 若补测完成：合并证据并重新评分
→ 若补测不可用：按缺失政策计算，同时保留人工复核结论
→ 若题目无效或模型无法判断：INCOMPLETE，不做自动补算
```

## 12.3 缺失项按其他得分比例补算：需要先写成数学定义

用户提出的理解是：

> 先不算缺失项，计算其他项得分比例，再按该比例乘上缺失项的分数，作为缺失项最终分数。

为了避免歧义，建议定义为：

设：

- `O` 为有效评分项集合；
- `M` 为缺失项集合；
- `w_i` 为模型已确认的 item 权重，所有 item 权重总和为 1；
- `s_i` 为有效项归一化得分，范围为 0–1；
- `S_observed = Σ(i∈O) w_i × s_i`；
- `W_observed = Σ(i∈O) w_i`。

则观察项平均能力比例为：

```text
r = S_observed / W_observed
```

每个缺失项的估算分数为：

```text
ŝ_j = r,  j ∈ M
```

最终总分为：

```text
S_final = S_observed + Σ(j∈M) w_j × ŝ_j
        = S_observed + (1 - W_observed) × r
```

如果最终分数换算为百分制：

```text
final_score_100 = 100 × S_final
```

这个公式表达的是：缺失项暂时按候选人在已观察项上的加权平均比例估计，而不是按 0 处理。

### 示例

假设：

```text
有效项权重合计 W_observed = 0.75
有效项加权得分 S_observed = 0.60
r = 0.60 / 0.75 = 0.80
缺失项权重 = 0.25
缺失项估算贡献 = 0.25 × 0.80 = 0.20
最终分 = 0.60 + 0.20 = 0.80
```

### 这个方案的风险

它可能把“未测到”估算成“与已测能力平均”，从而掩盖某个关键 required 能力的缺失。因此建议增加硬条件：

- 如果缺失项属于 required，不能仅靠比例补算后直接通过 gate；
- 如果缺失项权重超过预设上限，必须 `INCOMPLETE + HUMAN_REVIEW_REQUIRED`；
- 如果缺失发生在 `qualification` 或门槛项，不能用平均比例补算；
- 如果缺失原因是 `ITEM_INVALID`、`MODEL_UNCERTAIN` 或系统错误，必须优先修复/补测；
- 补算结果必须显式标注为 `IMPUTED`，不能伪装成真实测量分；
- 报告应同时显示有效覆盖率和补算比例；
- 任何录用/淘汰门槛不能只依赖含有大量补算项的总分。

### 需要用户明确确认的三个问题

1. 该比例补算是否只针对普通能力项，不适用于 required 和 qualification？
2. 如果 required 缺失但补测失败，最终是 `INCOMPLETE` 不出结论，还是允许出带警告的临时报告？
3. 补算后的分数是否允许用于最终录用排序，还是只能用于展示性报告？

当前建议：

- 普通非 gate 项可以补算，但必须标 `IMPUTED`；
- required 缺失、qualification 缺失、题目无效、模型无法判断、系统错误均不能仅靠补算得出最终录用结论；
- 有任何上述状态时，报告可以生成“部分结果”，但最终决策进入人工复核。

# 13. 时间、题数和 Token 管理

## 13.1 本轮确认的硬约束

暂定：

- 全场活跃测评时间不超过 40 分钟；
- 单题活跃处理时间不超过 20 分钟；
- 每题最多两次追问；
- 全局追问总数暂不设额外硬上限；
- 暂不设置全会话 Token 硬预算；
- 暂不设置模型输出 Token 硬上限；
- 但应在配置和状态机中预留接口，后续实验可启用；
- 不实施 24 小时自动删除，数据和日志作为证据保留；
- 网络中断、技术故障和合理便利处理不应消耗有效测评时间。

### 一个需要澄清的表述

“全局追问总数不设限，每次追问最高两次已经兜底”在最坏情况下仍可能产生：

```text
主问题数量 × 每题两次追问
```

在 40 分钟上限下，这实际上仍由全场时间和主问题配额间接限制。建议保留“暂不设独立全局追问上限”，但必须有：

- 40 分钟硬熔断；
- 单题 20 分钟硬熔断；
- 异常状态下的重试次数限制；
- 后续可启用 `global_probe_budget` 配置。

## 13.2 时间状态

建议至少区分：

```text
ACTIVE
PAUSED_CANDIDATE
PAUSED_TECHNICAL
PAUSED_ACCOMMODATION
TIMEOUT_SESSION
TIMEOUT_QUESTION
SCORING_PENDING
INCOMPLETE
COMPLETED
```

计时只累计 `ACTIVE` 时间：

```text
active_elapsed = Σ(active_interval_end - active_interval_start)
```

以下不应累计到候选人有效测评时间：

- 服务端网络重试；
- 题目生成/系统处理等待；
- 技术故障；
- 已批准合理便利暂停；
- 人工处理等待。

## 13.3 到达时间上限时的行为

### 单题达到 20 分钟

1. 停止新增追问；
2. 发送固定收尾话术；
3. 封存当前题；
4. 若已有可评分证据，进入评分；
5. 若没有可评分证据，标 `INSUFFICIENT_EVIDENCE` 或 `INCOMPLETE`；
6. 不因为超时本身额外扣分；
7. 由策略决定是否还有时间进入下一道 required 题。

### 全场达到 40 分钟

1. 停止新增主问题和追问；
2. 封存会话；
3. 未完成项按状态标记；
4. 触发终局评分/人工复核流程；
5. 不把未提问项直接当能力为 0；
6. 如果缺失项符合允许补算条件，显示补算标记，否则输出部分结果。

## 13.4 与上下文管理的关系

本项目现有 P-refine 解决的是：

```text
单次候选人长回答过长
→ 保存原文
→ 生成较短的精炼文本供对话上下文使用
→ 评分时回捞原文
```

它不等于“会话上下文滑动窗口/摘要”。两者解决不同问题：

### P-refine：回答级压缩

- 对象：一条候选人回答；
- 触发：回答超过约 500 的近似 Token 阈值；
- 目的：过滤无关内容、减少单条输入长度；
- 原文：以 hash/原文记录保存；
- 评分：可回捞原文。

### 会话滑动窗口：历史级裁剪

- 对象：多轮完整会话历史；
- 触发：累计上下文接近模型上下文限制或工程预算；
- 目的：避免每轮把所有历史消息重新拼进 interviewer prompt；
- 做法：保留当前题、最近若干轮、结构化 session state 和证据摘要；
- 评分：不应只依赖滑窗摘要，仍回捞原始消息/原始回答。

### 会话摘要：状态级压缩

- 对象：已经完成的题目和能力项证据；
- 目的：让后续导航知道哪些能力已覆盖、哪些题已完成；
- 内容：结构化 evidence coverage、题目状态、难度、追问次数和待补点；
- 不应替代原始证据；
- 摘要版本、生成方式和来源必须留痕。

推荐的 interviewer 输入不是无限历史，而是：

```text
系统/策略约束
+ 当前 model/question/rubric 快照
+ 当前题完整必要上下文
+ 最近若干轮原始或精炼消息
+ 已完成题目的结构化 coverage summary
+ 当前预算和状态
```

这样可以同时满足：

- 候选人原文可审计；
- 对话上下文可控；
- 下一题选择不依赖无限增长的 prompt；
- 后续评分仍可回到原始证据。

## 13.5 暂不设置 Token 上限，但必须留接口

即使本轮不拍数值，也建议保留配置接口：

```text
MAX_CANDIDATE_INPUT_TOKENS = null
MAX_INTERVIEW_CONTEXT_TOKENS = null
MAX_INTERVIEW_OUTPUT_TOKENS = null
MAX_SCORE_OUTPUT_TOKENS = null
```

`null` 表示当前不启用硬限制，不表示永远没有限制。后续应通过真实模型测试、长回答测试、上下文溢出测试和成本监控确定数值。

# 14. 数据库设计：在表达能力和表数量之间取平衡

## 14.1 当前 18 张表不应继续无原则扩张

当前数据库已经有：

- 模块一 8 张；
- 模块二 7 张；
- 模块三 2 张；
- 模块四 1 张。

本轮不建议为了每个状态、每个工具、每个难度、每个报告片段都新建表。优先原则：

1. 会被独立查询、排序、约束、聚合的事实使用列；
2. 版本快照和不稳定扩展属性使用 JSON；
3. 一对多且需要独立生命周期的实体才新建表；
4. 审计事件应优先复用现有 trace/message/assessment_question，只有查询和保留需求明确时才新建事件表；
5. 关键外键关系不能只藏在 JSON 或字符串 `ref_id` 中。

## 14.2 推荐的最小增量模型

### 继续使用并扩展 `question_bank`

用于岗位题库静态资产：

- `position_id`；

## 14.3 是否需要新增 `assessment_state_event`

有两种方案：

### 方案 A：不新增表，分散写入现有表

- 题目状态写 `assessment_question`；
- 回答状态写 `assessment_message`；
- 评分状态写 `question_score`；
- LLM 调用写 `llm_trace`。

优点：少一张表。缺点：无法完整表达没有对应 message/question 的状态转移，例如暂停、重试、人工介入、预算变化和会话级异常。

### 方案 B：新增通用 `assessment_state_event`（推荐长期方案）

一张表承载所有会话状态事件：

```text
id
session_id
question_id nullable
event_type
from_state
to_state
actor_type（system/llm/candidate/admin）
policy_version
payload_json
created_at
idempotency_key
```

优点：

- 能统一审计状态机；
- 支持暂停、恢复、重试、降级、升级、工具和人工处理；
- 不需要为每种状态再建表。

缺点：

- 表会快速增长；
- payload_json 需要治理；
- 查询关键业务状态仍不能只依赖事件回放，当前状态应保留在主表列中。

**当前建议：**先不立刻新增，先用现有表扩展列验证状态机；如果事件种类和审计查询确实复杂，再新增一张通用事件表，而不是新增多张专用表。

## 14.4 是否需要 `question_bank_relation`

如果 chain 和等值关系只是单父链，可以放在 `question_bank.chain_id/chain_seq/equivalence_group_id`。如果未来出现：

- 一个题有多个后继；
- 题目之间有条件分支；
- 等值关系不是简单分组；
- 备用题有独立优先级和适用条件；

再考虑一张关系表：

```text
question_bank_relation
from_question_id
to_question_id
relation_type（chain_next/equivalent/fallback/branch）
condition_json
priority
version
```

当前建议：

- 第一阶段使用字段和 JSON 表达简单 chain；
- 不为尚未出现的多分支关系提前建表；
- 一旦关系不再是单链/分组，立即停止继续堆 JSON，改用关系表。

## 14.5 `user_profile`、表单和会话关系

本轮不重新拍板 `user_profile` 独立表还是扩展 `user`。但需要避免把候选人长期事实与某次 session 的回答混在一起：

- 跨 session 的稳定资料：进入 profile 领域；
- 本次岗位特定的表单：进入 `form_submission`；
- 本次自由回答：进入 `assessment_message/context_raw`；
- 本次 gate 判定：进入 session/报告快照；
- 评分不得直接读取后来修改的 profile 覆盖当时证据。

表单 schema 不能只存在前端 `FormCard`，应有版本化注册来源。是否建立独立 `form_schema` 表，需要根据表单数量和管理员编辑需求决定：

- 只有少量固定 schema：代码常量 + 版本快照即可；
- 需要管理员动态配置：再建 `form_schema`/`form_definition` 表；
- 不建议为了当前一两个固定表单过早建复杂表单设计器。

## 14.6 必须增加的数据库约束

无论最终表数如何，至少需要考虑：

- session/question/message/report 的所有权或可追溯外键；
- 同一 session 同一 question 的幂等提交；
- 同一题追问计数不能并发超限；
- question_bank 题目版本不可被已开始 session 静默修改；
- `equivalence_group_id` 只能关联相同批准模型范围的题；
- `score_state` 与 `score_value` 组合合法性；
- `REFUSED` 可以有 0，但 `INSUFFICIENT_EVIDENCE` 不应自动变成 0；
- `INVALIDATED` 不进入普通聚合分母；
- `is_imputed=true` 必须有补算原因和来源；
- tool call 幂等键唯一；
- raw answer hash 与原文记录一致；
- 任何状态迁移有时间和版本记录。

# 15. 报告与人工复核的新增要求

报告不应只展示一个总分，而应至少区分：

```text
final_score
observed_coverage
imputed_coverage
refused_items
insufficient_evidence_items
not_administered_items
invalidated_items
human_review_status
difficulty_path_summary
scaffold_events
process_events
```

候选人可见内容与管理员审计内容可以分层：

### 候选人可见

- 能力项分数或区间；
- 有效证据引用；
- 哪些项目因未完成/缺证据无法给出确定结论；
- 申诉入口；
- 必要的测评异常说明。

### 管理员/审计可见

- 完整状态轨迹；
- 追问和脚手架事件；
- 降/升难度原因；
- 模型不确定性；
- 工具调用；
- 原始回答和 hash；
- 人工覆盖；
- 补算过程；
- 版本快照。

不得让报告 LLM 自由生成没有证据的优势、短板或建议。所有自然语言内容都应从已确认的结构化事实和证据生成。

# 16. 当前明确发现的实现差距（不代表本轮授权修复）

以下是本轮讨论对应的代码差距，先记录，不实施：

1. `question_selection.py` 在创建 session 时一次性按固定配额选题，尚未实现逐轮动态策略；
2. 当前 `assessment_question` 主要表示预排队列，尚未表示动态激活和选择原因；
3. `score_live` 仍参与现有评分合成，需改为仅导航；
4. `finish` 在非末题时缺少强制护栏；
5. 过程状态没有覆盖拒答、不会、跑题、攻击、模型不确定、题目无效等完整枚举；
6. mock 面试官仍主要按回答长度作判断；
7. 当前没有动态难度状态、升级/降级路径和最高难度覆盖计划；
8. 当前没有严格的等值题字段和测量等值标记；
9. 表单缺少完整 schema 获取、严格校验、幂等提交和固定触发策略；
10. 当前没有 Web Search，也不计划加入；
11. 网络重试、计时暂停/恢复和系统错误不扣分的机制不完整；
12. `assessment` 资源所有权校验仍需补齐；
13. 正常前端流程仍未自动执行终局评分后再生成报告；
14. interviewer 上下文仍可能拼接全量历史，尚未有会话滑窗/结构化摘要；
15. trace 与 message/question/report 主要是间接关联，严格外键/事件链不完整；
16. 缺失项、拒答、无效题和补算状态尚未在聚合器中完整区分；
17. `assessment_session` 尚无 40 分钟活跃计时和单题 20 分钟硬约束；
18. 报告任务失败、人工复核和补测任务的状态/可观测性不足。

# 17. 本轮需要逐项确认的问题

为了避免把复杂问题一次性混成一个“同意/不同意”，建议按以下顺序确认。

## A. 题库和题目关系

1. `qualification` 是否完全走结构化表单、不占普通主问题配额？
2. `experience` 是否允许“表单事实 + 行为题”双通道？
3. 一个题是否只能绑定一个主评分能力项？
4. 当前阶段采用动态实例化方案 A，还是候选集合方案 B？
5. chain 第一阶段是否只支持单链字段，不提前建立关系表？

## B. 选题和配额

6. required 能力未覆盖但大类配额已满时，是否按“回收非 required 配额 → 仍不足则 incomplete + human review”处理？
7. 类目顺序是否由岗位级 `category_plan` 决定，而不是固定硬编码顺序？
8. 大类/子类配额是否只用于主问题数量，不直接再乘入最终分？
9. 是否接受“题目数量是测量资源，难度是测量路径，item.weight 才是最终业务权重”的原则？

## C. Chain、追问和等值

10. 是否接受优先级：流程安全 → 当前 followup → required 覆盖 → chain → 难度 → 剩余配额/题目质量？
11. chain 是否允许因 required 覆盖、时间、拒答或证据已充分而提前终止？
12. 等值备用题是否要求 `measurement_equivalent=true`，而不只检查字段一致？
13. 等值题是否必须连 `difficulty` 和 `chain_role` 也一致？

## D. 难度和最终分

14. 是否确认静态难度不作为第三层最终权重？
15. 最高难度题的要求采用“岗位级最小覆盖计划”，而不是全局固定题数？
16. 最高难度覆盖更接近：每个 required 能力一次、固定 session 数量，还是仅对有机会达到高等级的能力项？
17. 是否接受每级至少一次有效证据、每次最多升一级、低→中一次充分证据、中→高一次充分或两次稳定证据？
18. 连续答错两题是否严格限定同一 item、同一 difficulty、均为有效作答？

## E. 状态、拒答和缺失

19. 含糊的中性澄清是否正式定义为一次 followup？
20. “不会/想不到”是否采用“记录脚手架 + 不固定扣分；只有 rubric 明确要求独立作答时限制最高等级”的策略？
21. 明确拒答是否采用 `score_value=0 + score_state=REFUSED`，而不是把量表整体改为 0–5？
22. 拒答是否不提供测评末尾补答机会，只允许当前题一次确认后跳过？
23. 网络中断是否采用幂等重试、暂停计时、恢复失败人工介入，并且绝不扣分？
24. `MODEL_UNCERTAIN` 和 `ITEM_INVALID` 是否都暂停不利评分并进入人工处理，但后者将题目从正常分母剔除？
25. 缺证据补测后仍失败时，是否按“普通非 gate 项允许标记补算；required/qualification/系统错误/题目无效不允许仅靠补算出最终结论”处理？
26. 缺失项补算是否采用加权观察比例公式，并把结果标记为 `IMPUTED`？
27. required 缺失时是否只出部分报告并进入人工复核，不允许自动通过/淘汰？

## F. 情绪和 Tools

28. 是否接受只提供标准化流程支持、不做情绪识别或情绪能力推断？
29. `render_form` 是否代码触发为主，LLM 只能提出请求？
30. `submit_form` 是否完全由前端/服务端执行，不作为 LLM 代调用工具？
31. 是否保留 `get_form_schema`、`extract_form_facts`、`request_pause` 的分离职责？
32. 是否接受 Web Search 完全不进入当前正式测评范围？

## G. 时间、上下文和数据库

33. 是否确认全场活跃时间 40 分钟、单题活跃时间 20 分钟？
34. 是否确认暂不设独立全局追问上限，但保留全局预算接口和时间硬熔断？
35. 是否确认暂不启用 Token 硬上限，但预留配置接口？
36. 是否确认不做 24 小时自动删除，数据/日志保留为证据？
37. 是否接受 P-refine 继续作为“回答级压缩”，另行增加“会话滑窗 + 结构化状态摘要”？
38. 是否先扩展现有三张测评核心表（`question_bank`、`assessment_question`、`assessment_message`/`question_score`），暂不新增多张专用状态表？
39. 是否暂不新增通用 `assessment_state_event`，等状态机运行证据表明需要后再加？
40. 是否接受“逻辑树、物理扁平表”的题库数据库方案？

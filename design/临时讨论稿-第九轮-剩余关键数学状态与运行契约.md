# 2. 任务执行：BackgroundTasks 与重启恢复

## 2.1 已确认

- 目标是演示上线、单机、单实例；
- 接受单进程 FastAPI `BackgroundTasks`；
- 同时要求进程重启后任务可恢复；
- 任务失败要向用户显示可理解的失败状态；
- 任务重试覆盖原任务；
- 不允许部分题库或部分评分直接发布。

## 2.2 矛盾

当前 FastAPI `BackgroundTasks` 只保存内存中的待执行函数。进程重启后，尚未开始或执行中的任务不会自动恢复。因此：

```text
仅使用 BackgroundTasks
≠
重启可恢复
```

## 2.3 推荐收敛方案：持久化 job 表 + 单进程执行

在不引入外部队列的前提下，建议采用最小可恢复方案：

```text
业务请求
→ 同事务写入 job(status=QUEUED)
→ BackgroundTasks 执行 job
→ job 状态和业务结果同事务更新
```

启动时扫描：

```text
QUEUED                  → 重新执行
RUNNING 且 lease 已过期 → 标记可重试并重新执行
SUCCEEDED/FAILED        → 不重复执行
```

建议 job 状态：

```text
QUEUED
RUNNING
SUCCEEDED
FAILED
CANCELLED
```

建议最小字段：

```text
id
task_type
resource_type
resource_id
status
idempotency_key
attempt_count
last_error
created_at
started_at
finished_at
lease_until
```

任务函数必须幂等；重复执行只能得到同一个最终结果，不能重复插入题目、评分或报告。

这仍然是单进程演示架构，不承诺高并发、高可用或多副本；但可以满足“重启后恢复未完成任务”的最低要求。

## 2.4 仍需用户确认的重大问题

是否接受：

> **保留单进程 BackgroundTasks 作为执行器，同时新增最小持久化 job 状态、启动扫描和幂等恢复机制；不引入外部队列。**

如果不接受，则必须在“演示上线”范围内放弃重启恢复要求，或者引入超出当前范围的外部队列。

# 3. 难度与 1–5 能力等级

## 3.1 已确认

- 普通路径为 `easy → medium → hard`；
- 难度不直接加权；
- 每题有 `observable_level_max`；
- hard 是有条件阶段；
- hard 强证据可支持高等级；
- 低难度题不能支撑超过自身上限的等级；
- 多题 item 聚合采用证据裁决，冲突时取低值。

## 3.2 推荐的非加权映射

建议先把题目能力等级上限作为 rubric 配置，而不是把难度换算成分数倍数：

| 普通难度 | 建议默认可观测等级上限 | 说明 |
|---|---:|---|
| easy | 3 | 可验证基础概念、基本方法和简单场景 |
| medium | 4 | 可验证独立处理复杂场景和权衡 |
| hard | 5 | 可验证高复杂度、边界条件、系统性决策 |

这是一组**默认映射候选**，不是所有岗位必须使用的固定值。题目/rubric 可以配置更低上限，但不应超过所属难度的默认上限，除非模型版本明确批准例外。

最终 item 分仍是 1–5 的能力等级：

```text
局部评分 = rubric 评分
局部最高等级 = min(question.observable_level_max, rubric_allowed_level)
item_final_level = 证据裁决后的最高可信等级
```

`required_level` 或 `target_level` 只影响是否有必要开放更高难度和是否达到岗位要求，不额外改变分数权重。

## 3.3 建议的 hard 开放条件

```text
item.target_level > medium_max
且
前序普通测量达到进入 hard 的路径条件
且
存在合法 hard 题
```

如果 `target_level` 不需要 hard 才能观察，则不必问 hard。

## 3.4 仍需确认

这里唯一可能影响整个评分模型的数值决定是：

1. 是否接受 easy/medium/hard 默认上限为 `3/4/5`？
2. 是否允许单个 rubric 将某一难度的上限配置得低于默认值？
3. `required_level` 是只决定路径，还是同时作为报告中的达标比较值？

我的推荐是接受上述三点：

- 默认上限 `3/4/5`；
- rubric 可以下调上限；
- `required_level` 用于达标比较和路径，不改变 item.weight 或局部评分。

# 4. 拒答特殊观察值与 item 聚合

## 4.1 已确认

- 明确拒答：`score_value=0`、`score_state=REFUSED`；
- 拒答是特殊观察值，不是能力量表 1 分；
- 后续有效回答可以改变 item 最终能力等级；
- 拒答事件永久保留。

## 4.2 推荐的记录和聚合分层

为了同时满足“拒答按 0 留痕”和“后续有效回答可改变最终等级”，建议分成两个结果：

```text
item_behavior_summary
  refusal_count
  refusal_positions

item_ability_result
  score_value
  score_state
  evidence_summary
```

拒答记录为一次特殊观察值，但不让它机械地永久覆盖后来有效能力证据。若同一 item 既有拒答又有有效回答：

1. `refusal_count` 增加；
2. 拒答 observation 保留为 0；
3. 后续有效回答进入能力证据裁决；
4. 最终 item 能力等级可以由有效回答决定；
5. 报告同时展示拒答行为，不把最终能力等级解释为“拒答等于 1 分”。

## 4.3 仍有一个必须明确的数学选择

“拒答是特殊观察值”仍有两种不同含义：

### 方案 R1：拒答 0 进入能力数值聚合

例如有效观察为 3、4，拒答为 0，按固定规则共同聚合。

优点：拒答确实影响 item 数值。  
风险：一次拒答可能对后续有效证据造成过大影响；0 与 1–5 量表的统计语义不同。

### 方案 R2：拒答 0 只进入行为/完整度聚合，不直接进入能力等级聚合

最终能力等级由有效证据决定，但拒答会降低完整度、增加风险提示，并可影响报告状态。

优点：保持能力量表 1–5 的解释一致，也允许后续有效回答改变能力等级。  
风险：需要明确“拒答按 0 参与 item 聚合”的既有表述应如何解释。

**需要用户明确：**这里的“参与该项聚合”是指 R1 的能力数值聚合，还是 R2 的 item 结果/行为完整度聚合？

在没有明确前，不能写出最终数学公式。

# 5. 综合题与普通题的最终合并

## 5.1 已确认

- 综合题一题多 item，按 `(question_id, item_id)` 独立评分；
- 综合题不使用整体分参与最终总分；
- 综合题不能替代普通题最低测量；
- 综合题可以作为 item 的最高等级证据；
- 共享 span 必须显式标记；
- 整体无效时所有绑定 item 的综合结果无效。

## 5.2 推荐的 item 级合并规则

普通题和综合题都先生成 item 级测量记录：

```text
ordinary_measurements(item_id, question_id, level, evidence)
integrated_measurements(item_id, question_id, level, evidence)
```

然后在 item 级统一裁决：

1. 普通题至少有一次有效普通测量机会；
2. 综合题结果不能替代该最低普通测量；
3. 所有有效测量按 rubric、覆盖、稳定性和冲突进行证据裁决；
4. 不按“普通题/综合题”额外加权；
5. 不按题目数量重复乘 `item.weight`；
6. 同一证据 span 即使被多个 item 引用，也不能产生相同分数的自动复制；
7. 重大冲突取低值，并保留人工复核标记。

因此建议：

```text
item_final_level
  = adjudicate(ordinary_measurements + integrated_measurements)
```

其中 `adjudicate` 不是简单平均，而是受测量资格、证据完整性、版本、覆盖和冲突规则约束的代码裁决。

## 5.3 推荐的综合题第二题决策表

| 第一题结果 | 尚有合法联合 target | 第二题可用 | 建议动作 |
|---|---:|---:|---|
| 正常且覆盖充分 | 否 | 任意 | 结束综合阶段 |
| 正常但覆盖不足 | 是 | 是 | 激活第二题 |
| 整体无效 | 任意 | 是 | 激活第二题 |
| 整体无效 | 任意 | 否 | 结束并进入人工/不完整 |
| 局部 item 缺证据 | 是 | 是 | 激活第二题 |
| session 全场超时 | 任意 | 任意 | 不再激活 |

第二题仍受最多两题、题库版本匹配和 session 状态约束。

## 5.4 仍需确认

主要需要确认的是：

1. 是否接受普通题和综合题先转成统一 item 测量记录，再统一证据裁决？
2. 共享 span 是否只影响证据解释，不额外产生分数折扣？
3. 综合题局部结果和普通题发生冲突时，是否继续按较低值处理？

我的推荐是全部接受。

# 6. `assessment_state_event` 和 `trace_link` 最终契约候选

## 6.1 推荐字段

### `assessment_state_event`

```text
id
session_id
sequence_no
assessment_question_id nullable
assessment_message_id nullable
event_type
from_state nullable
to_state nullable
actor_type
actor_id nullable
request_id nullable
idempotency_key nullable
policy_version nullable
model_version nullable
question_bank_version nullable
correlation_id nullable
causation_event_id nullable
payload_json
created_at
```

建议：

- `(session_id, sequence_no)` 唯一；
- 幂等键按 `session_id + endpoint + idempotency_key` 作用；
- 状态迁移事件必须有 from/to；动作事件可以为空；
- 旧事件不可修改/删除；
- 当前快照和事件在同一事务更新；
- LLM 调用不持有长事务；
- 回放只用于恢复、审计、修复和测试。

### `trace_link`

```text
id
trace_id
entity_type
entity_id
link_role
created_at
```

建议唯一约束：

```text
(trace_id, entity_type, entity_id, link_role)
```

`link_role` 用于区分：

```text
input
output
caused_by
scored
reported
source
```

## 6.2 推荐事件分组

```text
SESSION_*
QUESTION_*
MESSAGE_*
OBSERVATION_*
POLICY_*
CONTROL_*
FORM_*
TASK_*
REVIEW_*
TOOL_*
```

具体事件名称应在实现前形成枚举表，并为每个枚举注明：

- 必填字段；
- 是否改变状态；
- 是否计入题量；
- 是否计入计时；
- 是否需要人工处理。

## 6.3 仍需确认

建议确认是否接受：

1. `sequence_no` 作为 session 内单调递增序号；
2. `correlation_id/causation_event_id` 一并加入；
3. `trace_link` 使用统一关联表而不是各业务表增加多个 trace 外键；
4. 事件和 trace link 均采用追加式记录。

# 7. 计时、断线、无活动和 abandoned

## 7.1 已确认

- 全场从候选人确认开始且首题成功激活计时；
- 单题从题目成功激活并发送计时；
- followup 共用单题计时器；
- 页面关闭默认不暂停；
- 显式 pause/技术状态才暂停；
- 所有暂停类型不计入 40 分钟；
- 单题超时封存并继续；
- 全场超时停止新增题并进入评分/收尾；
- 服务端权威。

## 7.2 推荐的服务端计时表达

不要只保存客户端提交的开始和结束时间；建议按事件累计有效区间：

```text
session_time_interval
  session_id
  interval_type: active | paused
  reason nullable
  started_at_server
  ended_at_server
```

如果不新增 interval 表，也可以把区间作为事件 payload 保存，但必须由服务端计算：

```text
active_elapsed = Σ(active intervals)
question_active_elapsed = Σ(question active intervals)
```

客户端传来的时间只用于展示，不参与裁决。

## 7.3 断线和无活动候选规则

建议区分：

```text
短暂断线：保留当前题/待处理请求，不自动暂停
显式暂停：停止有效计时
长时间无活动：标记 session 需要恢复或人工处理
```

`abandoned` 不应仅由页面关闭立即产生。建议由服务端在后续请求或启动扫描时判断，并记录：

```text
ABANDONMENT_CHECKED
ABANDONED
RESUMED_AFTER_ABANDONED
```

## 7.4 仍需确认

1. “长时间无活动”是否需要一个具体时长？
2. 是否继续保留旧设计中的 24 小时 abandoned 概念，但不删除证据？
3. session 标记 `ABANDONED` 后是否允许候选人恢复，还是只能人工处理？

这些问题会决定恢复接口和计时规则，不能完全由实现侧自行假设。

# 8. 人工复核与报告发布

## 8.1 已确认

- 异议反馈不改变评分；
- 人工复核必须能查看证据；
- 题库/模型失效或不可用时需要二次人工确认；
- required 缺失产生临时报告和人工复核；
- 报告不能在终局评分失败时作为正常报告发布。

## 8.2 推荐的报告状态

```text
GENERATING
PROVISIONAL
HUMAN_REVIEW_REQUIRED
READY
PUBLISHED
FAILED
```

建议 `PROVISIONAL` 和 `HUMAN_REVIEW_REQUIRED` 可以同时表达：

- `report_status`：当前报告内容是否为临时版本；
- `review_status`：是否等待人工处理。

## 8.3 推荐发布流程

```text
评分完成
→ 聚合和证据校验
→ 生成临时/正式报告
→ 若有人工复核要求，保持 PROVISIONAL
→ 管理员查看并确认“报告可发布”
→ PUBLISHED
```

人工复核不修改原始评分，也不自动改分。若人工发现题库/模型失效，需要二次人工确认；必要时由管理员决定是否废弃当前测量并重新安排后续处理。

## 8.4 仍需确认

1. required 缺失的临时报告是否允许管理员直接发布为 `PUBLISHED`，还是只能保持 `PROVISIONAL`？
2. 人工复核完成后是否需要管理员明确点击“发布”，还是复核完成自动发布？
3. 候选人异议是否只保留反馈记录，且永远不触发报告重算？

我的建议是：

- required 缺失只能保持 `PROVISIONAL`，除非人工明确确认缺失不影响本次报告用途；
- 采用明确的管理员发布动作；
- 异议默认不重算、不改分，只作为反馈和后续质量数据。

- **日期**：2026-09-08
- **性质**：事故复盘登记稿（ fixes already merged，SSOT 变更日志待授权写入）
- **关联**：会话 `sess_75f9c0b382d8`（2026-09-08 完赛实测）两轮复现；分支 `fix/report-guard`（adee478）、`fix/report-regen-button`（dd91d1a）、`fix/report-llmlock`（e31bd03），合入 88f3d0c / 7806fb7 / 06c926a

## 一、事故时间线（两轮复现的共同形态）

用户做完所有题目、提交最后一个资格核验表单后：

1. **第一轮（08:33–08:37）**：页面显示「本场测评已完成」约 99 秒（无任何跳转——用户手动刷新才被 `load()` 重定向）；报告页轮询 2 分钟超时显示「生成超时」。后台：评分链 10/10 为成功入库（含事故会话 26 行 question_score / TASK_SUCCEEDED）；`generate_report` 静默死亡——`call_type='report'` 的 llm_trace 全库 0 条甚至没有失败 trace、无 FAILED 行、无 TASK_FAILED 事件，当时 `except: pass` 兜底不落任何痕迹（写行/写事件兜底本身失败也被吞）。
2. **第二轮（13:16–13:17，修复 1–3 合入、重启后接管重试）**：接管 POST 202 成功（v2 新行 + 重新入队）；评分快速通过；`generate_report` 同一位置再次死亡。这次看门狗留下了关键证据（stderr）：

   `[report-task] session=sess_… FAILED 行/TASK_FAILED 事件写入失败：OperationalError('database is locked')`

   且此后全进程所有写库请求 500（管理端聚合 rerun 亦 ASGI 500），锁持续泄漏至进程重启。

## 二、根因链（全部实证，无推测环节）

1. **死锁本体（方案 A 修复对象）**：`generate_report` 单连接跑全程；`_detect_bad_case_divergence(conn, …)` 对双分背离行（本会话 c_12ad63b093e5：live=5 / final=3，差值恰达 `BAD_CASE_DIVERGENCE_THRESHOLD=2`）INSERT `bad_case_candidate`，**按设计不提交**（等调用方末尾 commit）→ SQLite RESERVED 写锁被该连接持有 → 随后 `call_llm_json('report')` 的 `_record_trace` 开**自己的新连接**写入 `llm_trace` → 被锁挡住 5s 超时 `database is locked` → `call_llm_json` 的 except 再落失败 trace 同样 locked → 异常从 except 块本身抛出 → 任务层写 FAILED 行（新连接）同样 locked → 任务死掉且 `generate_report` 的连接**从未 rollback/close，锁泄漏至进程重启**。最小复现已验证：conn A 未提交写 → conn B INSERT 必失败，A rollback 后立即恢复。
   - 这是会话数据的**确定性复现**（有背离行 → 必死锁），非偶发。
2. **表单完赛收尾缺口（修复 1）**：`submit-v2` 响应含 `action:'finish'`（池耗尽完赛），但 FormCard 丢弃响应体只 `emit('submitted')`，Chat 的 `onFormSubmitted` 只 `refreshSession()` —— 无跳转代码，页面停在「本场测评已完成」直至手动刷新（99 秒来源）。答题完赛路径（SSE onDone finish 分支）本就有跳转，两路径不对称。
3. **GENERATING 毒化（修复 2）**：`request_report` 对 GENERATING 一律 409，无超龄判定 —— 后台任务死亡后占位行永久卡死重试入口。用户体验为「重新生成永远无效」。
4. **「重新生成」按钮接线错误（修复 2 前端半边）**：按钮 `@click="bootstrap"`，而 bootstrap 只 GET（拿到 GENERATING 就轮询、拿到 FAILED 就显示失败），只有 GET 404 才 POST —— 卡死 GENERATING / FAILED 行两种形态下按钮永远发不出 POST，上述接管逻辑 UI 永远够不到。
5. **兜底静默（修复 3）**：`_generate_report_task` 的 `except Exception: pass` —— 任何失败形态（含本次锁死）都无痕迹，事故无法尸检（第一轮零证据）。且无超时看门狗，挂起任务与死任务无法区分。

## 三、修复清单（全部已合入 feature/m5-assessment）

| # | 修复 | 内容 | 裁决 |
|---|---|---|---|
| 1 | 表单完赛跳转 | FormCard 透传 submit-v2 响应；Chat 按 `action='finish'` 与答题完赛路径对齐跳报告页 | 直接做（用户） |
| 2 | GENERATING 超龄接管 | `_STALE_GENERATING_SECONDS = 60*60`：最新 GENERATING 行行龄超 60 分钟视为死任务，POST 放行版本化接管（不覆盖旧行）；解析失败保守 409 | **60 分钟 = 死任务，用户裁决** |
| 2b | 重新生成按钮 | `regenerate()` 真正发 POST，409 分支分派（REPORT_GENERATING 并入轮询 / ALREADY_GENERATED 重取 / SESSION_NOT_COMPLETED 文案） | 实施中发现缺口，联动修复 |
| 3 | 看门狗 + 非静默兜底 | `_generate_report_task` 改包装器：内层线程跑串行链，`join(60min)` 超时写 TASK_FAILED + FAILED 行（文案注明超时）；兜底写行失败至少打 stderr；**60 分钟与修复 2 共用常量** | 直接做（用户） |
| 4 | 写锁死锁（方案 A） | `_detect_bad_case_divergence` 改**独立小事务**（自开连接、自 commit/close，不借主 conn）→ 进 LLM 调用前写锁已释放；`generate_report` 全函数 `try/finally conn.rollback()` 兜底（正常路径已 commit → no-op；异常路径清未决事务放锁） | **方案 A，用户裁决**（对照方案 B busy_timeout 治标不治本，否决） |

红绿验证：修复 4 回归测试在旧代码上精确复现 `database is locked`（含全进程锁泄漏连带伤害）；修复后全绿。全量 347 passed。子代理核查全部 9 个 `call_llm_json` 调用点：其余 8 处均已有「先 commit 再进 LLM」纪律（docstring 明载），本处为唯一违例。

## 四、不修 / 边缘观察

- `llm.py _record_trace` 每次调用新开连接不 close（靠 GC）：事故期每个超时连接叠 5s 等待。非缺陷，连接生命周期治理另行考虑。
- 事故期间（21:17 起至重启）管理端写库请求 500 属锁泄漏辐射，非独立事故。
- 本轮四项均为 bug 修复与既定语义的工程实现（60 分钟阈值经用户裁决），不涉及模块范围 / 接口契约增改 → 变更日志单条合并登记，正文仅 §21.1 增补死任务接管与看门狗语义，其余修复以日志条目承载。
- 模块二/三分册同步摘录：另行收口（沿用既有先例）。

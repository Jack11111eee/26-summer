## 一、背景与现状（裁决依据）

同岗位 confirm 新模型版本后生成新题库，旧版题库行的处置现状：

1. **写入侧**：题库生成全部为 `INSERT`（携新 model_id + model_version），无任何代码
   路径 UPDATE/DELETE 旧版行——旧库 append-only 保留是事实要求（`assessment_question.
   bank_question_id` 外键 + 在途/历史会话追溯链依赖行存在，评分/报告/追问 join 均按
   question_id 直连、不过滤 status）。
2. **`question_bank.status` 现为死字段**：全库 516 行均为写入时默认 `'active'`，
   无代码路径改变它；列上无 CHECK 约束（N11 风格——枚举代码校验）。且现状已有
   第三种值先例：eval 工具占位题写 `status='eval_seed'`（隔离态，见下文第五节）。
3. **旧版行事实上休眠**：选题池（`_load_candidate_rows`）、readiness 计数、管理端
   题量计数均按 model_id + model_version 绑定（D-50），旧版行归不归档都不影响新会话；
   唯一真实风险是**在途会话的动态派题**——会话锚定创建时的模型版本，若旧版题在会话
   进行中被标非 active，`_load_candidate_rows` 查空，考试断粮。
4. **当前库实况**（2026-09-08）：SLAM 算法两代 confirmed（v3 / v5 各 258 题），
   v3 已被 v5 取代但无标记；一个在途会话 `sess_27101dbe8816` 仍挂 v3（5 题实例、
   4 题已答、动态派题中）。即：本设计真实要解决的就是这个组合——标记
   已被取代的旧版题库，同时不打断在途会话。
5. **管理端可见性缺口**：§9.5 题库状态页的题量计数（`question_count`）、题目表、
   覆盖统计全部 active-only——若归档落地而计数口径不改，旧版行在列表显示 0 题、
   详情页一片空白，形似「题丢了」。

## 二、设计裁决（用户 2026-09-08 逐项确认）

### R1 归档语义与值名

- `question_bank.status` 增枚举值 **`'archived'`**，语义：**被同岗位更新 confirmed
  模型的题库取代、保留行以支撑追溯**。选 archived 不用 inactive——position 的
  inactive 是「岗位下架」，此处是「版本取代」，词义域分开避免概念混用。
- **不影响任何 join 语义**：评分、报告、追问、答卷展示、计时等全部按
  `bank_question_id` 直连、不读 status——已归档版本的答卷、评分、报告、追溯不受
  任何影响（登记为 by-design 不变量，实施含回归测试守恒）。
- **不需要 DB 迁移**：列无 CHECK，纯代码级枚举扩展（N11 风格）。

### R2 归档单元与谓词

- 归档单元 = **模型（model_id）**：按被取代模型的题库行整体（scope 无关——
  生成侧 2026-09-07 起只有 scope='position'，historical general 行按 model_id 集
  合覆盖时不特判）。
- 是否「已被取代」的判定基准：同岗位存在**更新的 confirmed 模型**（version 更高；
  同 version 可能有多行时取 rowid 最新，与 `_latest_confirmed_model` 口径一致）。
- 归档目标行：`status='active'` 且 `model_id` ∈（该岗位全部 confirmed 模型 −
  最新行）。
- **豁免在途**：`model_id` 被 `status='in_progress'` 会话引用时该模型行不动。
  （豁免范围只认 in_progress：completed/abandoned 会话的追溯靠 join 语义，
  R1 已论证不需要 active。）

### R3 触发点（两处，同一 helper）

`archive_superseded_banks(position_id)`（services 层单点实现，内部自取最新
confirmed 作 keep）：

1. **confirm_model 事务内**（新 confirm 即归档旧版）：归档不依赖新库生成结果——
   新会话可用性由模型绑定决定（readiness 按新 task 行判 GENERATING/INCOMPLETE），
   归档与否不改变「新会话开不了考」的判定，故无「生成成功才归档」的异步耦合。
2. **会话到终态时补刀**：completed / abandoned 落库处顺带执行——豁免在途模型在
   其最后一个 in_progress 会话结束后即归档。

不在触发点清单内的写路径一律不写 archived：retry 幂等查重只认 active 行，
已归档模型重跑会"复活"出新的 active 行（功能上新会话仍选不到，但污染标记与
管理端计数）→ 由 R4 堵住。

### R4 retry 护栏

`POST /admin/question-bank-tasks/{task_id}/retry`（CR-02）对 FAILED 任务无校验重跑；
**已归档所属模型（即：该岗位已存在更新 confirmed 模型）的任务 retry 时返回 409**
（响应体给出冲突原因）。FAILED 的最新版任务 retry 路径不变。

### R5 管理端（§9.5 端点契约扩展）

| 端点 | 变更 |
|---|---|
| `GET /admin/question-bank-tasks` | 列表行增派生字段 `bank_status`（active/archived——按该 task 行 model 的最新题库行状态派生）；增 `bank_status` 过滤参数（与既有 status 过滤并列）；`question_count` 旁增 `archived_count`（该模型 archived 行计数），避免归档后主计数归零显见「题丢失」 |
| `GET /admin/question-bank-tasks/{task_id}` | 覆盖统计（coverage）：该模型已整体归档时按「不过滤 status」口径重算（归档版本的覆盖照常可看） |
| `GET /admin/question-bank-tasks/{task_id}/questions` | 该模型已整体归档时 queryset 放开 status 过滤（active+archived 全量分页），题目行增 status 列输出 |

「已整体归档时后端自动放开」（用户裁决口径 3）：不引入手动 toggle 的 UI 状态，
归档版本打开详情 = 直接看到全量历史题目。

### R6 前端（web-next QbankStatus.vue）

- 列表行：显示 bank_status 标签（使用中 / 已归档——已归档行弱化视觉样式）；
  `question_count` 旁并列展示 archived_count。
- 筛选器：`status_filter`（任务状态）旁增 `bank_status` 筛选（全部 / 使用中 /
  已归档），与现有 select 同款式。
- 详情/题目表：无新增交互——归档版本打开即见全量（后端放开），题目表加 status
  列（值仅 active/archived，直译）。

### R7 代码内常量与文案登记

- 枚举值 `status ∈ {'active','archived', <eval 既有 'eval_seed'>}`（N11 代码校验，
  不加 DB CHECK）。
- 管理端文案：「使用中」「已归档」。

## 三、不实施范围（显式）

- **不删旧版题库行**、不改外键、不做表重建 migration；
- **不改选题/评分/报告逻辑**——这些链路对 archived 的不敏感性是登记的不变量
  （除 R5 的主动放开外，无任何消费端「需要」感知 archived；若实施中发现某处
  `WHERE status='active'` 隐式承担了旧版过滤职责，属于冲突，**停手上报**而不是顺手改）；
- 不做 archived 的恢复入口（unarchive）——无需求先例，不预设；
- 不迁移历史数据（含 scope=general 遗留行——按 model_id 集合谓词自然覆盖，
  其所挂模型被更新 confirmed 取代时同样归档；模型行仍在 active 概念下的不动）；
- 不动 §10.4 readiness 检查逻辑（它按 task 行 + 模型绑定工作，与归档正交）。

## 五、与现存实现的两个潜在冲突点（供实施时留意）

### C1：eval_seed 与本机制的邻接

`virtual_candidates` 的占位题 `status='eval_seed'` 是 eval 工具特定设计：
不进选题池、仅 eval 自身会话可见。本设计的归档谓词是 `status='active'`，
天然不触碰 eval_seed 行（master 表 status CHECK 不存在；本设计也不引入新
status 语义覆盖）。但注意：`_get_or_seed_bank` 创建会话**按最新 confirmed 模型
锚定**，其后查询带 `status IN ('active','eval_seed')` **不带 model/version 绑定**
——新版本题库落库后，eval 会话的题目查询 `WHERE position_id=? ... LIMIT 3` 会
**串到新模型版本的题上去**（旧版 active 行也同病）。这是**现存缺陷，与本次
归档设计正交**（eval 工具偶用、且其分离声明 WR-13 是「与真实选题池隔离」，
不是「与多版本隔离」）。本设计不为 eval 工具修缺陷，仅登记——如需修复
（查询补 model/version 绑定）另行授权。

### C2：retry 幂等查重与归档行的相互作用

R3 堵住了 confirm-取代场景的重跑；但若 retry 发生在「归档之前」但任务 FAILED
在「归档之后」（时序竞争：confirm 事务归档旧版 / 旧版 FAILED task 行同时存在——
现行 retry 只认 FAILED，409 护栏按「该岗位存在更新 confirmed 模型」判定，与
归档行无关，判定基准稳定，无竞争窗口）。此点无需额外设计，登记说明即可。
